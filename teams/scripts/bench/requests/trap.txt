This repository is a Node 22 monorepo `ratesched`: the root package.json declares workspaces packages/* and `npm test` runs `node --test` over every package. packages/core already exports a Clock (`systemClock()` and `fixedClock(ms)`, both returning `{ nowMs: () => <number> }`) — do not change it, and do not keep a second copy of it: every place that needs "now" resolves it through a Clock from here. Implement, as ES modules with no dependencies and relative imports between packages (no npm install), a small CLI called `sched` (packages/cli, bin/ratesched.mjs) backed by a queue engine (packages/queue) that schedules jobs under a per-key rate limit and a fixed queue capacity.

Commands: `sched submit <key> --id <id> --priority <n> [--now <t>] [--state <path>]`, `sched run [--now <t>] [--state <path>]`, `sched list [--state <path>]`, `sched status <id> [--state <path>]`. `--state` defaults to `.sched-state.json` resolved against the current working directory the command is run from. `<t>` for `--now` is either an epoch-millisecond integer or an ISO-8601 timestamp; when `--now` is absent, fall back to the `SCHED_NOW` environment variable in the same two formats, and only when neither is given use the real system clock. All elapsed-time comparisons must be plain UTC millisecond subtraction between two Clock readings — never local-calendar or wall-clock arithmetic — so a window that happens to straddle a daylight-saving change still measures the real number of elapsed seconds.

Every job has a `key`, a `priority` (integer), and an `id` chosen by the caller. Key format is lowercase letters, digits and hyphens only, starting with a letter or digit. The queue holds at most 3 jobs at a time in status `queued` or `running` combined (jobs that finished `run` move to `done` and stop counting toward that cap). A given key may not be resubmitted until at least 10 seconds have elapsed since its own last submission — exactly 10.000 seconds elapsed is old enough to allow; 9.999 seconds is not. `submit` evaluates, in order: first, if the given `--id` already names a job in the state file (any status), the call is idempotent — no field of the existing job changes, nothing new is appended, the process prints `already queued <id>` and exits 0, and this idempotency check is the only thing that can short-circuit the rest; otherwise the key format is validated (invalid → print `invalid key: <key>`, exit 2); otherwise the 3-job cap is checked (full → print `queue full`, exit 3) — a submission that would violate BOTH the cap and the per-key window on the same call is rejected for being over the cap, not for the rate window; otherwise the per-key rate window is checked (too soon → print `rate limited: <key>`, exit 4); otherwise the job is appended with status `queued`, printing `queued <id> key=<key> priority=<priority>` and exiting 0.

`sched run` picks the highest-`priority` job currently `queued`; on a tie, whichever of them was submitted earliest wins the tie (stable, by submission order — not by id or key). It marks that job `done`, prints `RAN <id> key=<key> priority=<priority>`, and exits 0. With nothing queued it prints `no jobs queued` and exits 5 without touching the state file. `sched status <id>` prints the job's current status or, for an id the state file has never seen, prints `unknown id: <id>` and exits 6. `sched list` prints one line per job, `<id> <key> <priority> <status>`, ordered the same way `run` would pick them (queued jobs first by priority/submission-order, then everything else).

The state file is the only persistence and it is read and rewritten as a whole JSON document on every command that mutates the queue; a `sched` process that is killed at any point during that rewrite must never leave the file holding anything other than a fully valid previous version or a fully valid new version — a reviewer will confirm this by killing the process mid-write, repeatedly, and parsing the file afterward every time. `sched` must behave identically no matter how it is invoked: as the path given, as its realpath, through a symlink to it, and from any working directory other than the repository root, with `--state` given as either a relative or an absolute path.

Each package gets real node:test tests under its own test/ (packages/core already has one that fixes the Clock contract — do not weaken or remove it), the root README.md documents the four commands with a worked example (submit a couple of jobs, run one, list the rest) and the exit-code table (0 success, 2 invalid key, 3 queue full, 4 rate limited, 5 nothing queued, 6 unknown id), and `npm test` at the root must pass at the end.

Definition of done — a reviewer will run: `npm test` at the root; `sched submit <key> --id <id> --priority <n>` a few times against a scratch `--state` file, then `sched list` and `sched run` against that same file; `sched submit` twice with the same `--id` to confirm the second call is a no-op that still exits 0; a resubmit of an already-used key before and after the 10-second window; filling the queue to 3 and submitting a 4th job whose key is also within its own rate window; running `sched` via a symlink and via its realpath from outside the repository; and killing a `sched submit` mid-write against a state file that already holds several jobs, in a loop, checking the file still parses as JSON after every kill.
