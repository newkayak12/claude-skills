- v0.41.0 — **defect packages filed after shape are ordered by touches; the daemon survives Mac sleep/wake** (2026-10-06). **Defect ordering** (design doc C7, found by the 0.40.1 real run ws-a6b31c1b, blocked at integrate:2 for $54.43): QA filed D1-D4, which all touch `packages/csv/src/record.mjs`, and D7/D9/D10/D11, which all touch `packages/rules/src/index.mjs`, with no ordering among them. They ran in parallel, the merges conflicted, and the daemon only suggested `tm_retry` repackage, so the unattended run stopped before report. Now `fileDefects` (QA `settleQaRound`, `tm_file`, `fileUpstreamDefects`, audit) gives every package it files a dep on each earlier package whose touches overlap, using the same `touchScope`/`scopesOverlap` rule shape applies (containment counts as overlap). It skips repair packages, the filer and every package that depends on it (so an upstream fix never orders behind its downstream filer, and no cycle forms), and packages whose latest accept is skipped, unreachable or final-failed. A not-yet-done package becomes a dep only if it was itself filed. Explicit deps come first, so the base branch is unchanged when the filer names deps. When it names none, the first overlap dep's delivered branch becomes the base, so the fix builds on the work it overlaps. Replaying the ws-a6b31c1b defects turns D1-D4 and D7-D11 into backward-pointing chains. **Sleep/wake** (a Mac sleep killed or wedged runs): the daemon tick and every `tm_*` path compare wall-clock and monotonic deltas, and a forward gap of 60s or more (`SUSPEND_GAP_MS`) is recorded as `suspend_detected`, together with `task.suspended_ms`, `resumed_at` and `suspends` (merged, idempotent, clipped to the task's creation; past the 50-entry cap, `suspends_floor` clips each new suspend to start after the newest dropped one, so a repeat of a dropped suspend is not counted again). The stall watchdog measures idle time from `resumed_at` at the earliest. The timebox subtracts suspended time, and so does the ask timeout for suspends after the ask started waiting. A driver death in the wake window (10 min, `WAKE_WINDOW_MS`) gets one free restart per driver per suspend. The lock wait deadline uses `performance.now()`, and the daemon catches `LockTimeoutError`, records `daemon_lock_timeout` once per streak and retries after 1s instead of exiting. On darwin the daemon spawn also starts `caffeinate -i -w <daemonPid>`. No default value changed. On a machine that never sleeps nothing changes, with one exception: a forward wall-clock step of 60s or more (NTP, a manual change) reads as a suspend. `caffeinate -i` blocks idle sleep only. It does not stop lid-close or forced sleep, so detection and the wake rules still do the work there. Whether `performance.now()` pauses across a darwin sleep has not been verified on a real Mac yet. Out of scope (still wall-clock): the broker's `STALE_AFTER_MS` for ownerless nodes and `budget_grace_minutes`. Known gaps: `crashesClustered` still reads wake-time deaths as clustered pushback; the `tm_status` ask `expires_at` display ignores suspended time; the `task.daemon.restarts` counter is not wake-aware; `suspends` is capped at 50, so older suspends can drop out of the ask and free-restart sums; a live owner that holds the lock forever leaves the daemon retrying after one record. graph 1.8.2 gets its own monotonic lock deadline (no shared code). Tests: teams suite 1085 (from 1066): 4 defect-ordering tests (3 failed before), the new `test-sleep.mjs` (14: 12 failed before, including the cap idempotency test; the never-sleeping no-op guard and the `serviceHarnessRun` after-wake stamp test pass both ways) and 1 store test that failed before. graph suite 146 (from 145). The real end-to-end run of 0.41.0 has not been done yet.

- v0.39.0 — **one transactional task store** (2026-10-02 architecture review; seam-beta-D2 torn read in foldChild, seam-silent-beta-E1, and the v0.26.3 daemon + tm_submit double fold of one dispatch were each patched locally, never at the store). New `mcp/store.mjs` `mutateTask(id|path, fn)`: lock → read fresh from disk → `fn(fresh)` → write-then-rename, all under one lock. A lock timeout (`TEAMS_LOCK_TIMEOUT_MS`, 5000) now THROWS `LockTimeoutError` instead of falling through and writing unlocked; a live owner is never stolen; a dead owner is stolen through a separate `<lock>.steal` lock, so two stealers cannot both win (the first version of the steal lost 2 of 105 updates with 6-10 processes contending on a planted dead lock; the shipped version lost 0 in 460 contention rounds, including dead, garbage and chained `.steal` files). `fn` must be synchronous, a throw aborts with nothing written and the ledger lines dropped, and an unchanged task is not rewritten. Every task-state write goes through it: each `tm_*` handler and each daemon phase is its own transaction, and `saveRun` of a `task.json` outside one throws `outside mutateTask` — strict is always on, no flag. **Claims before side effects**: `advanceDispatches` and `prepareReadyIntegrations` (daemon and `tm_next` both run them) claim the node in a transaction (owner pid, token, attempt) before `openChild`, `git worktree add`, `prepareIntegration`, `mergeInto` or the fold, then apply the result only if the claim still holds (else `claim_lost`); a node another live owner claimed is skipped, a failed effect is `claim_failed` and goes back to pending, a dead owner's claim is `claim_reclaimed`. Before, a daemon `advanceDispatches` racing `tm_next` on one ready dispatch opened 2 child runs, and the daemon and `tm_submit` could fold one dispatch twice; now exactly one. **Judge compare-and-set**: the daemon no longer holds a snapshot across `await judge`; it stamps the node (`n.judging`), judges a copy, and applies the verdict only if the node is still pending at the same attempt and reopen count with its stamp, else drops it as `judge_superseded` (ledger + node). A superseded size verdict spawns no driver. `QUESTIONS_CONTRACT` has one source: exported from prompts.mjs, imported by taskmanager.mjs. **Opens that lost their claim**: an open writes an intent file (`opening/<token>.json`) before `openChild`. If its effect ran but the claim was lost or `openChild` threw, the driver is stopped and the child run marked `retired` (`open_undone`); if the apply threw or the process crashed, the finished intent is adopted (`open_adopted`), otherwise undone and the node reopened, so a worktree never gets a second driver. `openChild`'s ledger lines are held until the apply, so an open that lost its claim writes no dispatch line, and one that crashed and was adopted writes its held dispatch line once, on adoption; when `openChild` itself throws, the held lines are written as evidence, followed by `open_undone`. Known remaining path: the teams broker's child-run `saveRun` sites stay on the locked merge path (they now throw on lock timeout too, but are not read-fn-write transactions). Tests: new test-store (25) and test-store-interleave (40: stale snapshot after a concurrent tm_submit keeps the node, `spec.packages` and `task.decisions`; daemon + tm_next race opens one child; moved node's judge result superseded; lock timeout throws; lost or crashed opens, one in a real subprocess crash), test-prompts +1 (1035). graph 1.8.0 gets its own store (no shared code) and the fixes ported from teams; what was deliberately not ported, and why, is listed under graph README v1.8.0. ## Background: why teams exists (from the old README)

`graph` is built for one shape of work: a request that becomes subgoals, each of which
**changes files** and is verified by **running commands** against a git worktree. That is
the right shape for code. It is the wrong shape for a design document, a research write-up,
or a request large enough that it should be split into several runs across several
worktrees — and it has no notion of a run that manages other runs. `teams` adds exactly that,
on the same engine lineage:

Three things this plugin adds, in this order, each behind the previous one's tests:

1. **Kinds.** A subgoal declares what kind of work it is, and the kind decides which node
   chain it expands into. `subgoal` (code) keeps `implement → test → gate` exactly as today.
   `document` gets `draft → review → gate`: author ≠ reviewer, rubric-based, a missing
   worktree change is not a failure. A spec may mix kinds — "implement the feature and
   update the design doc" is one run.
2. **Entry per flow.** `teams:orchestrate` stays the no-decision entry: `plan` sizes the
   request and picks the flow. `teams:develop` and `teams:document` are thin
   manual entries — trigger words, a `flow` default, a persona set — that hand off to the
   same loop. Nothing in the loop is duplicated.
3. **TaskManager.** A second MCP server in this plugin, `task-manager`, for medium and large
   requests. It sizes, splits into packages with `touches[]` and dependencies, and for each
   package opens a child graph run in its own worktree — **the broker opens it, never a
   node** — then accepts the child's verdict, integrates worktrees, and reports. It reuses
   `mcp/graph.mjs` as a library (DAG, typed edges, retries, settled failure) and reads child
   run files without ever writing them. Small requests skip it entirely.

Design and step list: [`_repo/docs/plans/2026-09-11-teams-taskmanager.md`](../_repo/docs/plans/2026-09-11-teams-taskmanager.md).
