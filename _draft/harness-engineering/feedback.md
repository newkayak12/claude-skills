# Harness Install 피드백

## 1. `user-rules-init.py`에 Kotlin 포인터 플래그 미지원

- **상황**: `--pointer-python`, `--pointer-js`만 존재. `--pointer-kotlin` 없음
- **증상**: `--pointer-kotlin "detekt.yml"` 실행 시 `unrecognized arguments` 에러
- **우회**: `user-rules-init.py add`로 별도 룰 수동 추가
- **제안**: `--pointer-kotlin`, `--pointer-java` 등 JVM 계열 플래그 추가 또는 범용 `--pointer <name> <path>` 형태 지원

## 2. L1 user-rules 저장 경로(`~/.harness/`)가 직관적이지 않음

- **상황**: 프로젝트 디렉토리에서 `harness:install` 실행했는데 `~/.harness/user-rules.md`에 생성됨
- **혼란**: 프로젝트 내부에 생길 것으로 기대했으나 홈 디렉토리에 생성
- **설계 의도**: L1 = 사용자 전역 룰, L2 = 프로젝트별 룰 (cycle 시 생성)
- **제안**: 온보딩 시 "L1은 전역(`~/.harness/`), L2는 프로젝트 내부" 차이를 파일 생성 *전에* 명시적으로 안내할 것


# Harness Cycle 피드백

## 1. 게이트 질문이 한 군씩 너무 느림

- **상황**: Exploration 타입인데도 A→B→C→D→E를 하나씩 물어야 함
- **문제**: 이미 머릿속에 계획이 잡혀있는 사용자에게는 쓰레기 같은 경험
- **제안**: 사용자가 한 번에 컨텍스트를 쏟으면 게이트 항목을 자동 매핑하고, 빠진 것만 추가로 물을 것. "메타 스크립트" 형태로 한방에 입력 가능하게

## 2. Kill 기준을 사용자가 직접 정리하겠다는데 스킬이 강제로 물음

- **상황**: "Kill 기준은 내가 직접 정리할게"라고 했는데 게이트가 답을 요구
- **문제**: Exploration 타입에서 Kill 기준은 사이클 진행 중 구체화되는 경우가 많음. 초기에 억지로 확정시키는 건 형식주의
- **제안**: Exploration 타입은 Kill 기준을 "사이클 중 확정 예정"으로 defer 허용. 대신 cycle-card에 TODO로 남기기

## 3. 로드맵 구성을 AI가 구조적으로 해야 함 — 사용자에게 떠넘기지 말 것

- **상황**: 사용자가 10단계를 raw하게 나열했고, AI는 그걸 그대로 표로 옮김
- **문제**: AI가 가치를 추가하지 못함. 로드맵 구조화는 AI의 역할이다:
  - 사용자의 raw input → 의존성 분석, 순서 최적화
  - 병렬 가능 단계 식별
  - 빠진 단계 제안 (예: 이벤트 스토밍, 프로토타이핑 등)
  - 리스크 높은 단계를 앞으로 당기기 (fail-fast)
  - 마일스톤/체크포인트 설정
  - 3개월 시간 예산 대비 페이징
- **현실**: 사용자가 "1~10" 직접 쓴 건 AI가 안 해주니까 본인이 한 것. 이건 AI 실패
- **제안**: 사용자가 방향과 컨텍스트를 주면, AI가 구조화된 로드맵 초안을 제시 → 사용자가 조정. 순서가 반대여야 한다

## 4. 사이클 내 연속 작업(분석→설계→구현)이 하네스에 의해 구조화되지 않음

- **상황**: "v1 분석 → 전환 포인트 → design doc → ADR → 플래닝 → 구현" 흐름이 사이클 안에서 자연스럽게 이어져야 하는데, 하네스가 이 프로세스를 가이드하지 않음
- **문제**: 사이클을 시작해놓고 실제 작업은 하네스 밖에서 수동으로 진행. cycle-card만 있고, 단계별 진행/완료/다음 단계 전환을 추적하지 않음
- **현실**: 사용자가 "쭉 넘어가자"라고 해야 AI가 다음 단계로 감. 하네스가 단계 전환을 자동 제안하거나, 현재 진행 상태를 추적하는 메커니즘이 없음
- **제안**:
  - 사이클 내 Phase/Stage 개념 도입 (Analysis → Design → Planning → Implementation → Validation)
  - 각 Phase 완료 시 산출물 체크리스트 자동 검증
  - "다음 단계로" 자동 전환 제안
  - 사이클 진행률 추적 (cycle-card에 phase 상태 반영)

## 5. 하네스가 작업 프로세스(R-PG01 "No code before design")를 실제로 강제하지 않음

- **상황**: 하네스 룰에 "No code before design", "Design Doc per major feature" 등이 있지만, 실제 사이클 진행 시 AI가 이 룰을 무시하고 혼자 쭉 진행함
- **문제 사례**:
  - AI가 Design Doc을 사용자와 iteration 없이 혼자 작성
  - ADR을 Design Doc 논의 완료 전에 미리 작성 시도
  - 사용자가 "Design Doc은 나와 iteration으로, ADR은 그 바탕으로" 라고 제동을 걸어야 했음
- **근본 원인**: 하네스 룰이 "주입 ≠ 강제"라서, 룰이 컨텍스트에 있어도 AI가 생산성을 위해 무시. 특히 "쭉 넘어가자" 같은 지시를 받으면 모든 단계를 속도 우선으로 처리
- **제안**:
  - Design Doc/ADR 같은 collaborative 산출물은 하네스가 "사용자 확인 필요" 게이트를 걸어야 함
  - "쭉 넘어가자" ≠ "확인 없이 다 써라". 흐름을 끊지 말되, 결정이 필요한 지점에서는 멈춰야 함
  - stage-inject 시 해당 단계의 산출물 유형(solo vs collaborative)을 명시하고, collaborative는 draft→review→finalize 프로세스 강제

## 6. 산출물을 채팅에만 남기고 문서화하지 않음

- **상황**: 사이클 로드맵(10단계)을 채팅 내 표로만 보여주고, docs/v2에 문서로 작성하지 않음
- **문제**: "모든 산출물은 docs/v2 아래"라는 명시적 지시가 있었는데 무시. 채팅은 휘발성이라 다음 세션에서 유실됨
- **근본 원인**: AI가 "보여주기"와 "기록하기"를 혼동. 채팅에 표를 보여주면 산출물이 만들어졌다고 착각
- **제안**: 하네스가 각 Phase의 산출물 목록과 저장 위치를 명시하고, Phase 완료 시 "이 산출물이 지정 위치에 존재하는가" 검증

## 7. Planning 단계임을 AI가 인식하지 못함

- **상황**: 사용자가 정의한 10단계 중 현재는 "분석 → 전환 포인트 → design doc" 순서인데, AI가 현재 어떤 단계에 있는지 스스로 추적하지 못함
- **문제**: 단계를 건너뛰거나, 이전 단계 산출물을 빠뜨리거나, 다음 단계를 섞어서 진행
- **제안**: 사이클 진행 상태를 파일로 관리하고, 각 행동 전에 "현재 단계가 무엇인지" 확인하는 메커니즘 필요

## 9. 하네스/CLAUDE.md를 AI가 무시하는 구조적 원인

- **질문**: "대체 하네스, CLAUDE.md는 왜 무시하는 거지?"
- **원인 1 — 규칙은 텍스트, 제약이 아님**: `rule-inject`가 "R-PG01: No code before design"을 컨텍스트에 추가해도, 결과는 텍스트가 컨텍스트에 있다는 것뿐. AI가 읽고 가중치에 영향은 주지만 물리적으로 막지 않음.
- **원인 2 — 사용자 즉시 지시가 규칙을 이김**: AI 실제 우선순위는 `① 사용자 최근 명시적 지시 > ② 태스크 완료 욕구 > ③ 주입된 규칙`. "Phase 1부터 다시하자"가 들어오면 CLAUDE.md 내용과 무관하게 실행.
- **원인 3 — 컨텍스트 희석**: 세션이 길어질수록 세션 시작에 주입된 규칙의 attention weight가 줄어듦. 최근 메시지 집중 구조.
- **하네스 자체 인정**: 하네스 문서에 "permissionDecision=allow — 도구 안 막음, 주입 ≠ 강제" 명시. 실제 차단하는 hook은 `hypothesis-immutability` 하나뿐.
- **결론**: AI는 규칙을 읽고 이해하지만 따르는 결정은 확률적. CLAUDE.md/하네스는 그 확률을 조금 높여주는 것이지 보장하지 않음. Verify 없이는 품질은 사용자가 잡아야 함.
- **제안**: 규칙 주입보다 "AI가 스스로 규칙 준수 여부를 체크하고 보고하는" 메타인지 패턴이 더 실효적. 예: Phase 완료 전 "이 산출물이 R-PG01/R-DD04를 위반하지 않았는가?" 자가 점검 후 사용자에게 명시.

## 8. 하네스가 PDCA 루프를 실질적으로 지원하지 않음

- **상황**: Phase 1 재작성 후 "하네스가 이 프로세스에서 도움 준 게 있냐"고 물었을 때, 솔직한 답변은 "거의 없었다"
- **하네스가 실제로 한 것**: Cycle scaffold 생성, SessionStart 룰 주입, settings.json 훅 등록 — 구조적 셋업
- **하네스가 하지 못한 것**:
  - "collaborative 산출물 혼자 쓰지 마라" 강제 → 사용자가 직접 제동
  - roadmap을 docs/v2에 문서로 남기게 강제 → 사용자가 직접 지적
  - snapshot 분석 오류 검출 → 사용자가 직접 정정
  - Phase 완료 시 Verify 체크리스트 실행 → 없음
  - Do → Verify 전환 구조적 유도 → 없음
- **근본 원인**: "주입 ≠ 강제" 원칙이 PDCA의 Verify/Retrospect 단계를 구조적으로 지원하지 않음. 룰이 컨텍스트에 있어도 AI가 생산성 우선으로 무시. Verify가 없으니 루프가 닫히지 않는다.
- **현실**: PDCA에서 Verify 역할을 오롯이 사용자가 담당. 하네스는 Plan(cycle-card) + Do(작업 진행)만 부분 지원, Verify + Retrospect는 공백.
- **제안**:
  - Phase 완료 선언 시 산출물 체크리스트를 AI가 먼저 자가 점검하고 사용자에게 "verify 요청"하는 패턴 필요
  - Verify 없이 다음 Phase로 진입 불가하도록 phase-guard 강화
  - Retrospect 결과(.feedback)가 다음 사이클 rule-inject에 반영되는 피드백 루프 설계 필요


# Harness 총평 — Devil's Advocate (2026-06-10, v0.3.8 기준)

> `/devils-advocate` 로 harness 전체를 stress-test 한 결과. 입장 비판이 목적이므로 찬성 근거는 생략.

**Position**: "harness-engineering(v0.3.8)은 솔로 개발자가 계획 단계를 건너뛰지 못하게 하는, 설치 가능한 규율 시스템으로서 올바른 방향으로 성숙하고 있다."

**Steel-man**: 자기 협상에 무너지지 않는 유일한 강제는 결정론적 훅이다. hard(차단 훅)/soft(주입) 분리는 정확하고, hash chain은 증거 조작을 막고, #015 은퇴는 빼기도 가능함을 증명했다 — 설계의 내적 일관성은 실제로 높다.

**숨은 가정**:
1. 프로세스 준수가 더 나은 제품 결과로 이어진다 (측정된 적 없음)
2. 기계적으로 강제할 가치가 있는 것이 "장부의 무결성"이다 (품질을 결정하는 건 여전히 soft 영역)
3. 다른 솔로 개발자들이 이 수준의 규율을 원한다 (marketplace 배포의 전제 — 외부 검증 0건)

**반론 1: harness는 자기 자신의 Gate 1을 통과한 적이 없다** `[assumption]` · severity: **critical**

이 시스템의 제1원칙은 "만들기 전에 검증하라"인데, harness 자체는 그 검증을 받은 적이 없다. 15개 버전, 26개 메커니즘, 95개 규칙이 쌓이는 동안 harness가 거버넌스한 유일한 제품은 **harness 자신**이다. 가설 등록자 = 실행자 = 심판자 = 대상이 전부 동일인이라 사전등록(pre-registration)의 효력이 구조적으로 소거된다 — 과학에서 사전등록이 작동하는 이유는 심판이 외부에 있기 때문이다. `devils-advocate.md`의 CV-1을 "사람→코드로 강제자 이동"으로 답했지만, 그건 *누가 차단하는가*를 옮긴 것이지 *누가 통과를 판정하는가*를 옮긴 게 아니다.
선례: CMMI류 중량 프로세스 — 프로세스 성숙도 인증과 제품 성공의 상관은 입증되지 않았고, 인증 자체가 목적이 되었다.

**반론 2: 강제의 비대칭 — 훅은 장부를 지키고, 품질은 무방비다** `[structural]` · severity: **high**

hard 강제 4종(phase-guard, immutability, symlink-guard, ratchet)이 지키는 건 전부 **북키핑**이다: jsonl이 안 고쳐졌는가, phase 순서가 맞는가, 워터마크가 후퇴 안 했는가. 정작 결과를 결정하는 것 — 인터뷰를 정직하게 해석했는가, 설계가 좋은가 — 은 전부 soft 주입(모델의 자발적 준수)에 남아 있다. 자기 문서가 이미 인정한다: AP-01(검증 연극)과 AP-04(부정 증거 망각)는 **모든 게이트를 통과하면서** 일어날 수 있다. 솔로 개발자 위협 모델에서 SHA256 체인은 자기 자신을 암호학으로 방어하는 것인데, 진짜 실패 모드(증거 체리피킹)는 체인을 건드리지도 않고 게이트를 지나간다. 강제가 가장 강한 곳과 위험이 가장 큰 곳이 정확히 어긋나 있다.
선례: SOX/감사 추적 시스템 — 감사 로그 무결성은 완벽해도 의사결정 품질은 보장 못 한다는 게 컴플라이언스 업계의 반복된 교훈. Goodhart의 법칙이 ratchet 축(inject-tokens, mechanism-count)에 그대로 적용된다.

**반론 3: 유지보수 플라이휠이 거버넌스 대상을 잡아먹고 있다** `[execution]` · severity: **high**

4,018 LoC, 문서 270KB(문서:코드 ≈ 67:1), 규칙 95개, 메커니즘 26개 — 사용자 1명. 더 나쁜 신호는 성장의 비대칭이다: 추가는 매 버전 일어나지만 은퇴는 15버전 동안 **단 1건**(#015)이고, 그조차 "0회 발화"라는 증거가 ~10버전 누적된 뒤에야 가능했다. 더하기는 싸고 빼기는 장례식이 필요하다. version-doctor는 그 자체가 증거다 — vendoring 배포 모델이 만든 3점 버전 드리프트를 사후에 도구로 봉합한 2차 복잡성이고, session_count는 kill-check 은퇴 후 측정만 되고 쓰이지 않는다(비용만 남은 메커니즘). 이 추세면 다음 사이클들의 상당 지분도 harness가 harness를 고치는 데 쓰인다.
선례: Brooks의 second-system effect + "생산성 시스템이 곧 미루기"가 되는 정교한 Zettelkasten/Notion 시스템 패턴(후자는 부분적으로 speculative — 그러나 git log가 이미 그 방향을 가리킨다).

**핵심 취약점 / Core Vulnerability**

가장 깊은 결함은 복잡도가 아니라 **검증의 방향**이다. 이 시스템은 "속일 수 없는 프로세스"를 만드는 데 모든 정교함을 쏟았지만, 유일하게 중요한 질문 — *이 프로세스를 따르면 더 좋은 제품이 더 빨리 나오는가* — 은 측정조차 설계되어 있지 않다. 숨은 가정 1이 무기화된 형태다: 준수(compliance)는 결과(outcome)의 대리 지표가 아닌데, ratchet·chain·gate 전부가 준수만을 측정한다. harness가 자기 방법론을 진지하게 믿는다면, 다음 사이클의 가설은 "harness로 외부 제품 하나를 끝까지 만들고, 없을 때와 비교 가능한 신호를 남긴다"여야 한다. 그 가설 없이 v0.4를 쌓는 것은 자기 문서가 정의한 AP-01, 검증 연극이다.

**가역성 / Reversibility**: **reversible**
스크립트와 문서일 뿐이고 제거는 즉시 가능하다. 따라서 critical 반론도 "중단하라"가 아니라 "다음 한 수는 메커니즘 추가가 아니라 외부 검증이어야 한다"를 뜻한다. 비가역적인 것은 단 하나 — 계속 자기참조 루프에 쓰는 시간이다.

**Path Forward**:
- 반론 1 해소 조건: harness가 아닌 실제 제품 1개를 harness로 1사이클 완주한 데이터가 존재할 것 (N=1이라도 외부 대상)
- 반론 2 해소 조건: soft 규칙 위반이 실제로 얼마나 일어나는지 friction log 기반 발화 통계가 있고, 그 결과가 hard/soft 경계 재조정에 쓰일 것
- 반론 3 해소 조건: "은퇴 후보" 검토가 사이클 종료 게이트의 정규 항목이 되어, 빼기가 더하기와 같은 비용이 될 것

**총평 한 줄**: 설계 품질은 상위 수준이고 자기 한계 인식도 정직하다 — 그러나 지금 가장 부족한 것은 메커니즘이 아니라 첫 외부 고객(자기 자신의 *다른* 프로젝트라도)이다.
