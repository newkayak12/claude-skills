# teams (team) — v0.12.0 ~ v0.14.0 스코프 사이징

> 상태: **사이징**. 코드 변경 없음. 2026-09-17.
> 대상: `2026-09-17-teams-team.md` §11의 남은 네 행.

## 0. 이 문서가 무엇이고 무엇이 아닌가

**구현 계획이 아니다.** 구현 계획은 파일 경로와 함수 이름을 박고, 그래서 빨리 썩는다 — v0.11.0
계획서는 구현 한 시간 전에 쓰였는데도 이미 낡은 경로 리터럴 하나를 들고 있었고 구현자가 코드에서
고쳐야 했다. v0.13.0의 계획서를 지금 쓰면 그보다 나쁘다.

이 문서가 답하는 것은 하나다: **각 단계에 무엇이 들어가고, 무엇이 빠지고, 얼마나 큰가.** 파일
경로·시그니처·코드 블록을 쓰지 않는다. 대신 설계 문서의 절 번호와, 이미 측정된 세 계획서의 태스크
번호로 근거를 댄다. 그래야 코드가 움직여도 이 문서는 살아 있다.

**추정은 추정이라고 쓴다.** 〔추정〕 표시가 없는 숫자는 실제 계획서에서 센 것이고, 있는 숫자는
보정된 짐작이다. 둘을 섞지 않는다.

## 1. 측정 단위 — task-unit이란 무엇인가

세 계획서(v0.10.0 12개, v0.10.1 8개, v0.11.0 6개)에서 "Task 하나"가 실제로 무엇이었는지를 읽어
보정 기준을 세웠다.

| 일의 모양 | task-unit | 근거 |
|---|---|---|
| 새 순수 모듈 하나 + 전용 테스트 파일 | 1 | v0.11.0 Task 1(티켓 파생), Task 2(문서 렌더러) |
| 매니저 서버 안의 초점 있는 배선 변경 + 테스트 갱신 | 1 | v0.11.0 Task 3(보드 이벤트 + 도구 2개), Task 4(도구 1개), v0.10.0 Task 2 |
| 엔진 파일 하나의 테이블·상수 확장 + 테스트 | 1 | v0.10.1 Task 1(kind 2개), Task 2(계약 3개), Task 3(마운트 2개) |
| 새 프로세스/드라이버 메커니즘 | 1 (단, 가장 무거움) | v0.10.0 Task 11(TaskLeader 드라이버, 계획 본문 253줄 — 전 단계 최대) |
| 두꺼운 entry 스킬 | 각 1 | v0.10.1 Task 4·5 |
| 얇은 명령 스킬 | 2개에 1 | v0.11.0 Task 5 |
| 교차 관심사 가드 + 통합 테스트 | 1 | v0.10.1 Task 7 |
| 릴리스(버전·마켓플레이스·README/KOR Status·설계 문서 갱신·전체 테스트) | **1, 매 단계 예외 없이** | v0.10.0 Task 9, v0.10.1 Task 8, v0.11.0 Task 6 |

**이 단위의 한계를 먼저 밝힌다.** task-unit은 *계획서의 스텝 수*이지 작업량의 등가물이 아니다.
같은 단계 안에서도 v0.10.0 Task 0(계획 본문 12줄)과 Task 11(253줄)은 20배 차이가 난다. 그러므로
이 숫자는 **단계끼리 비교하는 데** 쓰고, 시간으로 환산하는 데는 쓰지 않는다.

## 2. Part 1 — 열린 논점 A-1 판정

### 2.1 질문

역할 셋(기획/개발/QA)은 **대등한 STORY(패키지)**인가, 아니면 기획과 QA는 **EPIC의 phase에 붙는
Team**이고 패키지는 개발뿐인가. §14 A-1은 후자로 기울어 있으나("추천: 대안") 결정 기록에는 닫혀
있지 않다. 이게 v0.12.0의 모양을 통째로 바꾼다.

### 2.2 §14의 논거를 엔진에 대조했다

**논거 1 — "기획은 shape 이전에 필요하다."** 엔진에서는 §14가 말하는 것보다 강하다. 패키지의
dispatch/accept 노드는 **shape가 성공하는 순간 패키지 확장 경로가 한꺼번에 만든다**(설계 문서
§4 주1이 이미 기록한 사실). 즉 패키지는 정의상 shape의 *산출물*이고, 따라서 shape의 *입력*이 될 수
없다. 기획을 패키지로 두려면 반드시 재shape 라운드가 필요한데, 재shape는 `size`를 제외한 모든
미완료 노드를 폐기 처리하고 새 shape·critique를 얹는다. 결과는 죽은 1라운드와 살아 있는 2라운드가
공존하는 그래프이고, 기획 STORY만 라운드 번호가 어긋난 채 남는다. 티켓·문서 파생은 지금 "라운드
하나"를 정상 경로로 삼고 있으므로, 이 선택은 **2라운드 그래프를 예외가 아니라 기본으로** 만든다.

**논거 2 — "QA는 첫 integrate까지 놀고 있다."** 사실이지만 절반만 맞다. 패키지 확장이 만드는
통합 노드는 **모든 패키지의 accept를 의존성으로** 갖는다. 그러므로 shape가 낸 패키지는 놀고 있는
게 아니라 **구조적으로 통합 이전**이다. 통합 이후에 도는 패키지는 만들 수 없다.

**그런데 엔진에는 이미 통합 이후 패키지를 만드는 두 번째 경로가 있다.** 리페어 패키지가 그것이다:
shape를 거치지 않고 스펙에 패키지를 덧붙이고, 실패한 통합의 의존성을 물려받고, 그 뒤에 **새 통합
노드**를 열고, 옛 통합을 가리키던 모든 노드를 새 것으로 재배선한다. 자식 run을 여는 경로도 리페어
패키지일 때는 워크트리를 새로 만들지 않고 **통합 워크트리를 그대로** 준다. 즉 "통합 트리에서 도는,
통합 이후의 패키지"는 이미 출시되어 테스트까지 되어 있는 메커니즘이다 — 다만 **일반화되어 있지
않다**(리페어 전용 플래그로만 열린다).

**그리고 이 일반화는 A-1이 어느 쪽으로 가든 필요하다.** 결정 기록 #2(QA가 결함을 찾으면 결함 STORY를
발행한다)가 요구하는 것이 정확히 "통합 이후에, shape를 거치지 않고 생기는 패키지 + 그 뒤의 새 통합"
이기 때문이다. 그러므로 QA-as-패키지의 기계 비용 중 상당 부분은 **A-1 판정과 무관하게 이미 로드맵에
잡혀 있는 비용**이다(단, §6에서 보듯 지금 §11의 어느 행에도 들어 있지 않다).

**부수 확인 — 자식 run 쪽은 이미 양쪽 다 준비돼 있다.** v0.10.1이 planning/qa kind와 그에 대응하는
flow를 넣었고, 패키지는 자기 flow를 지정할 수 있으며 shape 검증이 이미 알려진 flow만 허용한다.
그러므로 "기획 Team / QA Team이 자기 체인을 도는 것" 자체는 **두 분기 어느 쪽에서도 새로 만들 일이
아니다.** 다만 shape에게 주는 계약 문구는 아직 develop/document 둘만 제시한다 — 이건 한 줄짜리
차이다. A-1이 가르는 것은 체인이 아니라 **순서**다.

### 2.3 두 분기의 비용

#### 분기 A — 역할 셋이 대등한 패키지 (`role`이 shape 출력에 생긴다)

| 항목 | 내용 |
|---|---|
| shape 출력 계약 | `role`이 생긴다. 계약 문구, shape 검증(역할별 필수 필드 — 기획 패키지는 touches가 없다), 그리고 그 계약을 읽는 모든 것(티켓 파생, 문서 렌더러, 골든 픽스처, 벤치 요청)이 따라 움직인다 |
| EPIC 흐름(§2) | 기획 STORY가 끝난 뒤 **재shape가 정상 경로**가 된다. 2라운드 그래프가 예외가 아니라 기본 |
| 통합 | QA 패키지를 통합의 의존성에서 빼고 통합 뒤에 꽂아야 한다 → 리페어 경로의 일반화를 **v0.12.0으로 당겨온다** |
| v0.12.0 비용 | **〔추정〕 8–10 task-unit** |
| 뒤 단계로 미는 것 | 2라운드 파생이 티켓·문서·보드에 영구적으로 남아, v0.13.1의 kill-and-resume 표 테스트가 커진다 |
| 되돌리기 | **어렵다.** shape 출력 계약은 이 시스템에서 가장 넓은 인터페이스다 — 프롬프트 문구, 검증, 확장, 티켓, 문서 골든, 저장된 모든 스펙이 걸린다. 나중에 `role`을 빼는 것은 저장된 스펙을 전부 무효화하는 일 |

#### 분기 B — 기획/QA는 EPIC의 phase에 붙는 Team (§14 추천안)

| 항목 | 내용 |
|---|---|
| shape 출력 계약 | `role`이 **없다**. §5가 이미 그렇게 쓰여 있다("`role` 필드는 없다 — shape가 내는 것은 전부 develop"). 추가되는 것은 `implements[]`와 `priority`뿐 |
| EPIC 흐름(§2) | EPIC 생성 시 노드 목록에 기획 phase는 shape **앞**, QA phase는 통합 **뒤**로 조건부 삽입. 켜고 끄는 스위치는 이미 프로젝트 설정에 있다 |
| 통합 | 통합 노드의 의존성은 그대로. QA는 통합과 목표 게이트 **사이의 노드 삽입** |
| v0.12.0 비용 | **〔추정〕 7–8 task-unit** |
| 뒤 단계로 미는 것 | 리페어 경로의 일반화(=결함 STORY)를 그것이 실제로 필요한 단계로 미룬다 |
| 되돌리기 | **상대적으로 쉽다.** 바뀌는 것은 노드 그래프의 내부 모양이고, 진행 중인 EPIC 파일은 깨지지만 shape 계약과 저장된 스펙은 건드리지 않는다 |

**여기서 해석이 들어갔음을 밝힌다.** 설계 문서는 "phase에 붙는 Team"이 *어떤 노드 종류로* 실려
자식 run을 여는지 말하지 않는다. §2는 "기획 Team = TaskLeader의 plan/setgoal 단계를 위임받은 팀"
이라고만 하고, §9 변경 지점 표에도 그 노드가 없다. 나는 **패키지 dispatch와 같은 모양의 노드를
스펙에 없는 합성 id로 여는 것**이 가장 싼 읽기라고 보고 그 전제로 비용을 냈다. 다른 읽기(새 노드
종류를 만든다)를 택하면 분기 B가 1 task-unit 늘어난다.

### 2.4 추천

**분기 B(§14의 대안)를 권한다.** 근거는 §14가 든 두 가지가 아니라, 대조에서 나온 셋이다.

1. **분기 A의 기획 절반은 엔진이 금지한다.** 패키지는 shape의 산출물이므로 shape의 입력이 될 수
   없다. 재shape로 우회할 수는 있으나 그 대가로 2라운드 그래프가 정상 경로가 되고, 이미 출시된
   티켓·문서 파생이 그 복잡도를 영구히 진다.
2. **원시 비용 차이는 크지 않다(8–10 대 7–8).** 결정의 근거는 개수가 아니라 **되돌리기 비용의
   비대칭**이다. 분기 B를 잘못 골랐으면 노드 그래프를 고치면 되고, 분기 A를 잘못 골랐으면 shape
   계약과 저장된 스펙을 전부 고쳐야 한다.
3. **분기 A가 사는 유일한 세계는 "기획도 QA도 여러 개일 때"다.** 기획 STORY가 둘 이상 병렬로
   필요하거나 QA Team이 영역별로 쪼개져야 한다면 패키지가 맞다. 설계 문서 어디에도 그 요구는 없고,
   §2는 오히려 기획이 EPIC 안에서 **두 번**(초안 + 크로스 검수) 돈다고만 말한다 — 이건 순서지
   병렬이 아니다.

**단서 하나.** 분기 B를 택해도 "통합 이후에 생기는 패키지"는 결국 만들어야 한다(결정 기록 #2).
분기 B는 그 일을 없애는 게 아니라 **v0.12.0 밖으로 미룬다.** 그 일이 지금 §11의 어느 행에도 없다는
것이 §6의 문제다.

## 4. 단계별 스코프

### 4.1 v0.12.0 — 개발 STORY의 순서·할당, 그리고 기획/QA가 EPIC 흐름에 들어온다

전제: **A-1이 분기 B로 결정된 경우.** 분기 A면 아래의 "범위 밖" 첫 줄이 범위 안으로 들어오고 크기가
8–10으로 바뀐다.

**범위 안 (행동으로)**
- 프로젝트 설정의 역할 스위치가 실제로 작동한다 — 기획을 켜면 EPIC이 shape **앞**에 기획 단계를
  갖고, QA를 켜면 통합 **뒤**에 QA 단계를 갖는다. 둘 다 끄면 지금의 흐름과 동일하다(하위 호환).
- 기획 단계가 산출한 PRD가 shape의 입력이 된다. shape는 자기가 낸 각 STORY가 어느 user story를
  구현하는지 매핑을 남기고, 빠진 user story가 있으면 거부당한다.
- QA 단계는 **통합 트리**에서 돈다 — 자기 워크트리가 아니라, 모든 패키지 브랜치가 합쳐진 그 트리.
- STORY가 우선순위를 갖고, 동시에 도는 Team 수에 상한이 걸린다. 지금은 준비된 dispatch를 **전부**

### 남은 비율

> **약 59–64% 남음. 중앙값 ~61%.**

**오차 막대와 그 근거**
- 측정된 부분은 **3 task-unit**뿐이다. 남은 일의 **약 91%가 추정치**다 — 이 문서를 쓰기 전보다
  비율이 나빠 보이는 이유는, v0.11.0이 거의 끝나서 측정된 잔여가 얼마 안 남았기 때문이다.
- 개별 단계 추정의 오차는 **±30%**로 본다(보정 표본이 세 단계뿐이고, 한 task-unit의 실제 무게가
  단계 안에서 20배까지 벌어지므로).
- **v0.14.0은 오차 막대 밖이다.** 워크트리 기준점 결정이 비싼 쪽으로 가면 혼자서 2배가 된다.
- **체계적 위험 하나**: 이 라인은 실제 벤더 실행으로 한 번도 검증된 적이 없다(v0.10.1의 자기
  검토란). 첫 실측(v0.13.1)이 무엇을 드러내든, 그것은 남은 단계가 아니라 **이미 완료로 센 23**을
  사후에 다시 열 수 있다. 이 경우 위 비율은 낙관적인 쪽으로 틀린다.

## 부록 — 근거 추적

모든 크기 주장이 아래 둘 중 하나에 걸려 있다.

**측정된 계획서에서 센 것**: v0.10.0 = Task 0–11(12개), v0.10.1 = Task 1–8(8개), v0.11.0 =
Task 1–6(6개). 보정 규칙은 §1의 표.

**엔진을 읽고 확인한 것** (설계 문서의 어느 절이 이미 옳은지, 무엇이 이미 만들어져 있는지):
1. 패키지의 dispatch/accept는 shape 성공 시 **한꺼번에** 만들어진다 → 기획은 패키지가 될 수 없다(§2.2).
2. 통합 노드는 **모든** 패키지의 accept에 의존한다 → shape가 낸 패키지는 통합 이후에 설 수 없다(§2.2).
3. 리페어 패키지 경로가 이미 **통합 이후 + 통합 워크트리 + 새 통합 재배선**을 한다 → QA/결함
   STORY의 기계 절반은 이미 존재한다(§2.2, §4.1의 3번).
4. planning/qa kind와 flow는 v0.10.1에 이미 있고 패키지 검증도 통과한다 → A-1이 가르는 것은
   체인이 아니라 순서다(§2.2).
5. 준비된 dispatch는 지금 **전부 한꺼번에** 열린다 → 동시 실행 상한은 순수한 새 동작이다(§4.1의 5번).
6. run 상태 집계는 여섯 상태 고정이고 "막힘"은 준비·실행 카운트로 파생된다 → 사람 대기 상태는
   엔진의 상태 어휘를 건드린다(§4.2의 1번).
7. 프로젝트 설정 모듈은 대화 모드·사람 게이트·역할 스위치·동시 팀 수·깊이·QA 라운드를 **이미
   해석하고 기록하되 아무도 읽지 않는다**(모듈 주석이 명시) → v0.12.0~v0.14.0의 설정 배선 비용은
   이미 지불됐다(§4.1의 1번, §4.4의 1번).
8. 마운트는 **단계 키로만** 되어 있고 코드 주석이 그 부작용을 인정한다 → 가이드 2·6번은 부분(§7).
9. 티켓 파생은 사용자 대기 상태를 이미 쓸 줄 알지만 "그것을 만들 실행자가 없다"고 주석에 적혀
   있다 → v0.13.0에서 처음 도달 가능해진다(§4.2).
10. 결함 STORY·크로스 검수·정리 도구·로그 도구는 **코드 어디에도 없고 §11 어느 행에도 없다**(§5).
11. phase 문서 렌더러는 8장이고, §7c가 요구한 기획·PRD·스펙 게이트·QA·검수 5장은 아직 없다 →
    v0.12.0과 v0.13.0이 각자 몫을 만든다(§4.1의 6번, §4.2의 7번).
