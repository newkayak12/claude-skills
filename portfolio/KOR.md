# portfolio — 한국어

[English](README.md) · **한국어**

지원 과정 전체를 다루는 스킬 모음입니다: 공고가 실제로 원하는 걸 읽어내고, 어디서 경쟁력이
있는지 정하고, 실제 경험이 실제 레벨대로 읽히게 문서를 다시 쓰고, 말로 방어할 수 있을 때까지
연습하는 것. 스킬들은 일부러 좁게 나눠져 있고 서로 겹치지 않습니다 — 포트폴리오 채점, 글쓰기
패턴 진단, 문장 리라이팅, JD 매칭은 각각 다른 작업이고, 각 스킬은 자기가 *아닌* 것을 명시합니다.

전부 한국 채용 시장 기준으로 맞춰져 있습니다 — 회사 유형별 프로파일, ATS 규칙, 컬처 시그널이
`references/ats-rules-korea.md`와 `references/korea-company-culture-signals.md`에 있습니다.
분석 결과물은 기본적으로 한국어로 씁니다.

여러 스킬이 가장 판단 비중 큰 지점(갭 심각도 분류, 서류 통과 가능성, 오너십 분류)에서
`think-tool`과 `mcp-reasoner`를 필수 체크포인트로 씁니다. Claude 설정 → MCP Servers에서
remote SSE 엔드포인트로 추가하세요.

## 설치 / 제거

```bash
/plugin install portfolio@newkayak12-claude-skills
/plugin uninstall portfolio@newkayak12-claude-skills
```

## 어떤 스킬을 쓰나

| 하고 싶은 것 | 스킬 |
|---|---|
| JD부터 면접 당일까지 지원 전 과정 | `job-application-workflow` |
| 특정 공고 하나에 얼마나 맞는지 | `portfolio-jd` |
| 공고 없이 어디에 지원할지 정하기 | `portfolio-company` |
| 면접관 시각의 솔직한 포트폴리오 평가 | `portfolio-feedback` |
| 숫자·스킬 목록·날짜, 그리고 주장하는 레벨이 앞뒤가 맞는지 | `portfolio-feedback` |
| 포트폴리오가 왜 "오너십 없어 보이는지" 찾기 | `portfolio-pattern` |
| 약한 문장을 시니어 수준으로 리라이팅 | `portfolio-rewrite` |
| 특정 JD 어휘에 맞춰 이력서 최적화 | `resume-tailorer` |
| 면접 전 주차별 학습 계획 | `interview-prep` |
| 모의 면접으로 내 작업 방어 연습 | `portfolio-interview` |
| PPTX 전체 슬라이드 키컬러 일괄 교체 | `ppt-keycolor-changer` |

## 스킬

### `job-application-workflow`

진입점입니다. 특정 역할 하나에 대해 네 단계: JD 분석 → 회사 리서치 → 이력서·포트폴리오 튜닝 →
면접 준비. 타깃 회사와 공고가 손에 있을 때 씁니다. "커리어 뭘 해야 하지" 같은 열린 질문이나,
이미 면접을 통과해 오퍼 협상 중일 때는 건너뜁니다.

```
쿠팡 백엔드 공고, 다음 주에 지원하려고 해. JD 아래 붙였고
JD 분석부터 면접 준비까지 전체 프로세스 같이 돌려줘.
```

```
[1] portfolio-jd          JD 해독, must-have vs nice-to-have, 핏 갭
      ↓
[2] portfolio-company     컬처 시그널, 대화 소재, 레드 플래그
      ↓
[3] resume-tailorer (+ portfolio-rewrite)   맞춤 이력서, 커버레터 초안
      ↓
[4] interview-prep        STAR 스토리 뱅크, 예상 질문, 역질문
```

각 단계에 skip 조건과 standalone 입력 대체안이 있어서, JD와 회사 이름만으로 Step 4부터 시작할
수도 있습니다. 전체 3–10시간, 단계당 30–90분 정도입니다.

### `portfolio-jd`

JD와 포트폴리오를 *따로* 파싱합니다 — 너무 일찍 비교하면 포트폴리오 프레이밍 쪽으로 판단이
쏠리기 때문입니다. 그다음 다섯 차원으로 핏을 채점합니다: 기술 스택, 경험 스케일, 역할 범위,
도메인, 소프트 시그널. 갭마다 치명적 / 보완 가능 / 마이너 등급과 그 등급인 이유가 붙습니다.
마지막은 서류 통과 가능성에 대한 솔직한 판단과, 그걸 가장 크게 바꿀 요인 하나입니다. 공고 없이
회사 유형만 볼 거면 `portfolio-company`, 이력서 키워드 작업은 `resume-tailorer`.

```
내 포트폴리오랑 시리즈 C 핀테크 시니어 백엔드 JD 전문이야.
핏 점수 내고, 어떤 갭이 치명적인지, 서류 통과 가능성 솔직하게 말해줘.
```

```
[종합 매칭 점수]  7 / 10
- 기술 스택 8/10   - 경험 스케일 6/10   - 역할 범위 7/10
- 도메인 5/10      - 소프트 시그널 8/10

[갭 분석]
갭: 결제 도메인 경험 없음
심각도: 보완 가능
대응 방법: 커버레터에서 정산 배치 경험을 도메인 인접성으로 프레이밍
```

### `portfolio-company`

특정 공고가 없을 때 씁니다. 이 포트폴리오가 어떤 유형의 엔지니어로 읽히는지 규정한 뒤, 한국
회사 유형별로 핏을 채점합니다 — 대형 플랫폼, 성장기 스타트업, 핀테크/엔터프라이즈, 글로벌 테크,
개발도구/OSS. 각 유형이 *말하는* 요구사항이 아니라 *실제로* 보는 것과 함께 green flag /
red flag를 냅니다. 가장 잘 맞는 Top 2와 고전할 유형을 지목합니다. 회사 인지도만으로 핏을
매기지 않고, 양보 못 할 조건(지역·도메인·스택)을 먼저 묻습니다.

```
백엔드 5년, 중견에서 사내 플랫폼 작업 위주였어. 아직 정한 공고는 없고,
이 포트폴리오가 실제로 어디서 경쟁력 있을지 봐줘.
```

회사 유형마다 핏 점수, 그 점수의 근거가 된 포트폴리오 내용, 구체적 미스매치, 그리고 지원 전
보완할 것 하나가 붙습니다.

### `portfolio-feedback`

이번 주에만 포트폴리오 백 개를 본 면접관처럼 읽습니다 — 있는 것보다 *없는 것*에 패턴 매칭을
겁니다. 리뷰어 페르소나 넷 중 하나를 고르면(대형 플랫폼 Staff / 스타트업 EM / 엔터프라이즈 Tech
Lead / OSS·DevTools Lead) 끝까지 그 시각을 유지합니다. 다섯 차원을 채점하고, 7점 이상은 전부
"회의적인 면접관이라면 뭐라고 깎을까"로 반박을 겁니다. 그 반박을 견딘 점수만 살아남습니다.
문장 리라이팅은 `portfolio-rewrite`, JD 매칭은 `portfolio-jd`.

```
대형 플랫폼 스태프 엔지니어 시각으로 내 포트폴리오 평가해줘.
면접장에서 듣느니 지금 듣는 게 나으니까 세게 봐줘.
```

다섯 차원: Technical Depth · System Design · Impact and Results · Leadership/Ownership ·
Portfolio Narrative. 점수는 *완전히* 충족한 최고 레벨이며, 부분 근거로 올림하지 않습니다.
출력에는 핵심 취약점 하나, 이 페르소나가 반드시 물을 질문 5개, 우선순위 매긴 개선 3개가
포함됩니다. 루브릭과 페르소나: `references/scoring-rubric.md`, `references/personas.md`.

```
[차원별 점수]
Technical Depth: 6 / 10
근거: Kafka 도입은 서술되어 있으나 대안 검토와 트레이드오프가 없음
🧠 Devil's advocate: 규모 수치는 인상적이나 본인 기여 범위가 불명확 — 7 → 6
```

인터뷰어 관점의 심사에 더해, 그 문서가 읽히기는 하는지에 답합니다. 문서 컨벤션 검사
(`references/resume-conventions.md` — 요약 블록, 불릿 예산, XYZ+S 형태, 섹션 순서, 언어별 오너십
규칙)를 나열이 아니라 수치로 집계하고 스크린 비용 상위 5개로 압축하며(`XYZ+S n/m · 의사결정 동사 n%`),
ATS/파서 안전성 검사(표·이미지에 갇힌 증거, 비표준 섹션 헤더, PDF 헤더의 연락처 — 문서는 읽히기
전에 파싱됩니다), `[AI 스크리너 요약]` — 스크리닝 모델이 실제로 생성할 3줄 요약과 거기서 살아남지
못한 최강 증거, 그리고 스크리닝 연구에 근거한(`references/screen-models.md`) 2-리더
`[서류 스크린 판정]` — 리크루터 6초 패스(Ladders 아이트래킹의 F-패턴 가시 영역만으로 판정)와
엔지니어 30초 스킴(오탈자·기술명 오기 체크, Lerner의 보정 데이터)을 각각 통과/경계/탈락으로 —
및 `[레드 플래그]` 블록(경력 갭, 잦은 이직, 직함 인플레이션, 검증 불가 주장 비율 등, 플래그마다
면접 방어 답변 한 줄)이 있습니다. 스크리너는 떨어뜨릴 이유를 찾으므로 플래그는 강점과 상계하지
않습니다.

이 스크린 레이어는 `-beta` 레인에서 개발한 뒤 두 번의 헤드투헤드 벤치마크(실제 40페이지 포트폴리오,
impressive-surface 픽스처)를 거쳐 합류했습니다. 양쪽 모두 차원 점수와 핵심 취약점 판정이 일치했고,
동시에 스크린 패스는 실질 리뷰가 구조적으로 낼 수 없는 발견을 순증했습니다 — 설명 없는 8개월 공백,
두 문서에서 서로 다른 지표에 붙은 같은 수치, 연락처가 아예 없는 이력서.

이전 버전을 같이 주면 **리비전 모드**(`references/revision-diff.md`)로 전환합니다. Before/After
집계표와 스크린 판정이 움직였는지로 시작하고, 후퇴는 별도 줄로 — 리라이팅이 *새로 만든* 주장(불릿은
여전히 개발인데 요약만 설계가 된 경우)까지 포함 — 쓰며, 기간이 붙은 주장("12개월 무사고")은 오늘
날짜와 대조합니다. v1/v2 헤드투헤드에서 구조화된 비교가 즉석 비교가 놓친 후퇴 두 건을 잡아 베타에서
승격했습니다. 집계 분모는 같은 파일에 고정해 두 버전을 항상 같은 방식으로 셉니다.

여기에 문서가 스스로와 맞는지를 묻는 세 패스(`references/claim-and-consistency.md`)가 더 붙습니다.
**정합성 교차 검사** — 섹션 간 날짜와 요약의 경력 연수, Skills 항목 하나하나를 그것을 증명하는
불릿과 대조(`스킬 근거율 n/m`, 근거 없는 항목은 이름을 지목), 직함 주장과 불릿 동사의 불일치.
**주장 감사** — 성과 불릿마다 수치·베이스라인·기간·기여 범위가 있는지(`완전 주장 n/m`), 최악의 세
개를 그것이 부르는 면접 질문 그대로와 함께 지목(이 집계는 Impact 점수의 천장이지 점수 자체가 아님).
**레벨 캘리브레이션** — 문서가 주장하는 레벨(연차·직함·지원 포지션)과 4단 근거 사다리(주니어 / 미드
/ 시니어 / 리드)에서 실제로 읽히는 레벨을 대조, `레벨 갭 ±n`과 천장을 정한 불릿 두 개. 과대 주장은
숫자가 붙은 직함 인플레이션 플래그, 과소 주장은 개선 우선순위 #1.

```
7년차 시니어라고 썼는데 이 문서가 진짜 시니어로 읽히는지 봐줘
```

```
레벨 갭: 주장 시니어 / 읽힘 미드 (−1) — 천장: "주문 조회 API 1.2s → 380ms", "중복 차감 주 12건 → 0건"
XYZ+S 0/8 · 완전 주장 2/3 · 스킬 근거율 5/6 · 날짜 불일치 0 · 레벨 갭 −1 · 의사결정 동사 0% · 불릿/롤 max 5
```

모든 리뷰는 이 집계 한 줄로 끝나고, 지원자는 자기 문서와 대조해 직접 다시 셀 수 있습니다 — 세기
전에 목록을 쓰고, 분모를 고정하고, 발견은 한 번만 말하고, 임계값은 잠정치로 표기합니다(§D, §F).
이 패스들은 세 번의 벤치마크 끝에 `-beta` 레인에서 승격했습니다. 앞의 두 번은 발견 항목은 동등하고
`레벨 갭` 하나가 추가됐지만 집계에 오류가 있었고, 카운팅 규칙을 고정한 뒤의 세 번째는 두 픽스처
모든 집계가 손으로 계산한 정답과 일치했습니다.

### `portfolio-pattern`

내용이 아니라 **읽히는 방식**을 봅니다. 여섯 차원을 감사합니다: 의사결정 동사 비율(제안/채택/배제
vs 맨 개발했습니다), 행위 주체 표현, 숫자 밀도, 실패 서사 유무, 의사결정 가시성, 동사 에너지. "오너십이 안
보인다"는 피드백은 받았는데 어디가 문제인지 아무도 못 짚어줄 때 씁니다. 지적된 문장을 고치는 건
`portfolio-rewrite`, 전체 채점은 `portfolio-feedback`.

```
포트폴리오에 오너십이 안 드러난다는 말을 계속 들어. 글쓰기 패턴 분석해서
그런 인상을 주는 실제 문장들을 짚어줘.
```

적용하는 기준선: 시니어 포트폴리오에서 행위 문장 중 의사결정 동사를 가진 비율이 ~20 % 미만이면
짚을 만합니다(`저는/제가` 비율은 의도적으로 세지 않습니다 — 국문에서 주어 생략은 정상 문체입니다).
5년차 이상에서 숫자 없는 임팩트 주장이 60 %를 넘으면 문제입니다. 다년 경력에
실패나 어려움 서술이 아예 없는 것 자체가 시그널입니다.

### `portfolio-rewrite`

특정 구절을 받아 Before / After와 "무엇이 바뀌었고 면접관에게 왜 다르게 읽히는지"를 2–4문장으로
냅니다. 리라이팅 전에 실제 약점을 먼저 진단하고 — 숫자 없음, 수동적 오너십, 맥락 없음,
트레이드오프 없음, 결과 없음 — 구체화에 필요한 사실이 없으면 지표를 지어내지 않고 물어봅니다.
입력 언어 그대로 출력합니다.

```
"모니터링 시스템을 구축했습니다" — 이 문장이랑 아래 불릿 3개
시니어 수준으로 다시 써줘.
```

| 원칙 | 약함 | 강함 |
|---|---|---|

### `ppt-keycolor-changer`

원본 XML을 스캔·치환해 PPTX 전체의 키컬러를 바꿉니다 — python-pptx API가 놓치는 테마 토큰,
그라디언트 스톱, 차트 시리즈, 표 셀, 하이퍼링크, `schemeClr` 매핑까지 잡습니다. hex를 이미
알고 있어도 discovery를 항상 먼저 돌립니다. 빈도 스캔이 그 색이 실제로 파일에 있음을 증명하고
놓친 톤 변형을 드러내기 때문입니다. 매핑 표를 확인받기 전에는 아무것도 쓰지 않고, 결과는 새
파일로 나옵니다(덮어쓰기 없음). Python 3.9+ 필요(표준 라이브러리만).

```
presentation.pptx의 오렌지 계열 색을 전부 토스 파란색으로 바꿔줘.
바꾸기 전에 어떤 색이 몇 번 쓰였는지 먼저 보여주고.
```

```bash
# Step 1 — discover: 파일 안 모든 hex의 빈도 표
python /abs/path/to/skills/ppt-keycolor-changer/scripts/ppt_keycolor_changer.py discover \
  --input "deck.pptx"

# Step 5 — replace: 매핑 표를 확인한 뒤에만
python /abs/path/to/skills/ppt-keycolor-changer/scripts/ppt_keycolor_changer.py replace \
  --input   "deck.pptx" \
  --mapping '{"E85E3A":"0064FF","FF8060":"4D96FF","FFB399":"99C2FF"}' \
  --exclude "336699" \
  --suffix  tossblue
```

내장 프리셋(main / light / lighter / muted / dark): `toss-vivid`, `toss-soft`, `apple-blue`,
`material-indigo`, `kakao-yellow`, `naver-green`. 원본 톤과 타깃 톤은 HSL 명도 순위로 짝지어져
시각적 위계가 유지됩니다.

명시적으로 override하지 않는 한 항상 보존: `#000000`, `#FFFFFF`, `#F9F9F9`, `#FEFEFE`,
`#FDFDFD`, RGB max − min ≤ 20인 무채색, 원본 색과 색상(hue)이 60° 이상 떨어진 색. 출력 파일명은
`<원본>_<suffix>.pptx`이고 이미 있으면 `_v2`, `_v3`로 증가합니다. 조용한 덮어쓰기는 없습니다.

숨기지 않고 명시적으로 보고되는 한계:

| 한계 | 내용 |
|---|---|
| 삽입 이미지 | PNG/JPEG/WMF/EMF 픽셀은 XML 치환으로 못 바꿈 |
| 외부 Excel 차트 | 링크된 `.xlsx`에 정의된 시리즈 색은 PPTX 밖 |
| 암호 걸린 PPTX | ZIP을 못 여니 암호를 먼저 해제 |

모든 리포트는 이미지 캐비엇으로 끝납니다: 삽입된 이미지 내부 색상은 여기가 아니라 이미지
편집 도구에서 고쳐야 합니다.
