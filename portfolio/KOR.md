# portfolio — 한국어

[English](README.md) · **한국어**

지원 과정 전체를 다루는 스킬 모음입니다: 공고가 실제로 원하는 걸 읽어내고, 어디서 경쟁력이
있는지 정하고, 실제 경험이 실제 레벨대로 읽히게 문서를 다시 쓰고, 말로 방어할 수 있을 때까지
연습하는 것. 스킬들은 일부러 좁게 나눠져 있고 서로 겹치지 않습니다 — 포트폴리오 채점, 글쓰기
패턴 진단, 문장 리라이팅, JD 매칭은 각각 다른 작업이고, 각 스킬은 자기가 *아닌* 것을 명시합니다.

전부 한국 채용 시장 기준으로 맞춰져 있습니다 — 회사 유형별 프로파일, ATS 규칙, 컬처 시그널이
`references/ats-rules-korea.md`와 `references/korea-company-culture-signals.md`에 있습니다.
분석 결과물은 기본적으로 한국어로 씁니다.

여러 스킬이 가장 판단 비중 큰 지점(갭 심각도 분류, 서류 통과 가능성, 오너십 분류)에서
`think-tool`과 `mcp-reasoner`를 필수 체크포인트로 씁니다. Claude 설정 → MCP Servers에서
remote SSE 엔드포인트로 추가하세요.

## 설치 / 제거

```bash
/plugin install portfolio@newkayak12-claude-skills
/plugin uninstall portfolio@newkayak12-claude-skills
```

## 스킬

### `job-application-workflow`

진입점입니다. 특정 역할 하나에 대해 네 단계: JD 분석 → 회사 리서치 → 이력서·포트폴리오 튜닝 →
면접 준비. 타깃 회사와 공고가 손에 있을 때 씁니다. "커리어 뭘 해야 하지" 같은 열린 질문이나,
이미 면접을 통과해 오퍼 협상 중일 때는 건너뜁니다.

```
쿠팡 백엔드 공고, 다음 주에 지원하려고 해. JD 아래 붙였고
JD 분석부터 면접 준비까지 전체 프로세스 같이 돌려줘.
```

```
[1] portfolio-jd          JD 해독, must-have vs nice-to-have, 핏 갭
      ↓
[2] portfolio-company     컬처 시그널, 대화 소재, 레드 플래그
      ↓
[3] resume-tailorer (+ portfolio-rewrite)   맞춤 이력서, 커버레터 초안
      ↓
[4] interview-prep        STAR 스토리 뱅크, 예상 질문, 역질문
```

각 단계에 skip 조건과 standalone 입력 대체안이 있어서, JD와 회사 이름만으로 Step 4부터 시작할
수도 있습니다. 전체 3–10시간, 단계당 30–90분 정도입니다.

### `portfolio-jd`

JD와 포트폴리오를 *따로* 파싱합니다 — 너무 일찍 비교하면 포트폴리오 프레이밍 쪽으로 판단이
쏠리기 때문입니다. 그다음 다섯 차원으로 핏을 채점합니다: 기술 스택, 경험 스케일, 역할 범위,
도메인, 소프트 시그널. 갭마다 치명적 / 보완 가능 / 마이너 등급과 그 등급인 이유가 붙습니다.
마지막은 서류 통과 가능성에 대한 솔직한 판단과, 그걸 가장 크게 바꿀 요인 하나입니다. 매치든 갭이든
JD와 포트폴리오 양쪽 문장을 함께 인용하고, Skills 목록에만 적힌 기술은 매치가 아니라 갭으로 셉니다.
없는 사실은 채우지 않고 `[확인 필요]`로 남습니다. 끝은 다시 대조할 수 있는 한 줄 — 판정, 5개 차원
점수, 등급별 갭 수, 미충족 must-have. 공고 없이 회사 유형만 볼 거면 `portfolio-company`, 이력서
키워드 작업은 `resume-tailorer`.

```
내 포트폴리오랑 시리즈 C 핀테크 시니어 백엔드 JD 전문이야.
핏 점수 내고, 어떤 갭이 치명적인지, 서류 통과 가능성 솔직하게 말해줘.
```

```
[종합 매칭 점수]  7 / 10
- 기술 스택 8/10   - 경험 스케일 6/10   - 역할 범위 7/10
- 도메인 5/10      - 소프트 시그널 8/10

[갭 분석]
갭: 결제 도메인 경험 없음
심각도: 보완 가능
대응 방법: 커버레터에서 정산 배치 경험을 도메인 인접성으로 프레이밍
```

### `portfolio-company`

특정 공고가 없을 때 씁니다. 이 포트폴리오가 어떤 유형의 엔지니어로 읽히는지 규정한 뒤, 한국
회사 유형별로 핏을 채점합니다 — 대형 플랫폼, 성장기 스타트업, 핀테크/엔터프라이즈, 글로벌 테크,
개발도구/OSS. 각 유형이 *말하는* 요구사항이 아니라 *실제로* 보는 것과 함께 green flag /
red flag를 냅니다. 가장 잘 맞는 Top 2와 고전할 유형을 지목합니다. 회사 인지도만으로 핏을
매기지 않고, 양보 못 할 조건(지역·도메인·스택)을 먼저 묻습니다.

```
백엔드 5년, 중견에서 사내 플랫폼 작업 위주였어. 아직 정한 공고는 없고,
이 포트폴리오가 실제로 어디서 경쟁력 있을지 봐줘.
```

회사 유형마다 핏 점수, 그 점수의 근거가 된 포트폴리오 내용, 구체적 미스매치, 그리고 지원 전
보완할 것 하나가 붙습니다.

### `portfolio-feedback`

이번 주에만 포트폴리오 백 개를 본 면접관처럼 읽습니다 — 있는 것보다 *없는 것*에 패턴 매칭을
겁니다. 리뷰어 페르소나 넷 중 하나를 고르면(대형 플랫폼 Staff / 스타트업 EM / 엔터프라이즈 Tech
Lead / OSS·DevTools Lead) 끝까지 그 시각을 유지합니다. 다섯 차원을 채점하고, 7점 이상은 전부
"회의적인 면접관이라면 뭐라고 깎을까"로 반박을 겁니다. 그 반박을 견딘 점수만 살아남습니다.
문장 리라이팅은 `portfolio-rewrite`, JD 매칭은 `portfolio-jd`.

```
대형 플랫폼 스태프 엔지니어 시각으로 내 포트폴리오 평가해줘.
면접장에서 듣느니 지금 듣는 게 나으니까 세게 봐줘.
```

다섯 차원: Technical Depth · System Design · Impact and Results · Leadership/Ownership ·
Portfolio Narrative. 점수는 *완전히* 충족한 최고 레벨이며, 부분 근거로 올림하지 않습니다.
출력에는 핵심 취약점 하나, 이 페르소나가 반드시 물을 질문 5개, 우선순위 매긴 개선 3개가
포함됩니다. 루브릭과 페르소나: `references/scoring-rubric.md`, `references/personas.md`.

```
[차원별 점수]
Technical Depth: 6 / 10
근거: Kafka 도입은 서술되어 있으나 대안 검토와 트레이드오프가 없음
🧠 Devil's advocate: 규모 수치는 인상적이나 본인 기여 범위가 불명확 — 7 → 6
```

인터뷰어 관점의 심사에 더해, 그 문서가 읽히기는 하는지에 답합니다. 문서 컨벤션 검사
(`references/resume-conventions.md` — 요약 블록, 불릿 예산, XYZ+S 형태, 섹션 순서, 언어별 오너십
규칙)를 나열이 아니라 수치로 집계하고 스크린 비용 상위 5개로 압축하며(`XYZ+S n/m · 의사결정 동사 n%`),
ATS/파서 안전성 검사(표·이미지에 갇힌 증거, 비표준 섹션 헤더, PDF 헤더의 연락처 — 문서는 읽히기
전에 파싱됩니다), `[AI 스크리너 요약]` — 스크리닝 모델이 실제로 생성할 3줄 요약과 거기서 살아남지
못한 최강 증거, 그리고 스크리닝 연구에 근거한(`references/screen-models.md`) 2-리더
`[서류 스크린 판정]` — 리크루터 6초 패스(Ladders 아이트래킹의 F-패턴 가시 영역만으로 판정)와
엔지니어 30초 스킴(오탈자·기술명 오기 체크, Lerner의 보정 데이터)을 각각 통과/경계/탈락으로 —
및 `[레드 플래그]` 블록(경력 갭, 잦은 이직, 직함 인플레이션, 검증 불가 주장 비율 등, 플래그마다
면접 방어 답변 한 줄)이 있습니다. 스크리너는 떨어뜨릴 이유를 찾으므로 플래그는 강점과 상계하지
않습니다.

이 스크린 레이어는 `-beta` 레인에서 개발한 뒤 두 번의 헤드투헤드 벤치마크(실제 40페이지 포트폴리오,
impressive-surface 픽스처)를 거쳐 합류했습니다. 양쪽 모두 차원 점수와 핵심 취약점 판정이 일치했고,
동시에 스크린 패스는 실질 리뷰가 구조적으로 낼 수 없는 발견을 순증했습니다 — 설명 없는 8개월 공백,
두 문서에서 서로 다른 지표에 붙은 같은 수치, 연락처가 아예 없는 이력서.

이전 버전을 같이 주면 **리비전 모드**(`references/revision-diff.md`)로 전환합니다. Before/After
집계표와 스크린 판정이 움직였는지로 시작하고, 후퇴는 별도 줄로 — 리라이팅이 *새로 만든* 주장(불릿은
여전히 개발인데 요약만 설계가 된 경우)까지 포함 — 쓰며, 기간이 붙은 주장("12개월 무사고")은 오늘
날짜와 대조합니다. v1/v2 헤드투헤드에서 구조화된 비교가 즉석 비교가 놓친 후퇴 두 건을 잡아 베타에서
승격했습니다. 집계 분모는 같은 파일에 고정해 두 버전을 항상 같은 방식으로 셉니다.

여기에 문서가 스스로와 맞는지를 묻는 세 패스(`references/claim-and-consistency.md`)가 더 붙습니다.
**정합성 교차 검사** — 섹션 간 날짜와 요약의 경력 연수, Skills 항목 하나하나를 그것을 증명하는
불릿과 대조(`스킬 근거율 n/m`, 근거 없는 항목은 이름을 지목), 직함 주장과 불릿 동사의 불일치.
**주장 감사** — 성과 불릿마다 수치·베이스라인·기간·기여 범위가 있는지(`완전 주장 n/m`), 최악의 세
개를 그것이 부르는 면접 질문 그대로와 함께 지목(이 집계는 Impact 점수의 천장이지 점수 자체가 아님).
**레벨 캘리브레이션** — 문서가 주장하는 레벨(연차·직함·지원 포지션)과 4단 근거 사다리(주니어 / 미드
/ 시니어 / 리드)에서 실제로 읽히는 레벨을 대조, `레벨 갭 ±n`과 천장을 정한 불릿 두 개. 과대 주장은
숫자가 붙은 직함 인플레이션 플래그, 과소 주장은 개선 우선순위 #1.

```
7년차 시니어라고 썼는데 이 문서가 진짜 시니어로 읽히는지 봐줘
```

```
레벨 갭: 주장 시니어 / 읽힘 미드 (−1) — 천장: "주문 조회 API 1.2s → 380ms", "중복 차감 주 12건 → 0건"
XYZ+S 0/8 · 완전 주장 2/3 · 스킬 근거율 5/6 · 날짜 불일치 0 · 레벨 갭 −1 · 의사결정 동사 0% · 불릿/롤 max 5
```

모든 리뷰는 이 집계 한 줄로 끝나고, 지원자는 자기 문서와 대조해 직접 다시 셀 수 있습니다 — 세기
전에 목록을 쓰고, 분모를 고정하고, 발견은 한 번만 말하고, 임계값은 잠정치로 표기합니다(§D, §F).
이 패스들은 세 번의 벤치마크 끝에 `-beta` 레인에서 승격했습니다. 앞의 두 번은 발견 항목은 동등하고
`레벨 갭` 하나가 추가됐지만 집계에 오류가 있었고, 카운팅 규칙을 고정한 뒤의 세 번째는 두 픽스처
모든 집계가 손으로 계산한 정답과 일치했습니다.

36장짜리 덱으로 실제 세션을 돌려보니 그 근거를 앞에 두는 대가가 드러났습니다. 판정이 아홉 번째
블록으로 밀렸고, 이력서용 분모(`XYZ+S 9/60`, `불릿/롤 21`, 6초 F-패턴 판정)가 슬라이드에 그대로
적용됐고, 기준 ~60%에 58%가 레드 플래그를 찍었고, 같은 발견이 네 번 나왔습니다. 1.14.0부터 리뷰는
**판정이 먼저**입니다: 총평(세 문장, 리크루터·엔지니어 판정 포함) → 차원별 점수 → 핵심 취약점 →
개선 우선순위, 그 다음 **부록**. 부록의 모든 발견은 ID(`R1` `C2` `A3` `L1` `F1`)를 달고, 본문은
다시 쓰는 대신 ID로 가리킵니다. 형식은 처음에 판별합니다(`claim-and-consistency.md` §0): 덱이면
XYZ+S 분모는 성과 주장 불릿만, `불릿/롤`은 `—`, 리크루터 패스는 첫 3장을 읽습니다. 경계값은
`경계 (58%, 기준 ~60%)`로 표기하고 그것만으로 플래그를 찍지 않습니다. 같은 세션에서 리뷰 *이후*의
태도에 대한 규칙 세 가지도 나왔습니다: 사실이 없으면 `[확인 필요: ○○]`로 비워두고 역산이나
그럴듯한 숫자를 절대 쓰지 않는다, 지원자가 확정한 결정은 `[확정]` 목록에 올리고 다시 꺼내지
않는다, 지원자가 직접 쓴 문장은 오타·용어 오용·문서 간 모순 세 가지만 보고 리뷰 자세를 작성에
끌고 가지 않는다.

### `portfolio-pattern`

내용이 아니라 **읽히는 방식**을 봅니다. 여섯 차원을 감사합니다: 의사결정 동사 비율(제안/채택/배제
vs 맨 개발했습니다), 행위 주체 표현, 숫자 밀도, 실패 서사 유무, 의사결정 가시성, 동사 에너지. "오너십이 안
보인다"는 피드백은 받았는데 어디가 문제인지 아무도 못 짚어줄 때 씁니다. 지적된 문장을 고치는 건
`portfolio-rewrite`, 전체 채점은 `portfolio-feedback`.

```
포트폴리오에 오너십이 안 드러난다는 말을 계속 들어. 글쓰기 패턴 분석해서
그런 인상을 주는 실제 문장들을 짚어줘.
```

적용하는 기준선: 시니어 포트폴리오에서 행위 문장 중 의사결정 동사를 가진 비율이 ~20 % 미만이면
짚을 만합니다(`저는/제가` 비율은 의도적으로 세지 않습니다 — 국문에서 주어 생략은 정상 문체입니다).
5년차 이상에서 숫자 없는 임팩트 주장이 60 %를 넘으면 문제입니다. 다년 경력에
실패나 어려움 서술이 아예 없는 것 자체가 시그널입니다.

### `deck-builder`

발표자료를 문서가 아니라 빌드로 다룹니다. `template.pptx`는 툴체인 — 그 슬라이드들이 아키타입
카탈로그입니다. `deck.mdx`는 소스 — 사람이 고치는 유일한 파일입니다. 출력 pptx는 빌드 산출물로
매번 통째로 다시 만들어집니다. 출력 슬라이드는 전부 템플릿 슬라이드의 복제본이고 내용만
갈아끼우기 때문에, 템플릿 디자인이 바이트 단위로 보존되고 레이아웃을 새로 짜는 일이 없습니다.
그림도 소스가 될 수 있습니다. 이미지 슬롯은 `.svg`를 받고, 빌드 때 프레임 크기에 맞춰 PNG로
래스터화한 뒤 내용 해시로 `.deckcache/`에 캐시합니다. pptx 안에는 래스터 이미지만 들어갑니다 —
SVG는 PowerPoint·Keynote·Google Slides·PDF 내보내기에서 똑같이 보이지 않고 구형 PowerPoint는
아예 아무것도 안 그리기 때문에, 벡터는 소스 트리에 남고 빌드가 "벡터가 패키지에 들어가지 않았다"를
단언합니다. 덱의 모든 것이 모델이 쓸 수 있는 텍스트인데
다이어그램 하나만 사람이 그려야 하던 구멍이 이걸로 닫힙니다. 이미지에는 맞춤 모드가 붙습니다 — `| fit`은 프레임을 이미지 모양으로 줄여 전부 보존하고, 기본값
`| fill`은 프레임에 맞춰 자르고, `| fill top`은 무엇을 남길지 고릅니다. `| transparent`는 PNG 배경을 가장자리에서 안쪽으로 flood fill 해 제거합니다 — 도형 안쪽의 흰색은
살아남고 바깥에 닿은 배경만 없어지므로, 스크린샷이 어두운 슬라이드에서 "붙여넣은 상자"로 보이지
않습니다. 기준은 깔끔함이 아니라 가시성입니다: 투명 처리 후 남는 내용이 슬라이드 배경과 비슷해지면
보이지 않는 이미지를 돌려주는 대신 그렇다고 말합니다. `check`는 크롭이 얼마나
버리는지, 프레임 대비 실효 해상도가 얼마인지, 생성된 그림이 템플릿 팔레트를 벗어났는지, 이미지
테두리가 그 슬라이드 배경에서 "붙여넣은 상자"로 보일지를 보고합니다. 이미지가 자기 절반을 잃는 것은
표 행이 슬라이드 밖으로 떨어지는 것과 같은 결함으로 다룹니다 — 엔진은 내용을 조용히 잃지 않습니다.

템플릿이 이미지 위에 글자를 얹는 경우 — 전면 배경 위의 제목 같은 — 이미지도 글자도 각각은
틀리지 않았는데 슬라이드는 안 읽힙니다. 그래서 `check`는 각 텍스트 박스 뒤에 실제로 깔리는
픽셀을 디코딩해서(크롭, fit 모드, 투명 처리까지 따라가서) 그 글자 자신의 색과 대비를 잽니다 —
큰 글자는 WCAG 3:1, 본문은 4.5:1. 면적의 5분의 1 이상이 기준 아래면 글자 뒤 평균색과 함께
보고합니다. 이미지가 자기가 덮는 텍스트보다 *나중에* 그려지면 경고가 아니라 에러입니다 —
글자가 이미지 뒤로 들어가니까요. 렌더 테스트가 이 예측을 실제 페이지와 대조합니다: 옅은 하늘
배경에서 `check`가 제목 뒤를 `#D2E1F8`이라고 말하고, pdftoppm이 그 자리에 칠하는 색도 같습니다.

넘치는 쪽도 같은 방식으로 잽니다. 템플릿 자신보다 줄 수가 늘어나면 설계 위치보다 얼마나 아래로
내려가는지, 무엇에 닿는지를 말합니다 — 다른 도형에 닿으면 에러입니다. 다만 추정 오차를 넘는
것만 보고합니다. em 모델로 줄바꿈을 예측하는 건 대략 한 줄만큼의 오차가 있고 실제 프레임의 여유는
그보다 좁은 경우가 많아서, 그 미세한 여백은 `render`의 몫입니다. 프레임이 아니라 템플릿을
기준으로 바꾸자 디자이너 자신의 슬라이드에 대한 오탐률이 46%에서 0이 됐습니다.

덜 채우는 것도 결함입니다. 4문단을 담도록 그린 프레임에 1문단을 넣으면 나머지가 있었어야 할
자리에 구멍이 생기는데, 아무도 그 말을 안 했습니다 — `check`는 넘칠 때만 보고 있었습니다. 이제
템플릿 자기 분량의 절반 아래로 떨어지면 몇 퍼센트인지 함께 보고합니다. 프레임은 움직이지 않고,
그 틈은 쓰는 사람이 메워야 하기 때문입니다.

용량은 글자 수가 아니라 em으로 잽니다. 글자 수로 세면 한글 한 줄이 실제보다 1.8배 짧아 보여서
넘치는 제목이 그냥 통과합니다. 기준선은 템플릿 자신입니다 — 대부분의 슬롯은 원래 여러 줄로
감기도록 만들어져서 절대 폭으로 경고하면 전부 노이즈가 됩니다. 그래서 `check`가 말하는 건
"템플릿이 한 줄로 유지하는 슬롯인데 두 줄로 밀린다" 또는 "템플릿 원문보다 훨씬 길다" 둘뿐입니다.
그리고 `render`는 미리보기를 보여주기 전에 렌더러에 없는 서체를 먼저 알려줍니다. 대체 폰트는
모든 줄을 다시 감아서, 미리보기가 덱이 아니라 대체 폰트에 대한 이야기가 되기 때문입니다.

`catalog`는 템플릿의 팔레트와 타입을
출력합니다 — 테마 슬롯, 슬라이드가 실제로 쓰는 색, 테마 폰트, 사용 중인 pt 크기, 그리고 각
이미지 프레임의 정확한 pt 치수까지. 그 pt 치수로 SVG를 그리면 `font-size="16"`이 옆 본문의
16pt와 같은 숫자가 됩니다. 그래서 생성된 그림이 비슷해 보이는 색이 아니라
레퍼런스의 색으로 그려집니다. 레퍼런스가 디자인을 주고, 생성된 소스는 내용만 줍니다. SVG 에셋은
*빌드* 시점에 렌더러가 필요한 유일한 경우이고, PNG·JPEG는 아무것도 필요 없습니다.

레퍼런스 템플릿은 필수입니다 — 내장 디자인도 폴백도 없어서, `.pptx`가 없으면 슬라이드를 지어내는
대신 에러로 끝냅니다. 소스 파일은 `deck.md`가 아니라 `deck.mdx`입니다. 읽는 문서가 아니라
컴파일되는 소스이고, 다른 확장자는 거부됩니다.
Python 3.9+ 필요(표준 라이브러리만 — python-pptx도 PyYAML도 안 씁니다).

```
이 템플릿 읽고 분기 리뷰 내용으로 PPT 만들어줘.
슬라이드별로 어떤 아키타입 쓸지 먼저 보여주고.
```

```bash
# 1 — catalog: 아키타입, 슬롯, 템플릿이 지금 보여주는 내용
python3 /abs/path/to/skills/deck-builder/scripts/deck.py catalog \
  --template "template.pptx" --output "deck.catalog.md"

# 2 — check: 없는 슬롯, 없는 이미지, 프레임을 넘칠 텍스트
python3 /abs/path/to/skills/deck-builder/scripts/deck.py check --deck deck.mdx

# 3 — build: 같은 deck.mdx는 항상 바이트까지 같은 pptx를 냅니다
python3 /abs/path/to/skills/deck-builder/scripts/deck.py build --deck deck.mdx

# 4 — render: 빌드하고 LibreOffice로 렌더해서 실제 지면을 검사합니다
python3 /abs/path/to/skills/deck-builder/scripts/deck.py render --deck deck.mdx
```

발표자료는 사람이 읽는 물건이라 `render`가 실질적인 마지막 단계입니다. PDF와 페이지 PNG
미리보기를 내놓고, 렌더된 지면에서 텍스트 프레임끼리 겹치는 곳, 한 프레임 안에서 행간이
자기 기준보다 좁아진 곳, 슬라이드 끝에서 잘려나간 텍스트를 찾아냅니다. 원시 박스를 교차시키는
대신 프레임 사이를 비교하는데, CJK 폰트의 em 박스가 행간 100%보다 커서 글자가 닿지 않아도
지면상으로는 항상 겹치기 때문입니다. `soffice`가 PATH에 있거나 `DECK_RENDER_DOCKER=<이미지>`가
필요하고, 없으면 검사한 척하지 않고 거부합니다.

`deck.mdx`는 그 밖에 슬라이드별 발표자 노트 `notes:`, 인라인 강조 `**굵게**` / `*기울임*` /
`` `코드` ``(템플릿 run을 복사해 속성만 뒤집으므로 타입은 그대로), 그리고 `catalog`이 주는
`template_hash`를 받습니다. 마지막 것이 이 설계가 원래 안고 있던 실패를 막습니다 — 템플릿에
슬라이드를 끼워 넣거나 순서를 바꾸면 `@s3`이 다른 슬라이드를 가리키기 시작하는데, 핀이 없으면
에러가 아니라 "뭔가 이상한 덱"으로만 드러납니다. 템플릿의 문구만 고치는 건 해시를 움직이지
않습니다. 구조만 움직입니다.

`deck.mdx`는 자체 파싱되는 최소 문법의 마크다운입니다 — `## @s3`은 템플릿 3번 슬라이드로 슬라이드를
시작하고, `key: value`는 텍스트 슬롯, 들여쓴 `- ` 줄은 리스트, 들여쓴 `| a | b |` 줄은 표 행,
경로는 이미지, `!drop`은 도형 삭제, 빠뜨린 슬롯은 템플릿 내용을 그대로 둡니다. 리스트와 표 행은
자유롭게 늘고 줄어듭니다 — 불릿 3개짜리 아키타입에 4개를 넣으면 서식을 지닌 문단을 복제합니다.
교체된 이미지는 늘어나지 않고 프레임 종횡비에 맞춰 가운데 크롭됩니다.

숨기지 않고 명시하는 한계:

| 한계 | 내용 |
|---|---|
| **템플릿 필수** | 레퍼런스 `.pptx`가 없으면 엔진은 에러로 끝내고 아무것도 만들지 않습니다. |
| **새 레이아웃 없음** | 출력 슬라이드는 템플릿 슬라이드의 복제본입니다. 맞는 아키타입이 없는 내용은 먼저 PowerPoint에서 템플릿을 늘려야 합니다. |
| **차트는 쓰기 불가** | 시리즈 값이 내장 xlsx와 캐시 XML에 나뉘어 있습니다. `catalog`은 차트 슬롯을 보여주고, `build`는 템플릿 값 그대로 둡니다. |
| **SVG 에셋은 빌드 때 렌더러 필요** | PNG·JPEG는 불필요. `.svg`만 래스터화가 필요합니다. |
| **레이아웃의 진실은 렌더러에만 있음** | `check`는 프레임 너비 ÷ 폰트 크기로 추정합니다. 실제 겹침은 `render`만 보고, 그건 LibreOffice가 필요합니다. |
| **용량은 추정치** | 오버플로 경고는 실제 텍스트 메트릭이 아니라 프레임 너비 ÷ 폰트 크기에서 나옵니다 — 판정이 아니라 확인하라는 신호입니다. |
| **서식은 템플릿을 따름** | 교체된 run은 템플릿 run의 폰트·크기·색을 물려받습니다. 단어 단위 강조는 `deck.mdx`로 표현할 수 없습니다. |
| **중첩은 템플릿이 들여쓸 때만 보임** | 중첩 항목은 아웃라인 레벨 1로 쓰입니다. 템플릿이 레벨 1 들여쓰기를 정의하지 않았다면 나머지와 같은 줄에서 시작합니다. |
| **발표자 노트 삭제** | 노트 슬라이드는 빌드에 실리지 않습니다. |

테스트 스위트는 둘이고, 둘 다 리포에 픽스처 파일을 두지 않습니다:

```bash
# 단위 — 패키지 구조, 파싱, 슬롯 쓰기. 최소 pptx를 스스로 만듭니다.
python3 portfolio/skills/deck-builder/scripts/test_deck.py

# 렌더 왕복 — mdx -> pptx -> PDF를 셋 다 대조. 렌더러가 필요합니다:
# PATH의 soffice, 또는 DECK_RENDER_DOCKER=<soffice가 든 이미지>. 없으면 깔끔히 skip합니다.
python3 portfolio/skills/deck-builder/scripts/test_render.py
```

렌더 스위트는 5개 아키타입짜리 디자인된 템플릿을 직접 작성하고(`fixture_template.py`), 거기서
한국어 6슬라이드 덱을 빌드하고, PDF로 뽑은 다음, `.mdx`의 모든 값이 pptx와 PDF 양쪽에 도달했는지,
템플릿 자리표시 문구가 새어나오지 않았는지, 브랜드 색과 장식 도형이 살아남았는지, 프레임보다 넓은
이미지가 늘어나지 않고 크롭됐는지를 확인합니다. `fixture_template.py`는 테스트 픽스처일 뿐 폴백이
아닙니다 — 엔진에는 내장 템플릿이 없고, 앞으로도 생기면 안 됩니다.

### `ppt-keycolor-changer`

원본 XML을 스캔·치환해 PPTX 전체의 키컬러를 바꿉니다 — python-pptx API가 놓치는 테마 토큰,
그라디언트 스톱, 차트 시리즈, 표 셀, 하이퍼링크, `schemeClr` 매핑까지 잡습니다. hex를 이미
알고 있어도 discovery를 항상 먼저 돌립니다. 빈도 스캔이 그 색이 실제로 파일에 있음을 증명하고
놓친 톤 변형을 드러내기 때문입니다. 매핑 표를 확인받기 전에는 아무것도 쓰지 않고, 결과는 새
파일로 나옵니다(덮어쓰기 없음). Python 3.9+ 필요(표준 라이브러리만).

```
presentation.pptx의 오렌지 계열 색을 전부 토스 파란색으로 바꿔줘.
바꾸기 전에 어떤 색이 몇 번 쓰였는지 먼저 보여주고.
```

```bash
# Step 1 — discover: 파일 안 모든 hex의 빈도 표
python /abs/path/to/skills/ppt-keycolor-changer/scripts/ppt_keycolor_changer.py discover \
  --input "deck.pptx"

# Step 5 — replace: 매핑 표를 확인한 뒤에만
python /abs/path/to/skills/ppt-keycolor-changer/scripts/ppt_keycolor_changer.py replace \
  --input   "deck.pptx" \
  --mapping '{"E85E3A":"0064FF","FF8060":"4D96FF","FFB399":"99C2FF"}' \
  --exclude "336699" \
  --suffix  tossblue
```

내장 프리셋(main / light / lighter / muted / dark): `toss-vivid`, `toss-soft`, `apple-blue`,
`material-indigo`, `kakao-yellow`, `naver-green`. 원본 톤과 타깃 톤은 HSL 명도 순위로 짝지어져
시각적 위계가 유지됩니다.

명시적으로 override하지 않는 한 항상 보존: `#000000`, `#FFFFFF`, `#F9F9F9`, `#FEFEFE`,
`#FDFDFD`, RGB max − min ≤ 20인 무채색, 원본 색과 색상(hue)이 60° 이상 떨어진 색. 출력 파일명은
`<원본>_<suffix>.pptx`이고 이미 있으면 `_v2`, `_v3`로 증가합니다. 조용한 덮어쓰기는 없습니다.

숨기지 않고 명시적으로 보고되는 한계:

| 한계 | 내용 |
|---|---|
| 삽입 이미지 | PNG/JPEG/WMF/EMF 픽셀은 XML 치환으로 못 바꿈 |
| 외부 Excel 차트 | 링크된 `.xlsx`에 정의된 시리즈 색은 PPTX 밖 |
| 암호 걸린 PPTX | ZIP을 못 여니 암호를 먼저 해제 |

모든 리포트는 이미지 캐비엇으로 끝납니다: 삽입된 이미지 내부 색상은 여기가 아니라 이미지
편집 도구에서 고쳐야 합니다.
