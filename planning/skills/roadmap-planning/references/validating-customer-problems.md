# Validating Customer Problems (Phase 1)

Phase 1 asks for "3-5 validated customer problems" — validated means a real pattern across
customers, not one loud voice. Use this check on raw interview notes, support tickets, NPS
verbatims, or churn survey text before a problem earns a place in Phase 1's output.

## Minimum Viable Dataset

Below these, treat every finding as an anecdote, not a customer problem:

- 5+ interviews or support threads for a single user segment
- 20+ survey responses for a quantitative theme claim
- 3+ independent sessions before calling something a UX pattern

## Pattern vs. Anecdote

| Signal | Threshold | Treatment |
|---|---|---|
| Strong pattern | n ≥ 5 AND ≥ 30% of the sample | Validated — include in Phase 1 output |
| Weak pattern | n = 3-4 OR 15-29% of the sample | Include, flagged "needs replication" |
| Anecdote | n = 1-2 OR < 15% of the sample | Do not generalize; log separately |
| Outlier | Contradicts the dominant pattern | Note explicitly — may reveal a distinct segment |

A vivid quote from a single customer will dominate a room unless the n= count sits next to it.
Always state the count.

## One-Line Validated Problem Format

Carry each validated problem into Phase 1 as:

```
[Problem in customer language] — n=X/Y, source: [interviews/tickets/survey]
```

Example: "Can't tell if an approval went through without checking email" — n=7/10 interviews,
support tickets.

## If No Recent Research Exists

Pull straight from the raw sources listed in Phase 1 (support tickets, NPS open-ends, churn
survey text) and apply the same thresholds — a validated problem does not require a formal
discovery process to precede it, only evidence that clears the bar above.
