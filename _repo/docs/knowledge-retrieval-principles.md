# knowledge 검색의 원리 — BM25, 코사인 유사도, RRF, 청킹

`knowledge` 플러그인의 검색(`knowledge/scripts/sqlite-knowledge.mjs`의 `searchIndex`)이 어떻게 순위를
매기는지, 각 부품의 원리를 작은 숫자 예시로 따라가며 정리한 학습용 문서입니다. 출처와 논문 목록, 이론과
다르게 간 이유의 측정 근거는 [`knowledge/docs/theory.md`](../../knowledge/docs/theory.md)에 있고, 여기서는
"왜 이 식이 이렇게 동작하는가"만 다룹니다.

작성 2026-11-16, knowledge 1.21.4 기준. 코드 위치는 `sqlite-knowledge.mjs`의 함수 이름으로 적습니다.

---

## 0. 전체 그림

질문 하나가 들어오면 세 갈래로 순위를 따로 낸 뒤 합칩니다.

```
질문
 ├─ 어휘 검색 (단어가 겹치는가)
 │   ├─ FTS5 unicode61 (정확한 단어)  ─┐ 컬럼별(title/terms/body) BM25 순위 → RRF
 │   └─ FTS5 trigram (3글자 조각)     ─┘ 컬럼별 BM25 순위 → RRF
 │          └─ 두 목록을 0.7 / 0.3 가중 RRF → 어휘 순위 하나
 ├─ 의미 검색 (뜻이 가까운가)
 │   └─ 질문 벡터와 문서 벡터의 코사인 유사도 → 의미 순위
 └─ relation 승격 (선언된 비교 노트)
          └─ 세 순위를 가중 RRF로 합침 → 노트당 1건으로 묶음 → (선택) 리랭커 → 상위 k
```

핵심 아이디어는 하나입니다. **점수는 서로 단위가 달라서 더할 수 없으니, 순위만 가져와 합친다(RRF).**
BM25 점수 4.6과 코사인 0.82는 비교할 수 없지만 "1등"과 "3등"은 비교할 수 있습니다.

## 1. 토큰화 — 글을 셀 수 있는 조각으로

검색은 결국 "조각이 겹치는가"를 셉니다. 무엇을 조각으로 볼지가 첫 결정입니다.

### 1.1 세 가지 토크나이저

| 어디 | 방식 | "재시도한 작업" → |
|---|---|---|
| FTS5 `unicode61` 색인 | 공백·구두점으로 끊은 단어 | `재시도한`, `작업` |
| FTS5 `trigram` 색인 | 3글자씩 미끄러지는 창 | `재시도`, `시도한`, `도한 `, `한 작`, ` 작업` |
| `tokenize()` (hash 임베딩용) | `Intl.Segmenter` 단어 + `~`붙은 3글자 조각 | `재시도한`, `작업`, `~재시도`, `~시도한`, … |

### 1.2 왜 trigram이 필요한가 — 한국어 조사와 활용

정확한 단어 색인은 `재시도한`과 `재시도`를 다른 단어로 봅니다. 질문이 "재시도"이면 "재시도한"이 적힌 문서를
못 찾습니다. trigram 색인은 `재시도`라는 3글자 조각이 두 쪽 모두에 있으니 찾습니다. 형태소 분석기 없이
부분 문자열 매칭을 얻는 방법입니다.

한계: trigram은 3글자보다 짧은 질의어를 못 찾습니다. 한국어의 흔한 명사(재고, 출고, 결제)는 2글자입니다. 그래서
질의 쪽에서 두 가지를 더 합니다(`ftsTokens`, `koreanForms`).

- 한글 질의어는 **접두어 검색**: `재고*` → `재고가`, `재고를`도 맞음.
- 끝의 조사를 떼어 **어간을 하나 더** 넣음: `재고를` → `재고를*`, `재고*`. 원래 단어는 남겨 둡니다
  (`재시도`의 `도`를 조사로 오인해 떼어도, 떼지 않은 쪽이 정답을 계속 올려 주도록).

## 2. BM25 — "이 단어가 이 문서에 얼마나 중요한가"

### 2.1 직관 세 가지

1. **많이 나올수록 관련 있다** — 하지만 10번 나온 문서가 1번 나온 문서보다 10배 관련 있지는 않다(포화).
2. **흔한 단어는 증거가 약하다** — 모든 문서에 있는 "시스템"보다 5개 문서에만 있는 "수불부"가 강한 증거(IDF).
3. **긴 문서는 우연히 단어를 품기 쉽다** — 같은 횟수라면 짧은 문서 쪽을 더 쳐준다(길이 정규화).

### 2.2 식

질의어 t 하나에 대해, 문서 d의 점수는

```
score(t, d) = IDF(t) × tf × (k1 + 1) / ( tf + k1 × (1 − b + b × |d| / avgdl) )

IDF(t) = ln( (N − n + 0.5) / (n + 0.5) )
```

| 기호 | 뜻 | SQLite FTS5 값 |
|---|---|---|
| tf | 문서 d에 t가 나온 횟수 | — |
| N, n | 전체 문서 수, t가 있는 문서 수 | — |
| \|d\|, avgdl | 문서 길이, 평균 문서 길이(토큰 수) | — |
| k1 | 포화 속도. 클수록 tf를 더 오래 믿음 | 1.2 |
| b | 길이 정규화 강도. 0이면 길이 무시, 1이면 완전 정규화 | 0.75 |

질의어가 여럿이면 각 질의어 점수를 더합니다. FTS5의 `bm25()`는 "작을수록 좋음"이 되도록 음수로 돌려주므로
코드는 `ORDER BY bm25(...)` 오름차순입니다.

### 2.3 숫자로 따라가기

문서 100개(N=100) 중 5개(n=5)에만 "수불부"가 있습니다.

```
IDF = ln( (100 − 5 + 0.5) / (5 + 0.5) ) = ln(17.36) ≈ 2.85
```

"수불부"가 2번 나온(tf=2) 두 문서, 평균 길이는 100 토큰:

| 문서 | 길이 | 분모 = tf + 1.2 × (0.25 + 0.75 × \|d\|/100) | tf 부분 = 2 × 2.2 / 분모 | 점수 |
|---|---|---|---|---|
| A | 50 | 2 + 1.2 × 0.625 = 2.75 | 1.60 | **4.57** |
| B | 200 | 2 + 1.2 × 1.75 = 4.10 | 1.07 | 3.06 |

같은 횟수인데 짧은 A가 이깁니다(직관 3). tf를 2에서 20으로 늘려도 A의 tf 부분은 2.2를 넘지 못합니다
(k1 + 1 = 2.2가 상한, 직관 1).

### 2.4 이 플러그인이 BM25를 쓰는 방식 — 컬럼별로 따로

색인은 `title`(제목), `terms`(별칭·태그·요약 등 큐레이션 어휘), `body`(본문) 세 컬럼입니다. 제목에 맞은 것이
본문에 한 번 지나가며 언급된 것보다 강한 증거입니다.

자연스러운 방법은 `bm25()`에 컬럼 가중치를 주는 것인데, 쓰지 않습니다. BM25의 길이 정규화는 **모든 컬럼을
합친 문서 길이**로 하므로, 제목이 맞은 긴 노트가 본문에서 한 번 언급한 짧은 노트에게 집니다(2.3의 A/B 효과).
대신 컬럼마다 BM25 순위를 **따로** 내고 RRF로 합칩니다(`ftsRanks`, `COLUMN_RRF_WEIGHTS = title 0.5,
terms 0.35, body 0.15`). 순위에는 길이가 섞이지 않습니다. 예시는 4.3에 있습니다.

## 3. 코사인 유사도 — "뜻이 얼마나 가까운가"

### 3.1 임베딩

임베딩 모델은 글 하나를 고정 길이 숫자 배열(벡터)로 바꿉니다. 학습 결과, 뜻이 비슷한 글은 비슷한 방향을
가리킵니다. "주문이 안 들어와요"와 "발주 누락"은 겹치는 단어가 없어도 벡터 방향이 가깝습니다. 어휘 검색이
못 하는 **바꿔 말한 질문**을 잡는 수단입니다.

### 3.2 식

```
cos(q, d) = (q · d) / (‖q‖ × ‖d‖) = Σ qᵢdᵢ / ( √Σqᵢ² × √Σdᵢ² )
```

두 벡터 사이 각도의 코사인입니다. 같은 방향 1, 직각 0, 반대 −1. **길이는 무시하고 방향만** 봅니다.
문서가 길어 벡터 성분이 커져도 방향이 같으면 점수가 같습니다.

### 3.3 숫자로 따라가기 (3차원)

```
q = (1, 2, 0)    d1 = (2, 4, 1)    d2 = (0, 1, 3)

q·d1 = 2 + 8 + 0 = 10    ‖q‖ = √5 ≈ 2.24   ‖d1‖ = √21 ≈ 4.58   cos = 10 / 10.25 ≈ 0.98
q·d2 = 0 + 2 + 0 = 2                      ‖d2‖ = √10 ≈ 3.16   cos = 2 / 7.07  ≈ 0.28
```

d1이 훨씬 가깝습니다. 실제 벡터는 수백 차원(embeddinggemma 768, hash 384)이지만 계산은 같습니다.

코드(`cosine`, `normalizeVector`)는 벡터를 저장할 때 미리 길이 1로 정규화합니다. 그러면 ‖q‖ = ‖d‖ = 1이라
코사인이 내적과 같아집니다. 검색은 모든 문서 벡터와 내적을 구해 정렬하는 전수 비교입니다(근사 최근접 색인
없음 — 노트 수천 개 규모에서는 충분히 빠릅니다).

### 3.4 비대칭 프롬프트

질문("X가 뭐야?")과 문서(설명문)는 생김새가 다릅니다. EmbeddingGemma는 질문 앞에 `task: search result |
query: `, 문서 앞에 `title: … | text: `를 붙이도록 학습되었습니다(`EMBEDDING_PROMPTS`). 이걸 빼면 질문을
문서처럼 인코딩해서 방향이 어긋납니다. 인덱스에 `embedding_prompt`를 기록해 두고, 문서가 붙인 방식대로만
질문에 붙입니다.

### 3.5 `hash` provider — 의미가 아닌 가짜 임베딩

모델 없이도 돌도록 기본값은 `hash`입니다(`hashEmbedding`). 토큰마다 SHA-256으로 384칸 중 한 칸을 골라 ±1을
더합니다(feature hashing). 단어가 겹치면 같은 칸이 올라가니 코사인이 올라가지만, **뜻은 전혀 모릅니다** —
결국 또 하나의 어휘 검색입니다. 그래서 hash일 때는 의미 가중을 0으로 둡니다(5장). 측정상 hash → embeddinggemma
전환이 recall@10 0.631 → 0.803으로, 엔진 개선 여섯 버전을 합친 것보다 컸습니다.

## 4. RRF — 단위가 다른 순위를 합치는 법

### 4.1 식

```
RRF(d) = Σ  w_s / ( k + rank_s(d) )      (k = 60, rank는 1부터)
        목록 s
```

어떤 목록에 없는 문서는 그 항이 0입니다. 원 논문(Cormack 2009)은 가중치 w 없이 k = 60을 썼고, 이 플러그인은
가중치를 붙인 형태를 씁니다(`RRF_K = 60`).

### 4.2 k = 60이 하는 일

```
1위: 1/61 = 0.01639     2위: 1/62 = 0.01613     10위: 1/70 = 0.01429     50위: 1/110 = 0.00909
```

1위와 2위 차이가 아주 작습니다. k가 크면 **한 목록에서의 압도적 1위보다, 여러 목록에서 고르게 상위인 것**이
이깁니다. 한 신호가 틀려도 다른 신호들이 보정합니다. k가 0에 가까우면 1위(1/1)와 2위(1/2) 차이가 커져 한
목록의 1위가 결과를 독점합니다.

### 4.3 숫자로 따라가기 — 컬럼 융합

| 문서 | title 순위 | terms 순위 | body 순위 | RRF |
|---|---|---|---|---|
| A (긴 노트, 제목이 맞음) | 1 | — | — | 0.5/61 = **0.00820** |
| B (짧은 노트, 본문·태그에 언급) | — | 5 | 1 | 0.35/65 + 0.15/61 = 0.00538 + 0.00246 = 0.00784 |

A가 이깁니다. BM25 점수를 그대로 더했다면 짧은 B의 높은 점수가 이겼을 수 있습니다(2.4).

### 4.4 이 플러그인에서 RRF가 쓰이는 네 곳

| 단계 | 합치는 것 | 가중치 | 함수 |
|---|---|---|---|
| 1 | 한 FTS 색인의 title / terms / body 순위 | 0.5 / 0.35 / 0.15 | `ftsRanks` |
| 2 | 정확 단어 색인 / trigram 색인 | 0.7 / 0.3 | `fuseLexicalRanks` |
| 3 | 의미 / 어휘 / relation 승격 | 0.7 / 0.3 / 0.3×0.35 (ollama), 0 / 1 / 0.35 (hash) | `searchIndex`, `fusionWeights` |
| — | (각 단계 결과는 점수가 아니라 다시 **순위**로 바꿔 다음 단계에 넘김) | | |

3단계 후보는 의미 목록과 어휘 목록의 **합집합**입니다. 의미 목록 안에서만 순위를 매기면 정확한 단어 매치가
의미 목록에 없을 때 올라갈 길이 막힙니다.

의미 0.7 / 어휘 0.3은 측정으로 정한 상수가 아니라 출발점입니다. 의미 가중이 크면 바꿔 말한 질문을 이기고,
화면 라벨을 그대로 인용한 질문에서 집니다. `eval --sweep`으로 자기 볼트에서 확인합니다.

## 5. 청킹 — 무엇을 한 단위로 검색할 것인가

### 5.1 왜 자르는가

1. **임베딩 창**: 모델은 창(embeddinggemma 약 2048 토큰)을 넘는 글을 조용히 잘라 버립니다. 긴 노트는 앞부분만
   의미 검색에 걸립니다.
2. **의미 희석**: 한 벡터에 여러 주제를 담으면 방향이 평균이 되어 어느 주제와도 덜 가까워집니다(3.3의 d1이
   여러 주제 벡터의 평균이 된다고 생각하면 됩니다).
3. **근거의 정밀도**: 답에 필요한 건 노트 전체가 아니라 한 단락입니다.

반대로 너무 잘게 자르면 조각이 "어디의 무엇인지" 모르게 됩니다("매출이 3% 늘었다" — 어느 회사, 어느 분기?).

### 5.2 이 플러그인의 규칙 (`rag-corpus-builder`)

| 규칙 | 이유 |
|---|---|
| 원문이 가진 구조(제목, 함수, 단계, 조항)에서 자른다 | 사람이 정한 경계가 이미 의미 단위 |
| 임베딩 유사도로 경계를 찾는 "의미 청킹"은 하지 않는다 | 고정 크기 분할보다 일관된 이득이 없었음(Qu et al. 2025). 방법보다 **크기**가 결과를 크게 바꿈 |
| 구조가 없으면 겹침 있는 고정 크기 | 경계에 걸친 문장이 한쪽에서는 온전하도록 |
| 청크 하나 = 답할 수 있는 한 지점, 임베딩 창 안쪽 | 1번, 2번 문제를 동시에 피함 |
| 청크마다 `context` 문장 50–100토큰 | 잘린 조각의 "어디·무엇"을 복원 (5.4) |

### 5.3 창보다 긴 문서 — 겹치는 윈도 + 평균 풀링

그래도 창보다 긴 문서가 오면 엔진이 처리합니다(`textWindows`, `poolVectors`).

```
예산 1800자, 보폭 = floor(1800 × 0.85) = 1530자 → 윈도끼리 270자 겹침

4000자 문서:  [0 ─ 1800)  [1530 ─ 3330)  [3060 ─ 4000)   → 윈도 3개
각 윈도를 따로 임베딩 → 세 벡터를 성분별 평균 → 다시 길이 1로 정규화 → 문서 벡터 1개
```

예산이 토큰이 아니라 **문자**인 이유: 토크나이저가 로컬에 없고, 한글은 대략 한 글자가 한 토큰 이상이라 문자로
세면 안전한 쪽으로 틀립니다. 색인 결과의 `documents_windowed`가 0보다 크면 청크가 너무 굵다는 신호이고,
고칠 곳은 엔진이 아니라 청크 규칙입니다.

### 5.4 잘린 조각에 맥락 붙이기

청크가 검색에 쓰는 텍스트 = `context` 문장 + 본문, 그리고 `terms` 컬럼에는 부모 노트의 제목·별칭·카탈로그
어휘를 **상속**합니다. 청크에 자기 제목이 없으면 부모 제목을 임베딩의 `title:` 자리에 씁니다.

Anthropic의 Contextual Retrieval 측정: 청크마다 맥락을 붙이면 top-20 검색 실패율이 5.7% → 3.7%(임베딩만),
BM25까지 더하면 2.9%, 리랭커까지 1.9%. 이 플러그인은 카탈로그가 이미 아는 부분은 엔진이 결정적으로 상속하고,
카탈로그가 모르는 "이 조각이 노트의 어디인지"만 `context`로 씁니다.

### 5.5 작게 찾고 크게 읽기

- 검색은 청크 단위로 하되, 결과는 **노트당 1건**으로 묶습니다(`group: 'note'`). 안 묶으면 청크 많은 노트
  하나가 상위 k를 독차지해, 여러 노트가 필요한 질문의 다른 노트가 밀려납니다.
- 답을 쓸 때는 `knowledge_get`으로 노트 **전체**를 엽니다. 검색 단위(작게)와 읽기 단위(크게)를 분리하는 것이
  parent-document 검색입니다.

## 6. 그 밖의 부품

### 6.1 relation 승격

"A와 B의 차이"처럼 비교 질문은 대조의 언어로 쓰여서, 대조를 적은 relation 노트만 걸리고 A·B 각각의 근거
노트는 안 걸리기 쉽습니다. 그래서:

- **정방향**: 어휘 검색이 relation 노트의 참여자를 2개 이상 맞혔으면 그 relation 노트를 올림(`relationRanks`).
- **역방향**: 상위 8위 안의 relation 노트가 선언한 참여자를, 상위 k에 없으면 **창의 끝**에 붙임
  (`relationParticipantRanks`). 최대 창의 절반까지.

끝에 붙이는 이유: 목표는 "상위 k 안에 들어오기"(회수)이지 "2등 하기"(순위)가 아닙니다. 상위에 끼워 넣었더니
비교 질문은 나아졌지만 다른 질문 다섯 개가 깨졌습니다.

### 6.2 리랭커 (크로스인코더)

임베딩(바이인코더)은 질문과 문서를 **따로** 벡터로 만들어 비교합니다. 크로스인코더는 질문과 문서를 **한 입력으로
같이** 읽고 관련도를 냅니다. 더 정확하지만 후보마다 모델을 한 번씩 돌려야 해서, 상위 50개(`--rerank-depth`)만
다시 정렬합니다.

천장: 리랭커는 이미 상위 50 안에 있는 것만 올릴 수 있으니, 최대 이득은 **recall@50 − recall@10**입니다.
리랭커를 붙이기 전에 `eval --k 10`과 `--k 50`으로 이 차이를 먼저 잽니다.

## 7. 잘 되는지 재는 법

`eval`은 `_knowledge/questions.jsonl`의 질문마다 "반드시 나와야 하는 노트"(`required_note_ids`)를 두고 잽니다.

| 지표 | 정의 | 예 (질문 3개) |
|---|---|---|
| recall@k | 찾은 필수 노트 수 / 전체 필수 노트 수 | 필수 5개 중 4개 → 0.8 |
| hits | 필수 노트를 **전부** 찾은 질문 수 | 2 |
| MRR | 질문마다 첫 필수 노트 순위의 역수, 평균(못 찾으면 0) | 1위, 3위, 없음 → (1 + 1/3 + 0)/3 ≈ 0.44 |

recall은 "들어왔는가", MRR은 "얼마나 위에 들어왔는가"입니다. 리랭커는 주로 MRR을, 청크·어휘 수정은 주로
recall을 움직입니다.

측정 규율 세 가지(자세한 근거는 theory.md §5):

- **holdout**: 질문 일부(기본 35%)는 첫 수정 전에 한 번 재고 그 뒤로 보지 않습니다. dev에만 맞춰 고치다 보면
  dev 점수는 오르는데 실제로는 나아지지 않는 과적합이 생깁니다.
- **누수 금지**: 질문 문구를 노트의 별칭에 복사하면 그 질문은 반드시 맞지만 아무것도 잰 게 아닙니다. 추가하는
  어휘는 원문에서만 가져옵니다.
- **한 번에 하나**: `--baseline`으로 질문별 개선/회귀를 비교합니다. 어휘·코퍼스 수정은 회귀가 하나라도 있으면 되돌립니다.

## 8. 한 장 요약

| 부품 | 묻는 것 | 강점 | 약점 |
|---|---|---|---|
| BM25 (단어) | 같은 단어가 얼마나 중요하게 있나 | 정확한 용어·라벨·코드명 | 바꿔 말하면 못 찾음, 활용형에 약함 |
| trigram | 같은 3글자 조각이 있나 | 한국어 활용·조사 | 2글자 단어, 잡음 |
| 코사인 (임베딩) | 뜻의 방향이 가까운가 | 바꿔 말한 질문 | 정확한 용어가 희석됨, 모델 필요 |
| RRF | 여러 순위에서 고르게 위인가 | 점수 단위 맞출 필요 없음 | 점수의 크기 정보는 버림 |
| 청킹 | 무엇을 한 단위로 볼까 | 창 안에 들어감, 정밀한 근거 | 잘린 조각은 맥락을 잃음 → context로 보완 |
| 리랭커 | 질문과 이 문서를 같이 읽으면? | 가장 정확한 순서 | 느림, 이미 회수된 것만 재정렬 |
