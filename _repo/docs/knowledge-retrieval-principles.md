## 0. 전체 그림 — 정보 검색이 푸는 문제

### 0.1 문제의 정의

문서 집합 D와 질의 q가 주어지면, q를 낸 사람에게 **관련 있는(relevant)** 문서를 위에 놓는 순서를 만드는 것.
"관련 있다"는 사람이 판단하는 것이라 기계는 직접 계산할 수 없습니다. 그래서 모든 검색 모델은 관련성을
**대리 신호**로 근사합니다.

| 대리 신호 | 모델 계열 | 이 플러그인 |
|---|---|---|
| 질의 단어가 문서에 있는가, 얼마나 중요하게 | 어휘(lexical, sparse) 모델: Boolean, TF-IDF, BM25, 언어 모델 | FTS5 `bm25()` |
| 질의와 문서의 뜻이 가까운가 | 밀집(dense) 모델: 바이인코더 임베딩 | embeddinggemma + 코사인 |
| 질의와 문서를 같이 읽으면 관련 있어 보이는가 | 크로스인코더 리랭커 | 선택 사항 `--reranker-url` |
| 사람이 선언한 구조 | 링크, 그래프 | relation 노트 승격, `knowledge_neighbors` |

### 0.2 확률 순위 원리 (Probability Ranking Principle)

Robertson(1977)의 원리: **문서를 "관련 있을 확률" P(R=1 | d, q)의 내림차순으로 놓으면, 각 문서의 관련성이
서로 독립이라는 가정 아래 기대 정밀도·재현율이 최적이다.** 거의 모든 순위 모델은 이 확률을 직접 또는
단조 변환한 값으로 근사하는 시도입니다. 순위만 맞으면 되므로, 확률 자체가 아니라 **확률과 같은 순서를 주는
아무 점수**여도 됩니다. 이 사실이 4장(점수 대신 순위로 융합)의 근거가 됩니다.

가정의 한계도 기억해 둘 만합니다. "독립"은 깨집니다. 같은 내용의 문서 두 개가 1, 2위에 오면 두 번째는 새
정보가 없습니다. 이 플러그인이 결과를 **노트당 1건**으로 묶는 것(5.6)은 이 중복 문제를 푸는 작은 다양화
장치입니다.

### 0.3 이 플러그인의 파이프라인

```
질문
 ├─ 어휘 검색 (단어가 겹치는가)
 │   ├─ FTS5 unicode61 (정확한 단어)  ─┐ 컬럼별(title/terms/body) BM25 순위 → RRF
 │   └─ FTS5 trigram (3글자 조각)     ─┘ 컬럼별 BM25 순위 → RRF
 │          └─ 두 목록을 0.7 / 0.3 가중 RRF → 어휘 순위 하나
 ├─ 의미 검색 (뜻이 가까운가)
 │   └─ 질문 벡터와 문서 벡터의 코사인 유사도 → 의미 순위
 └─ relation 승격 (선언된 비교 노트)
          └─ 세 순위를 가중 RRF로 합침 → 노트당 1건으로 묶음 → (선택) 리랭커 → relation 참여자 → 상위 k
```

이 구조를 **하이브리드 검색**이라 부릅니다. 어휘 모델과 밀집 모델은 서로 다른 곳에서 실패하기 때문에 섞습니다.
BEIR 벤치마크(Thakur et al. 2021)에서 학습된 밀집 모델이 학습 도메인 밖에서는 BM25에 자주 졌고, BM25는 정확한
용어를 쓰는 질문에 강하지만 바꿔 말한 질문은 놓칩니다.

## 1. 토큰화 — 글을 셀 수 있는 조각으로

### 1.1 직관

검색은 결국 "조각이 겹치는가"를 셉니다. 무엇을 조각(토큰)으로 볼지가 첫 결정이고, 이후의 모든 점수가 이
결정 위에 있습니다. "재시도"와 "재시도한"이 다른 토큰이면, BM25는 둘이 관련 있다는 걸 영영 모릅니다.

### 1.2 이 플러그인의 세 토크나이저

| 어디 | 방식 | "재시도한 작업" → |
|---|---|---|
| FTS5 `unicode61` 색인 | 유니코드 단어 경계로 끊고 소문자화, 발음 구별 기호 제거 | `재시도한`, `작업` |
| FTS5 `trigram` 색인 | 3글자씩 미끄러지는 창 | `재시도`, `시도한`, `도한␣`, `한␣작`, `␣작업` |
| `tokenize()` (hash 임베딩용) | `Intl.Segmenter` 단어 + `~`가 붙은 3글자 조각 | `재시도한`, `작업`, `~재시도`, `~시도한`, … |

### 1.3 이론: 형태론 문제와 세 가지 해법

한국어는 **교착어**입니다. 어간에 조사·어미가 붙어 하나의 어절이 됩니다(재고 + 를, 재시도 + 하 + ㄴ).
영어의 `retry / retried / retrying`보다 변화가 훨씬 많아서, 공백 단위 토큰은 같은 개념을 수십 개 토큰으로
흩어 놓습니다. 해법은 크게 셋입니다.

| 해법 | 원리 | 장점 | 단점 |
|---|---|---|---|
| 형태소 분석 | 사전과 통계 모델로 어절을 형태소로 나눔(Mecab-ko, Elasticsearch Nori) | 정확한 어간, 짧은 색인 | 사전 의존, 신조어·도메인 용어(`OMS`, `재고수불부`)에 약함, 설치 필요 |
| 어간 추출(stemming) | 규칙으로 접미사 제거(영어 Porter stemmer) | 빠름, 사전 불필요 | 과잉/과소 절단, 한국어 규칙은 조사 목록 수준이 한계 |
| 문자 n-gram | 모든 n글자 조각을 색인 | 언어 지식 불필요, 부분 문자열 매칭 | 색인이 커짐, 무관한 조각 매칭(잡음), n보다 짧은 단어 불가 |

n-gram이 왜 동작하는지: 두 단어가 공유하는 n-gram의 수는 문자열 유사도의 근사입니다. `재시도`와 `재시도한`은
trigram `재시도`를 공유하고, `재고`와 `재시도`는 trigram을 하나도 공유하지 않습니다. n이 작을수록 재현율이
오르고 잡음도 늘어납니다. n=3은 영어권에서 오래 쓰인 균형점이고, 한글은 한 글자가 음절이라 정보량이 커서
3글자면 꽤 구체적입니다.

### 1.4 이 플러그인의 선택

형태소 분석기를 넣지 않았습니다(의존성 없음이 플러그인 원칙). 대신 두 색인을 함께 두고 질의 쪽에서 보정합니다
(`ftsTokens`, `trigramTokens`, `koreanForms`).

- 정확한 단어 색인(정밀도) + trigram 색인(재현율)을 **둘 다** 질의하고 0.7 / 0.3으로 융합.
- trigram이 못 잡는 2글자 한글 명사(재고, 출고, 결제)를 위해, 한글 질의어는 **접두어 검색**(`재고*` → `재고가`).
- 끝의 조사를 떼어 **어간을 하나 더** 넣음: `재고를` → `재고를*`, `재고*`. 원래 단어는 남겨 둡니다. 조사
  목록은 모호하기 때문입니다. `재시도`의 `도`를 조사로 오인해 떼어 `재시*`가 되어도, 떼지 않은 `재시도*`가
  정답을 계속 위로 올립니다. **과잉 절단은 재현율을 넓힐 뿐 정답을 잃지 않게** 설계한 것입니다.
- 질의 토큰은 최대 24개(`MAX_QUERY_TOKENS`). 긴 문장형 질문이 수백 개의 OR 조건이 되는 것을 막습니다.

### 1.5 연습

- **1-1.** "결제를 취소한 주문"을 unicode61 토큰, trigram 토큰, `ftsTokens` 결과(접두어·어간 포함)로 각각 써 보세요.

## 2. BM25 — 확률 모델에서 나온 어휘 점수

### 2.1 직관 세 가지

1. **많이 나올수록 관련 있다**. 하지만 10번 나온 문서가 1번 나온 문서보다 10배 관련 있지는 않다(포화).
2. **흔한 단어는 증거가 약하다**. 모든 문서에 있는 "시스템"보다 5개 문서에만 있는 "수불부"가 강한 증거다(IDF).
3. **긴 문서는 우연히 단어를 품기 쉽다**. 같은 횟수라면 짧은 문서 쪽을 더 쳐준다(길이 정규화).

### 2.2 식

질의어 t 하나에 대한 문서 d의 점수:

```
score(t, d) = IDF(t) × tf × (k1 + 1) / ( tf + k1 × (1 − b + b × |d| / avgdl) )

IDF(t) = ln( (N − n + 0.5) / (n + 0.5) )
```

| 기호 | 뜻 | SQLite FTS5 값 |
|---|---|---|
| tf | 문서 d에 t가 나온 횟수 | — |
| N, n | 전체 문서 수, t가 있는 문서 수 | — |
| \|d\|, avgdl | 문서 길이, 평균 문서 길이(토큰 수) | — |
| k1 | 포화 속도. 클수록 tf를 더 오래 믿음 | 1.2 |
| b | 길이 정규화 강도. 0이면 길이 무시, 1이면 완전 정규화 | 0.75 |

질의어가 여럿이면 질의어별 점수를 더합니다. FTS5의 `bm25()`는 "작을수록 좋음"이 되도록 음수로 돌려주므로
코드는 `ORDER BY bm25(...)` 오름차순입니다.

### 2.3 숫자로 따라가기

문서 100개(N=100) 중 5개(n=5)에만 "수불부"가 있습니다.

```
IDF = ln( (100 − 5 + 0.5) / (5 + 0.5) ) = ln(17.36) ≈ 2.85
```

"수불부"가 2번 나온(tf=2) 두 문서, 평균 길이는 100 토큰:

| 문서 | 길이 | 분모 = tf + 1.2 × (0.25 + 0.75 × \|d\|/100) | tf 부분 = 2 × 2.2 / 분모 | 점수 |
|---|---|---|---|---|
| A | 50 | 2 + 1.2 × 0.625 = 2.75 | 1.60 | **4.57** |
| B | 200 | 2 + 1.2 × 1.75 = 4.10 | 1.07 | 3.06 |

같은 횟수인데 짧은 A가 이깁니다(직관 3). tf를 2에서 20으로 늘려도 A의 tf 부분은 2.2를 넘지 못합니다
(k1 + 1 = 2.2가 상한, 직관 1).

더 놀라운 경우: 길이 50에 **1번** 나온 문서와 길이 200에 **2번** 나온 문서는 짧은 쪽이 이길 수 있습니다.
연습 2-1에서 SQLite로 직접 확인합니다.

### 2.4 이론: BM25는 어디서 왔나

BM25는 경험식처럼 보이지만, 확률 모델 세 단계를 거쳐 나왔습니다. Robertson & Zaragoza(2009)가 전 과정을 정리했습니다.

#### (1) 이진 독립 모델(Binary Independence Model)과 IDF

0.2의 확률 순위 원리에서 출발합니다. 문서를 "각 단어가 있다/없다"의 이진 벡터로 보고, **관련성이 주어지면
단어끼리 독립**이라고 가정합니다. P(R=1|d)로 정렬하는 것은 로그 오즈 log[P(R=1|d) / P(R=0|d)]로 정렬하는 것과
같고, 베이즈 정리와 독립 가정을 적용하면 문서와 상관없는 항이 빠지고 다음만 남습니다.

```
RSV(d) = Σ  w_t,      w_t = log [ p_t (1 − u_t) ] / [ u_t (1 − p_t) ]
       t ∈ q ∩ d

p_t = P(t가 있음 | 관련 문서),  u_t = P(t가 있음 | 무관 문서)
```

이 w_t가 **Robertson–Spärck Jones(RSJ) 가중치**입니다. 관련 문서에 대한 정보가 없으면:

- p_t = 0.5로 둡니다(모르니 반반). 그러면 p_t/(1−p_t) = 1이 되어 사라집니다.
- 대부분의 문서는 무관하므로 u_t ≈ n/N(전체에서 t가 있는 비율).

```
w_t = log (1 − u_t) / u_t = log (N − n) / n    → 0.5 평활화: log (N − n + 0.5) / (n + 0.5)
```

이것이 BM25의 IDF입니다. Spärck Jones(1972)가 경험적으로 제안한 IDF = log(N/n)이 확률 모델에서 거의 그대로
나온다는 것이 이 유도의 의미입니다. 0.5는 n = 0이나 n = N일 때 로그가 터지지 않게 하는 평활화입니다.

**음수 IDF**: n > N/2이면 (N − n + 0.5) < (n + 0.5)라서 IDF가 음수가 됩니다. "절반 넘는 문서에 있는 단어는
있을수록 무관하다"는 뜻인데, 실무에서는 이상하게 동작하므로 구현마다 막습니다. SQLite FTS5는 음수 IDF를
1e-6으로 바꾸고, Lucene/Elasticsearch는 `ln(1 + (N − n + 0.5)/(n + 0.5))`로 항상 양수가 되게 합니다. 작은
볼트에서 아주 흔한 단어는 FTS5에서 사실상 점수에 기여하지 않습니다.

#### (2) 2-포아송 모델과 tf 포화

이진 모델은 횟수(tf)를 버립니다. Harter(1975)는 단어마다 **엘리트(eliteness)**라는 숨은 속성을 가정했습니다.
문서가 그 단어의 주제에 대해 "정말 다루는가"입니다. 엘리트 문서와 아닌 문서에서 tf는 각각 다른 평균의
포아송 분포를 따르고, 전체 tf 분포는 두 포아송의 혼합입니다.

이 혼합 모델로 가중치를 정확히 쓰면 매개변수가 너무 많습니다. Robertson & Walker(1994)는 그 곡선의 **모양**만
흉내 내는 단순한 함수를 골랐습니다.

```
tf × (k1 + 1) / (tf + k1)
```

- tf = 0이면 0, tf가 커지면 k1 + 1로 수렴하는 포화 곡선.
- k1 = 0이면 tf와 무관하게 1(이진 모델로 돌아감). k1 → ∞이면 tf에 비례(포화 없음).
- 의미: 단어가 한 번 나오면 "이 문서가 그 주제를 다룰" 확률이 크게 오르지만, 두 번째, 세 번째는 그 확률을
  점점 덜 올린다. 엘리트성은 있다/없다의 문제이고, 그 증거로서 tf의 한계 효용이 줄어드는 것.

#### (3) 길이 정규화 — 장황함 가설과 범위 가설

긴 문서에 tf가 높은 이유는 둘 중 하나입니다(Robertson & Walker 1994).

- **장황함(verbosity) 가설**: 같은 내용을 길게 썼다. 그러면 tf를 길이로 나눠야 한다.
- **범위(scope) 가설**: 더 많은 주제를 다룬다. 그러면 tf는 정당하고 나누면 안 된다.

현실은 둘의 섞임이라, 길이로 나누는 정도를 b로 조절합니다. 분모의 k1을 `k1 × (1 − b + b·|d|/avgdl)`로 바꾸는
것은 "긴 문서는 포화가 더 늦게 오게" 하는 것과 같습니다. b = 0.75는 TREC 실험에서 잘 나온 기본값이고, Singhal
et al.(1996)의 **피벗 길이 정규화**와 같은 아이디어(평균 길이를 기준으로 짧으면 보너스, 길면 감점)입니다.

이 세 조각을 곱하면 BM25입니다. 이름의 "BM"은 Best Match, 25는 Okapi 시스템에서 시도한 25번째 변형이라는 뜻입니다.

### 2.5 이론: 필드가 여럿일 때 — BM25F

문서가 제목·본문처럼 필드로 나뉠 때 쉬운 방법은 필드별 BM25를 가중합하는 것인데, Robertson, Zaragoza & Taylor
(2004)는 이것이 틀렸다고 지적했습니다. 각 필드에서 따로 **포화**가 일어나니, 제목에 1번 + 본문에 1번은
본문에 2번보다 훨씬 큰 점수가 됩니다. 포화의 의미(엘리트성의 증거)가 깨집니다.

BM25F는 **포화 전에** 필드를 합칩니다.

```
tf̃(t, d) = Σ  w_f × tf_f / (1 − b_f + b_f × len_f / avglen_f)
          필드 f

score(t, d) = IDF(t) × tf̃ × (k1 + 1) / (tf̃ + k1)
```

필드 가중치 w_f는 "제목의 1번은 본문의 몇 번 어치인가"를 뜻합니다.

### 2.6 이 플러그인: 필드 점수 대신 필드 순위

색인은 `title`(제목), `terms`(별칭·태그·요약 등 큐레이션 어휘), `body`(본문) 세 컬럼입니다. 이 플러그인은
BM25F도, FTS5의 컬럼 가중 `bm25(t, w1, w2, w3)`도 쓰지 않습니다. FTS5의 길이 정규화는 **모든 컬럼을 합친 문서
길이**로 하므로, 제목이 맞은 긴 노트가 본문에서 한 번 언급한 짧은 노트에게 집니다(2.3의 A/B 효과).

대신 컬럼마다 BM25 순위를 **따로** 내고 RRF로 합칩니다(`ftsRanks`, `COLUMN_RRF_WEIGHTS = title 0.5,
terms 0.35, body 0.15`). 순위에는 길이가 섞이지 않으므로 "제목에 맞음"이 길이와 상관없이 강한 증거로 남습니다.
BM25F가 "어떻게 합칠까"를 확률 모델로 푼다면, 여기서는 "합치지 말고 순위로 투표하자"로 피해 갑니다. 예시는 4.3.

### 2.7 참고: 다른 어휘 모델

| 모델 | 아이디어 | 관계 |
|---|---|---|
| Boolean | AND/OR/NOT 일치 여부만 | 순위 없음. FTS5 `MATCH`의 후보 선정이 이 단계 |
| TF-IDF + 벡터 공간 모델 (Salton 1975) | 문서를 tf×idf 벡터로, 질의와 코사인 | 3장 코사인 유사도의 원조. 포화와 길이 정규화가 약함 |
| 질의 우도 언어 모델 (Ponte & Croft 1998; Zhai & Lafferty 2001) | 문서마다 단어 분포를 세우고 P(q \| 문서 모델)로 정렬, Dirichlet 평활화 | BM25와 성능이 비슷하고, 평활화가 IDF·길이 정규화 역할을 함 |
| 학습된 희소 모델 (SPLADE, 2021) | 트랜스포머가 단어별 가중치와 확장어를 학습 | 색인은 BM25처럼 역색인, 의미는 신경망. 이 플러그인은 미사용 |

## 3. 임베딩과 코사인 유사도 — 뜻을 벡터로

### 3.1 직관

임베딩 모델은 글 하나를 고정 길이 숫자 배열(벡터)로 바꿉니다. 학습 결과 뜻이 비슷한 글은 비슷한 방향을
가리킵니다. "주문이 안 들어와요"와 "발주 누락"은 겹치는 단어가 없어도 방향이 가깝습니다. 어휘 검색이 못 하는
**바꿔 말한 질문**을 잡는 수단입니다.

### 3.2 식

```
cos(q, d) = (q · d) / (‖q‖ × ‖d‖) = Σ qᵢdᵢ / ( √Σqᵢ² × √Σdᵢ² )
```

두 벡터 사이 각도의 코사인입니다. 같은 방향 1, 직각 0, 반대 −1. **길이는 무시하고 방향만** 봅니다.

### 3.3 숫자로 따라가기 (3차원)

```
q = (1, 2, 0)    d1 = (2, 4, 1)    d2 = (0, 1, 3)

q·d1 = 2 + 8 + 0 = 10    ‖q‖ = √5 ≈ 2.24   ‖d1‖ = √21 ≈ 4.58   cos = 10 / 10.25 ≈ 0.98
q·d2 = 0 + 2 + 0 = 2                      ‖d2‖ = √10 ≈ 3.16   cos = 2 / 7.07  ≈ 0.28
```

### 3.4 이론: 뜻이 어떻게 숫자가 되나

#### (1) 분포 가설

"단어의 뜻은 그 단어가 함께 쓰이는 단어들로 알 수 있다"(Harris 1954; Firth 1957 "You shall know a word by the
company it keeps"). "재고"와 "수량"이 비슷한 문맥에 나오면 비슷한 벡터를 주도록 학습하면, 벡터 공간의 거리가
뜻의 거리를 근사합니다. word2vec(Mikolov et al. 2013)이 단어 수준에서, BERT(Devlin et al. 2019)가 문맥에 따라
같은 단어도 다른 벡터를 주는 수준에서 이를 구현했습니다.

#### (2) 문장 임베딩과 바이인코더

검색에는 단어가 아니라 질문·문서 전체의 벡터가 필요합니다. **바이인코더(bi-encoder, dual encoder)**는
질문과 문서를 **각각 따로** 인코더에 넣어 벡터를 얻습니다(Sentence-BERT, Reimers & Gurevych 2019; DPR,
Karpukhin et al. 2020). 따로 인코딩하기 때문에 문서 벡터는 **미리** 계산해 저장할 수 있고, 검색 시에는 질문
하나만 인코딩하면 됩니다. 이것이 리랭커(6장)와의 근본 차이입니다.

#### (3) 대조 학습 — 무엇이 "가까움"을 만드나

바이인코더는 (질문, 정답 문서) 쌍으로 학습합니다. 손실 함수는 보통 **InfoNCE**(대조 손실)입니다.

```
L = − log  exp( sim(q, d⁺) / τ )  /  Σⱼ exp( sim(q, dⱼ) / τ )
```

- d⁺는 정답 문서, 분모의 dⱼ는 정답 하나와 오답(음성) 여러 개.
- sim은 보통 **정규화된 내적 = 코사인**. 그래서 이렇게 학습된 모델은 코사인으로 비교해야 맞습니다.
- τ(온도)는 분포의 뾰족함. 작을수록 정답과 가장 헷갈리는 오답의 차이에 집중합니다.
- 분자를 키우고 분모를 줄이는 것 = 정답은 당기고 오답은 밀어내기.

음성 예시를 얻는 방법이 성능을 크게 좌우합니다. **배치 내 음성(in-batch negatives)**은 같은 배치의 다른 질문의
정답들을 오답으로 씁니다(B 쌍이면 질문당 B−1개 오답이 공짜). **어려운 음성(hard negatives)**은 BM25가 높게
매겼지만 정답이 아닌 문서처럼 헷갈리는 오답입니다. DPR은 BM25 어려운 음성으로 성능을 크게 올렸습니다.

#### (4) 비대칭 검색과 프롬프트

질문("X가 뭐야?")과 문서(설명문)는 생김새가 다릅니다. 같은 인코더로 둘을 똑같이 다루면 "질문끼리" 가까워지는
편향이 생깁니다. 그래서 E5, EmbeddingGemma 같은 모델은 입력 앞에 역할 표시를 붙여 학습합니다. EmbeddingGemma는
질문 앞에 `task: search result | query: `, 문서 앞에 `title: {제목|none} | text: `를 붙이도록 문서화되어 있습니다.

#### (5) 기하: 코사인, 내적, 유클리드 거리는 같은 순위를 준다 (단위 벡터일 때)

벡터를 길이 1로 정규화하면

```
‖a − b‖² = ‖a‖² + ‖b‖² − 2 a·b = 2 − 2 cos(a, b)
```

이므로 코사인이 크다 ⇔ 내적이 크다 ⇔ 거리가 작다. 세 척도의 순위가 같습니다. 이 플러그인은 저장 시 정규화
(`normalizeVector`)하므로 코사인 = 내적입니다.

#### (6) 코사인 값 자체는 믿지 말 것 — 비등방성

학습된 임베딩은 공간 전체에 고르게 퍼지지 않고 좁은 원뿔 안에 몰리는 경향이 있습니다(**비등방성**, Ethayarajh
2019). 그래서 아무 문장 쌍이나 코사인 0.6~0.8이 나오기도 하고, "0.75면 관련 있음" 같은 절대 기준이 모델·질문마다
달라집니다. 같은 질문 안에서의 **순서**는 믿을 만하지만 **값**은 보정되어 있지 않습니다. 4장에서 점수 대신 순위를
융합하는 또 하나의 이유입니다.

#### (7) 고차원에서 무작위 벡터는 거의 직교한다

d차원에서 무작위 단위 벡터 두 개의 코사인은 평균 0, 표준편차 약 1/√d로 모입니다. d = 384면 약 0.05, d = 768이면
약 0.036입니다. 즉 **관련 없는 것끼리는 거의 0 근처**에 모이고, 의미 있는 유사도는 그 바깥으로 튀어나옵니다.
3.5의 hash 임베딩이 충돌에도 불구하고 동작하는 이유이기도 합니다.

#### (8) Matryoshka 표현

EmbeddingGemma(768차원)는 Matryoshka 표현 학습(Kusupati et al. 2022)으로 학습되어, 앞 512, 256, 128차원만
잘라 써도 성능이 조금만 떨어집니다. 앞쪽 차원에 중요한 정보가 먼저 담기도록 여러 길이에서 동시에 손실을 거는
방식입니다. 이 플러그인은 전체 768차원을 씁니다.

### 3.5 이 플러그인: `hash` provider — 의미가 아닌 특징 해싱

모델 없이도 돌도록 기본값은 `hash`입니다(`hashEmbedding`, 384차원). 원리는 **특징 해싱(hashing trick,
Weinberger et al. 2009)**입니다.

```
φⱼ(x) = Σ  ξ(i) × xᵢ          h: 토큰 → {0..383},  ξ: 토큰 → {+1, −1}
       i: h(i) = j
```

- 토큰마다 해시 h로 칸 하나를 고르고, 다른 해시 비트 ξ로 부호를 정해 더합니다.
- 부호 해시가 있으면 E[φ(x)·φ(x′)] = x·x′입니다. 충돌이 나도 **평균적으로** 원래 내적이 보존됩니다(충돌의
  +와 −가 상쇄). 부호가 없으면 충돌이 항상 내적을 부풀립니다.
- 이 구현은 SHA-256 다이제스트에서 칸 두 개(두 번째는 가중 0.5)와 부호를 뽑고, 단어 1.0, `~`trigram 0.35
  가중치를 줍니다.

결과적으로 단어가 겹치면 같은 칸이 올라가 코사인이 올라가지만, **뜻은 전혀 모릅니다**. 또 하나의 어휘 검색입니다.
그래서 hash일 때 의미 가중은 0입니다(4.4). 측정상 hash → embeddinggemma 전환이 recall@10 0.631 → 0.803으로,
엔진 개선 여섯 버전을 합친 것보다 컸습니다.

### 3.6 이 플러그인: 검색 방법 — 전수 비교

질문 벡터와 **모든** 문서 벡터의 내적을 구해 정렬합니다. 비용은 문서 수 N × 차원 d입니다. 노트 1만 개 × 768차원 =
약 770만 번의 곱셈-덧셈이니, 수 밀리초입니다.

규모가 수백만이 되면 **근사 최근접 이웃(ANN)** 색인이 필요합니다. 정확도를 조금 잃는 대신 일부만 봅니다.

| 방법 | 아이디어 |
|---|---|
| IVF | k-means로 공간을 칸으로 나누고, 질문과 가까운 몇 칸만 봄 |
| PQ (Jégou et al. 2011) | 벡터를 조각내 각 조각을 코드북 번호로 압축, 메모리 절감 |
| HNSW (Malkov & Yashunin 2018) | 여러 층의 근접 그래프를 위층(성김)에서 아래층(촘촘)으로 탐욕 이동 |

이 플러그인은 정확한 결과와 단순함을 택해 전수 비교합니다.

  임베딩"이라는 말이 나오는지 InfoNCE 분모로 설명하세요.

## 4. 순위 융합 — RRF와 그 대안

### 4.1 직관

BM25 점수 4.6과 코사인 0.82는 단위가 달라 더할 수 없습니다. BM25는 상한이 없고 질의 길이에 따라 커지며, 코사인은
-1~1이지만 모델마다 쓰는 범위가 다릅니다(3.4(6)). 하지만 "1등"과 "3등"은 어느 시스템에서나 같은 뜻입니다.

### 4.2 식 — Reciprocal Rank Fusion

```
RRF(d) = Σ  w_s / ( k + rank_s(d) )      (k = 60, rank는 1부터)
        목록 s
```

어떤 목록에 없는 문서는 그 항이 0입니다. 원 논문(Cormack, Clarke & Buettcher 2009)은 가중치 없이 k = 60을
썼고, 이 플러그인은 가중치를 붙인 형태를 씁니다(`RRF_K = 60`).

### 4.3 숫자로 따라가기

**k = 60이 하는 일:**

```
1위: 1/61 = 0.01639     2위: 1/62 = 0.01613     10위: 1/70 = 0.01429     61위: 1/121 = 0.00826
```

- 1위와 2위의 차이가 아주 작습니다.
- 61위의 몫이 1위의 절반입니다. 즉 **한 목록에서 61위 안에만 들어도 1위 표의 절반을 받습니다.**

**고르게 중간 vs 한쪽 1위:**

| 문서 | 목록 1 | 목록 2 | RRF |
|---|---|---|---|
| X | 1위 | 없음 | 1/61 = 0.01639 |
| Y | 30위 | 30위 | 2/90 = **0.02222** |

두 시스템이 모두 "꽤 관련 있다"고 한 Y가, 한 시스템만 확신한 X를 이깁니다. RRF는 **합의**에 보상합니다.

**이 플러그인의 컬럼 융합:**

| 문서 | title 순위 | terms 순위 | body 순위 | RRF |
|---|---|---|---|---|
| A (긴 노트, 제목이 맞음) | 1 | — | — | 0.5/61 = **0.00820** |
| B (짧은 노트, 본문·태그에 언급) | — | 5 | 1 | 0.35/65 + 0.15/61 = 0.00538 + 0.00246 = 0.00784 |

A가 이깁니다. BM25 점수를 그대로 더했다면 짧은 B의 높은 점수가 이겼을 수 있습니다(2.6).

### 4.4 이론: 융합 방법의 계보

| 방법 | 식 | 문제 |
|---|---|---|
| CombSUM (Fox & Shaw 1994) | 정규화한 점수의 합 | 정규화 방법에 민감 |
| CombMNZ | CombSUM × (그 문서를 찾은 시스템 수) | 같음, 합의 보너스는 있음 |
| Borda count | 목록 길이 n에서 1위 n점, 2위 n−1점, … | 목록 길이가 다르면 불공평, 하위권 차이가 상위권 차이만큼 큼 |
| Condorcet | 문서 쌍마다 다수결 | 순환(A>B>C>A) 가능, 계산 비용 |
| RRF | Σ 1/(k + rank) | 점수 크기 정보를 버림, k에 민감 |

**점수 정규화가 왜 깨지기 쉬운가.** min-max 정규화 `(s − min)/(max − min)`는 이상치 하나에 무너집니다. BM25
점수가 [12.0, 3.1, 3.0, 2.9]이면 정규화 후 [1.0, 0.02, 0.01, 0]이 되어, 2~4위가 사실상 0과 같아집니다.
목록마다 이상치의 유무가 달라서 같은 "0.5"가 시스템마다 다른 뜻이 됩니다. z-score도 분포 가정이 맞지 않습니다.

**RRF가 잘 동작하는 이유.** 순위는 시스템에 상관없이 같은 척도이고, 1/(k + r)는 상위를 더 중시하면서도(오목)
k가 커서 1위의 독점을 막습니다. Cormack 등은 TREC 데이터에서 RRF가 Condorcet, CombMNZ, 개별 학습 순위 모델보다
일관되게 좋다고 보고했습니다.

**반론.** Bruch, Gai & Ingber(2023, ACM TOIS)는 하이브리드 검색에서 RRF를 분석해, (1) RRF가 k에 생각보다
민감하고 (2) 점수를 잘 정규화한 **볼록 결합** α·lexical + (1−α)·semantic을 소량의 라벨 데이터로 맞추면 RRF보다
나으며 표본 효율도 좋다고 보고했습니다. "RRF는 조정 없이 쓸 수 있는 좋은 기본값이고, 평가 셋이 있으면 더 나은
방법이 있다"가 공정한 요약입니다. 이 플러그인이 가중치를 `eval --sweep`으로 조정하게 둔 것이 그 중간입니다.

### 4.5 이 플러그인: RRF가 쓰이는 네 곳

| 단계 | 합치는 것 | 가중치 | 함수 |
|---|---|---|---|
| 1 | 한 FTS 색인의 title / terms / body 순위 | 0.5 / 0.35 / 0.15 | `ftsRanks` |
| 2 | 정확 단어 색인 / trigram 색인 | 0.7 / 0.3 | `fuseLexicalRanks` |
| 3 | 의미 / 어휘 / relation 승격 | 0.7 / 0.3 / 0.3×0.35 (ollama), 0 / 1 / 0.35 (hash) | `searchIndex`, `fusionWeights` |

- 각 단계 결과는 점수가 아니라 다시 **순위**로 바꿔 다음 단계에 넘깁니다. 그래서 3단계는 언제나 "순위 둘"을 합칩니다.
- 3단계 후보는 의미 목록과 어휘 목록의 **합집합**입니다. 의미 목록 안에서만 순위를 매기면 정확한 단어 매치가
  의미 목록에 없을 때 올라갈 길이 막힙니다.
- 동점이면 코사인 값으로 2차 정렬합니다. 어휘 매치가 하나도 없으면 모든 어휘 항이 0이라 의미 순서로 떨어집니다.
- 의미 0.7 / 어휘 0.3은 측정된 상수가 아니라 출발점입니다. 의미 가중이 크면 바꿔 말한 질문을 이기고, 화면 라벨을
  그대로 인용한 질문에서 집니다. `eval --sweep 0.2,0.3,0.5`로 자기 볼트에서 확인합니다.

## 5. 청킹 — 무엇을 한 단위로 검색할 것인가

### 5.1 직관

청크는 "검색이 돌려주는 가장 작은 단위"입니다. 자르는 이유는 셋입니다.

1. **임베딩 창**: 모델은 창(EmbeddingGemma 2048 토큰)을 넘는 글을 조용히 잘라 버립니다. 긴 노트는 앞부분만 의미 검색에 걸립니다.
2. **의미 희석**: 한 벡터에 여러 주제를 담으면 방향이 그 평균이 되어 어느 주제와도 덜 가까워집니다.
3. **근거의 정밀도**: 답에 필요한 건 노트 전체가 아니라 한 단락입니다.

반대로 너무 잘게 자르면 조각이 "어디의 무엇인지" 모르게 됩니다("매출이 3% 늘었다" — 어느 회사, 어느 분기?).

### 5.2 이론: 희석을 기하로 보기

문서가 주제 A, B를 반씩 담는다고 하고, 주제 벡터 a, b가 직교하는 단위 벡터라고 합시다. 문서 벡터는 대략
(a + b)/‖a + b‖ = (a + b)/√2입니다. A에 대한 질문 q = a와의 코사인은 1/√2 ≈ 0.71. 주제가 4개면 1/2, n개면
1/√n로 떨어집니다. A만 담은 짧은 청크는 1.0이니, **주제가 섞일수록 각 주제의 질문에서 순위가 내려갑니다.**
Dense X Retrieval(Chen et al. 2024)이 문단 대신 **명제**(사실 하나를 담은 자족적 문장)를 단위로 쓰면 검색이
나아진다고 보고한 것도 같은 원리입니다.

BM25에도 비슷한 효과가 있습니다. 긴 청크는 길이 정규화로 감점됩니다(2.4(3)).

### 5.3 이론: 경계를 어떻게 정할까

| 방법 | 원리 | 근거 |
|---|---|---|
| 고정 크기 + 겹침 | n자/n토큰마다 자름 | 단순, 재현 가능 |
| 구조 기반 | 제목, 함수, 단계, 조항에서 자름 | 사람이 정한 의미 단위 |
| 의미 청킹 | 인접 문장 임베딩 유사도가 떨어지는 곳에서 자름 | Qu et al.(NAACL 2025 Findings): 고정 크기 대비 **일관된 이득 없음**, 비용만 큼 |
| 명제 분해 | LLM이 문서를 자족적 명제로 다시 씀 | Dense X(2024): 검색 향상, 대신 LLM 비용과 원문과의 거리 |
| late chunking | 문서 전체를 긴 문맥 모델에 넣고, 토큰 표현을 청크별로 평균 | Günther et al.(2024): 청크가 주변 문맥을 품음. 토큰 단위 출력이 필요 |

Chroma(2024)의 측정은 같은 방법이라도 **크기**(200 vs 400 토큰)에 따라 순위가 뒤집힌다는 것을 보였습니다.
"어떻게 자르느냐"보다 "얼마나 크게 자르느냐"가 더 중요하다는 것이 현재까지의 실증적 결론입니다.

### 5.4 이론: 겹침이 보장하는 것

윈도 크기 W, 보폭 s = W − o(o = 겹침)로 자르면, **길이가 o 이하인 구간은 반드시 어떤 윈도 하나에 온전히
들어갑니다.**

증명: 구간 [a, a + L), L ≤ o. 시작점이 a 이하인 윈도 중 가장 늦은 것의 시작점 p는 a − s < p ≤ a를 만족합니다.
그 끝은 p + W > a − s + W = a + o ≥ a + L. 따라서 구간 전체가 그 윈도 안에 있습니다. ∎

즉 겹침은 "경계에 걸쳐서 어느 쪽에서도 온전하지 않은 문장"을 없애는 장치이고, 겹침 크기는 지키고 싶은 문장
길이로 정합니다.

### 5.5 이 플러그인의 규칙

**청크를 만드는 쪽 (`rag-corpus-builder`)**

| 규칙 | 이유 |
|---|---|
| 원문이 가진 구조(제목, 함수, 단계, 조항)에서 자른다 | 사람이 정한 경계가 이미 의미 단위 |
| 의미 청킹은 하지 않는다 | 5.3, 비용 대비 이득 없음 |
| 구조가 없으면 겹침 있는 고정 크기 | 5.4 |
| 청크 하나 = 답할 수 있는 한 지점, 임베딩 창 안쪽 | 5.1의 1번, 2번 문제를 동시에 피함 |
| 청크마다 `context` 문장 50–100토큰 | 잘린 조각의 "어디·무엇"을 복원(아래) |

**창보다 긴 문서 — 겹치는 윈도 + 평균 풀링 (`textWindows`, `poolVectors`)**

```
예산 1800자, 보폭 = floor(1800 × 0.85) = 1530자 → 윈도끼리 270자 겹침

4000자 문서:  [0 ─ 1800)  [1530 ─ 3330)  [3060 ─ 4000)   → 윈도 3개
각 윈도를 따로 임베딩 → 세 벡터를 성분별 평균 → 다시 길이 1로 정규화 → 문서 벡터 1개
```

- 5.4에 따라 270자 이하의 구절은 어떤 윈도에 온전히 들어갑니다.
- 평균 풀링은 윈도 벡터들의 **무게 중심 방향**입니다. 윈도들이 같은 주제면 평균도 그 방향이고, 다르면 5.2의
  희석이 그대로 일어납니다. 그래서 윈도링은 응급조치이고 해결은 청크를 잘게 만드는 것입니다.
- late chunking(5.3)과 반대 방향입니다. 윈도를 **각각** 인코딩하므로 윈도 사이 문맥은 공유되지 않습니다.
  Ollama `/api/embed`가 토큰 단위 출력을 주지 않아 late chunking은 쓸 수 없습니다. 윈도마다 문서 프롬프트와
  제목을 붙이는 것이 현재의 근사입니다.
- 예산이 토큰이 아니라 **문자**인 이유: 토크나이저가 로컬에 없고, 한글은 대략 한 글자가 한 토큰 이상이라
  문자로 세면 안전한 쪽으로 틀립니다.
- 색인 결과의 `documents_windowed`가 0보다 크면 청크가 너무 굵다는 신호이고, 고칠 곳은 엔진이 아니라 청크 규칙입니다.

**잘린 조각에 맥락 붙이기 (Contextual Retrieval)**

- 청크가 검색에 쓰는 텍스트 = `context` 문장 + 본문.
- `terms` 컬럼에는 부모 노트의 제목·별칭·카탈로그 어휘를 **상속**합니다. 자기 제목이 없으면 부모 제목을
  임베딩의 `title:` 자리에 씁니다.
- Anthropic의 측정(2024): 청크마다 맥락을 붙이면 top-20 검색 실패율이 5.7% → 3.7%(임베딩만), BM25까지 2.9%,
  리랭커까지 1.9%. 문서 요약을 모든 청크에 똑같이 붙이는 방식은 이득이 매우 작았습니다.
- 이 플러그인은 카탈로그가 이미 아는 부분은 엔진이 결정적으로 상속하고, 카탈로그가 모르는 "이 조각이 노트의
  어디인지"만 `context`로 씁니다.

### 5.6 작게 찾고 크게 읽기

- 검색은 청크 단위로 하되, 결과는 **노트당 1건**으로 묶습니다(`group: 'note'`). 안 묶으면 청크 많은 노트 하나가
  상위 k를 독차지해, 여러 노트가 필요한 질문의 다른 노트가 밀려납니다(0.2의 독립 가정이 깨지는 경우).
- 답을 쓸 때는 `knowledge_get`으로 노트 **전체**를 엽니다. 검색 단위(작게)와 읽기 단위(크게)를 분리하는 것이
  parent-document(small-to-big) 검색입니다.
- 생성 쪽 근거: 긴 문맥을 받은 LLM은 문맥 **가운데**에 있는 정보를 앞뒤보다 덜 활용합니다("Lost in the Middle",
  Liu et al. 2024). 많이 넣는 것보다 맞는 것을 넣는 것이 중요한 이유입니다.

  (`textWindows`의 반복 조건: `start + budget >= length`이면 멈춤)
- **5-2.** 주제 3개가 같은 비중으로 섞인 청크에서, 한 주제에 대한 질문과의 코사인은 대략 얼마인가요?(5.2 가정)

## 6. 리랭킹과 그 밖의 모델 지도

### 6.1 세 가지 상호작용 방식

| 방식 | 질문과 문서를 어떻게 보나 | 점수 | 비용 | 예 |
|---|---|---|---|---|
| 바이인코더 | 따로 인코딩, 벡터 하나씩 | 코사인 | 문서는 미리, 질문 1회 | DPR, EmbeddingGemma |
| late interaction | 따로 인코딩, **토큰마다** 벡터 | Σᵢ maxⱼ qᵢ·dⱼ (MaxSim) | 문서는 미리, 저장량 큼 | ColBERT (Khattab & Zaharia 2020) |
| 크로스인코더 | **한 입력으로 같이** 읽음 | 관련도 하나 | 후보마다 모델 1회 | monoBERT (Nogueira & Cho 2019), bge-reranker |

크로스인코더가 가장 정확한 이유는 어텐션이 질문의 각 단어와 문서의 각 단어를 **직접** 비교하기 때문입니다.
바이인코더는 문서를 질문과 상관없이 하나의 벡터로 미리 압축하니 정보가 손실됩니다. 대신 크로스인코더는 문서를
미리 계산할 수 없어 전체 코퍼스에는 못 쓰고, **짧은 후보 목록을 다시 정렬**하는 데만 씁니다. 이 "싸게 많이 찾고,
비싸게 적게 고르는" 다단계 구조가 현대 검색의 표준입니다(Lin, Nogueira & Yates 2021).

### 6.2 이 플러그인

- `--reranker-url`, `--reranker-model`, `--rerank-depth 50`(기본). Cohere/Jina `/v1/rerank` 형식이라 llama.cpp,
  text-embeddings-inference 서버를 그대로 붙일 수 있습니다. 문서는 제목 + 섹션 + 본문 앞 1200자로 보냅니다.
- 노트당 1건으로 묶은 **뒤**, 창을 만들기 **전**에 다시 정렬합니다. 실패하면 융합 순서로 돌아가고 `rerank_error`를 보고합니다.
- **천장**: 리랭커는 이미 상위 50 안에 있는 것만 올릴 수 있으니, 최대 이득은 **recall@50 − recall@10**입니다.
  리랭커를 붙이기 전에 `eval --k 10`과 `--k 50`으로 이 차이를 먼저 잽니다. 차이가 작으면 리랭커보다 회수
  단계(어휘, 임베딩, 청크)를 고쳐야 합니다.

## 7. relation 승격 — 이 플러그인 고유 규칙

외부 이론이 아니라 측정에서 나온 설계입니다.

**문제.** "A와 B의 차이"처럼 비교 질문은 대조의 언어로 쓰여서, 대조를 적은 relation 노트만 걸리고 A·B 각각의
근거 노트는 안 걸리기 쉽습니다. HotpotQA(Yang et al. 2018)가 구분한 **비교형 멀티홉 질문**입니다.

**해법.**

- **정방향** (`relationRanks`): 어휘 검색이 한 relation 노트의 선언된 참여자를 2개 이상 맞혔으면 그 relation
  노트를 별도 RRF 항(가중 0.35 × 어휘 가중)으로 올림. 점수를 더하기만 하므로 강등은 없음.
- **역방향** (`relationParticipantRanks`): 상위 8위 안의 relation 노트가 선언한 참여자를, 상위 k에 없으면
  **창의 끝**에 붙임. 최대 창의 절반까지.

**설계 원리.**

- 목표는 **회수**(상위 k 안에 들어오기)이지 **순위**(2등 하기)가 아닙니다. 상위에 끼워 넣었더니 비교 질문은
  나아졌지만 MRR이 떨어지고 다른 질문 다섯 개가 깨졌습니다.
- 끝에 붙이면 창의 경계가 움직입니다(9위였던 형제 노트가 밀려남). 그래서 경계를 한 번 읽지 않고 **고정점이 될
  때까지 다시 풉니다**. 밀려난 노트는 `relation_participant_evicted_ids`로 보고합니다.
- 동시출현이 아니라 **선언된 참여자만** 승격합니다. 같이 나온다는 것은 관계의 후보이지 증거가 아닙니다.

## 8. 평가 — 무엇을, 어떻게 재는가

### 8.1 지표

`eval`은 `_knowledge/questions.jsonl`의 질문마다 "반드시 나와야 하는 노트"(`required_note_ids`)를 두고 잽니다.

| 지표 | 정의 | 예 (질문 3개) |
|---|---|---|
| recall@k | 찾은 필수 노트 수 / 전체 필수 노트 수 (전체 합산) | 필수 5개 중 4개 → 0.8 |
| hits | 필수 노트를 **전부** 찾은 질문 수 | 2 |
| MRR | 질문마다 첫 필수 노트 순위의 역수, 평균(못 찾으면 0) | 1위, 3위, 없음 → (1 + 1/3 + 0)/3 ≈ 0.44 |

recall은 "들어왔는가", MRR은 "얼마나 위에 들어왔는가"입니다. 리랭커는 주로 MRR을, 청크·어휘 수정은 주로 recall을 움직입니다.

### 8.2 이론: 다른 지표들

| 지표 | 식 | 언제 |
|---|---|---|
| precision@k | 상위 k 중 관련 문서 비율 | 사용자가 상위 k를 다 볼 때 |
| AP / MAP | 관련 문서가 나올 때마다 그 지점의 precision을 평균 / 질문별 평균 | 관련 문서가 여럿, 순위 전체가 중요할 때 |
| nDCG@k (Järvelin & Kekäläinen 2002) | DCG = Σᵢ (2^relᵢ − 1) / log₂(i + 1), 이상적 순서의 DCG로 나눔 | 관련도가 등급(0/1/2/3)일 때 |
| MRR | 1 / 첫 정답 순위 | 정답 하나만 찾으면 될 때 |

nDCG 예: 상위 3개의 관련도가 [2, 0, 1]이면 DCG = 3/1 + 0/1.585 + 1/2 = 3.5. 이상적 순서 [2, 1, 0]의 DCG =
3 + 1/1.585 = 3.63. nDCG = 3.5 / 3.63 ≈ 0.96. 아래 순위일수록 log로 할인됩니다.

이 플러그인은 관련도가 "필수 노트냐 아니냐"의 이진이고, 답을 쓰려면 필수 노트가 **모두** 필요하므로 recall과
hits를 중심에 둡니다. 생성 쪽은 인용 정밀도/재현율(RAGAS의 context precision/recall과 같은 틀)을 보고만 하고
게이트로 걸지 않습니다. 게이트로 걸면 답이 더 잘이 아니라 덜 인용하도록 길들여지기 때문입니다.

### 8.3 이론: 두 설정 중 어느 쪽이 나은가 — 부호 검정

질문이 수십 개뿐이면 한 문항이 recall을 몇 포인트 움직입니다. "0.80 → 0.82"는 우연일 수 있습니다.
이 플러그인은 `eval --sweep`의 승자가 `decisive`인지 **정확 이항 부호 검정**(`signTestPValue`)으로 판정합니다.

- 질문마다 나아짐(+), 나빠짐(−), 그대로를 셉니다. 그대로는 정보가 없으니 버립니다.
- "두 설정이 같다"는 귀무가설 아래 움직인 질문 각각은 공정한 동전입니다. n = (+) + (−)개 중 적은 쪽이 m개 이하로
  나올 확률을 양쪽으로 계산합니다.

```
p = 2 × Σ_{i=0..m} C(n, i) / 2ⁿ     (m = min(+, −))
```

| 결과 | 계산 | p | decisive (p < 0.05) |
|---|---|---|---|
| 개선 8, 회귀 1 | 2 × (1 + 9) / 512 | 0.039 | 예 |
| 개선 6, 회귀 1 | 2 × (1 + 7) / 128 | 0.125 | 아니오 |
| 개선 5, 회귀 0 | 2 × 1 / 32 | 0.0625 | 아니오 |

개선 5, 회귀 0도 결정적이지 않습니다. 움직인 문항이 적으면 어떤 결과도 우연과 구별되지 않습니다.

### 8.4 이론: 적응적 분석과 holdout

같은 평가 셋을 보며 고치고, 다시 재고, 또 고치면 그 셋에 **과적합**합니다. 평가 셋 점수는 오르는데 새 질문에서는
안 나아지는 상태입니다. Dwork et al.(2015)은 데이터를 본 뒤 분석을 고르는 "적응적 분석"에서 holdout을 반복해
쓰는 순간 그 holdout도 편향된다는 것을 보였습니다.

- 질문의 약 35%를 holdout으로 떼어, 첫 수정 전에 한 번 재고 그 뒤로 고치는 데 쓰지 않습니다. 수리는 dev에만.
- "dev는 오르는데 holdout이 안 움직이면 멈춘다."
- 분할은 질문 id의 해시(FNV-1a + MurmurHash3 finalizer)로 정해, 실행·순서·머신이 바뀌어도 질문이 분할 사이를
  옮겨 다니지 않습니다.

### 8.5 이론: 누수(leakage)

Kaufman et al.(2012)이 정리한 데이터 마이닝의 대표 실수입니다. 예측 시점에 쓸 수 없는 정답 정보가 학습에 섞이는
것. 여기서는 질문 문구를 노트의 별칭에 복사하는 것이 그렇습니다. 그 질문은 반드시 맞지만 아무것도 잰 게 아닙니다.
추가하는 어휘는 원문에서만 가져오고, 원문에서 찾을 수 없는 용어는 "노트나 소스가 빠졌다"는 신호로 읽습니다.
