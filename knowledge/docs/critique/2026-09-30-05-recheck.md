# Devil's Advocate — 재검증: "스킬 완성도 우선순위 1→5"

작성 2026-09-30, 대상 v1.19.1. 대상은 플러그인이 아니라 **직전 제안**이다:
1 생애주기 닫기(stale·큐) → 2 첫 결과 비용 축소(최소 경로) → 3 소스에 없는 지식 우선 → 4 스킬 설명과 코드 정합 → 5 측정은 뒤로(CI만).

```
Position:   "증명 연구 대신 사용자가 체감하는 스킬 완성도를 1→5 순서로 올린다"
Steel-man:  비판 5건 중 사용자 경험에 닿는 것만 골랐고, 이미 실측된 결함(큐 616줄 방치, 노트 정정 커밋)부터
            고치므로 증명을 기다리지 않고도 확실히 나아진다.
```

## 숨은 가정
1. "완성도"가 무엇인지 정의하지 않아도 비판 목록에서 고르면 된다.
2. 1번(소스 해시 stale 검출)과 3번(소스에 없는 지식 우선)이 같은 방향을 향한다.
3. 게이트를 건너뛰는 최소 경로를 넣어도 플러그인의 논지(answerability)는 유지된다.

## 반론 1: 1번과 3번이 서로를 무효화한다 · structural · severity: critical
stale 검출은 노트의 `sources:`(knowledge-base-builder/SKILL.md:117, 파일 경로) 해시를 비교한다. 그런데 3번이
우선하라는 결정 이유, 운영자 용어, 폐기된 선택지, 모듈 간 대조는 **해시할 소스 파일이 없거나 여러 개에 흩어진**
지식이다. 1번은 3번이 뒤로 미룬 코드 요약 노트만 지키고, 3번이 앞세운 노트는 무방비로 둔다. 3번이 성공할수록
1번의 적용 범위는 줄어든다.
선례: no clear precedent — speculative concern (다만 "측정 가능한 것만 관리된다"는 McNamara fallacy와 같은 모양).

## 반론 2: 최소 경로는 원칙을 비용 때문에 빼는 일이다 · assumption · severity: high
README 개념 1은 "답할 수 있어야 끝난다"이고, 컴피턴시 질문이 완료 게이트다. 질문 없이 바로 질의되는 최소 경로는
그 게이트를 우회한다. CLAUDE.md는 "비용이나 단순함을 이유로 stage·gate·principle을 제거하지 말 것(승인 없이)"이라고
못박고 있고, ROADMAP은 새 스킬을 동결했다. 최소 경로가 인기를 얻으면 게이트 있는 경로는 아무도 안 쓰는 고급 옵션이 된다.
선례: 안전장치를 opt-in으로 바꾸면 기본값을 아무도 바꾸지 않는다 — 기본값 효과(default effect), 잘 알려진 패턴.

## 반론 3: 이 저장소 기준의 "완성도"는 이미 정의돼 있는데 안 봤다 · execution · severity: high
CLAUDE.md 스킬 작성 규칙: 모든 스킬은 Process → Output Template → What Claude Does / What You Do → Related Skills.
실측(각 SKILL.md의 `## Output Template|What Claude Does|Related` 헤더 수): knowledge 8개 중 **6개가 3개 섹션 중 1개만** 있다
(knowledge-graph-builder, knowledge-query, ontology-builder, rag-corpus-builder, render-graph-view, sqlite-index-builder).
"70% 길이" 목표 대비 knowledge-base-builder 247줄. 저장소가 스스로 정한 완성도 기준에서 가장 싸고 확실한 결함을
제안이 한 줄도 다루지 않았다.
선례: 저장소 자체 — 다른 플러그인들은 이 템플릿으로 정리되어 있다(writing-skills 규칙).

## 반론 4 (5번에 대한 것): 측정을 빼면 "나아졌다"를 말할 수 없다 · assumption · severity: medium
이 플러그인의 역사에서 측정 없이 넣은 개선(어휘 작업 3회)은 효과 0이었다(ROADMAP). 1~4번의 완료 기준이
"규칙이 문서에 들어갔다"뿐이면, 완성도가 올랐는지는 여전히 느낌이다. 무거운 벤치마크는 아니어도 스킬별로
하나의 관찰 가능한 합격선은 필요하다.
선례: 저장소 자체 기록(ROADMAP "코퍼스/어휘 작업 0 (3회 시도)").

## 핵심 취약점
**"완성도"를 정의하지 않은 채 비판 목록에서 우선순위를 골랐다.** 그래서 1번과 3번이 서로 부딪히는 것을 못 봤고
(무엇을 지키는 게 완성인지 몰라서), 게이트를 빼는 2번을 개선으로 착각했고(원칙이 완성도의 일부라는 걸 놓쳐서),
저장소가 이미 정해둔 기준(템플릿)을 지나쳤다. 앞선 계획이 "필요한가"로 흘렀던 것과 같은 실수를 반대 방향으로 반복했다.

## 가역성
reversible — 문서·스킬 규칙 수준. 단 2번(최소 경로)은 사용자가 익숙해지면 되돌리기 어렵다. 2번만 one-way door에 가깝다.

## 개선 경로
- **먼저 완성도를 3층으로 정의한다.** (a) 저장소 규칙 준수 — 템플릿 4섹션, `Use when`, EN/KR 시나리오, 길이.
  (b) 생애주기 — 만들기·질의·갱신이 스킬 안에서 닫힌다. (c) 원칙 보존 — answerability 게이트를 빼지 않는다.
- **반론 3 해소:** 6개 스킬에 빠진 Output Template / What Claude Does / Related를 채운다. 가장 싸고 확실한 1순위.
- **반론 1 해소:** stale 검출을 "소스 해시"만이 아니라 **`checked_at` + 재확인 주기**로도 정의한다. 소스 파일이 없는
  지식은 날짜로, 있는 지식은 해시로. 두 방식이 한 필드(`freshness`)로 보고되면 1번과 3번이 같은 방향을 향한다.
- **반론 2 해소:** 최소 경로를 버리고, 대신 **질문 3개로 시작하는 작은 게이트**를 둔다. 게이트는 남기고 문턱만 낮춘다.
- **반론 4 해소:** 각 항목에 관찰 가능한 합격선을 붙인다(예: 섹션 헤더 검사 통과, knowledge-chat stale 비율 수치화).
