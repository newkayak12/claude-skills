# Devil's Advocate — knowledge 플러그인 (페르소나: 유지보수자)

작성 2026-09-30, 대상 v1.19.1.

```
Position:   "이 플러그인을 물려받아 유지한다"
Steel-man:  의존성 0의 단일 Node 스크립트에 주석이 "왜"를 적고, 테스트 84개(45+15+4+20)와
            측정 기록이 있어 규칙마다 근거를 따라갈 수 있다.
```

## 숨은 가정
1. 튜닝 상수는 근거가 주석·커밋에 있으니 다음 사람이 안전하게 만질 수 있다.
2. 테스트가 통과하면 회귀가 잡힌다. 그리고 그 테스트는 누군가 돌린다.
3. 작성자가 계속 곁에 있어 "왜 이 값인가"를 물을 수 있다. (커밋 60건 전부 작성자 1명, `git log --format=%an`)

## 반론 1: 테스트는 있지만 돌리는 장치가 없고, 이 환경에선 가장 큰 파일이 통째로 죽는다 · execution · severity: high
`node --test scripts/*.test.mjs hooks/*.test.mjs`를 Node 22.12에서 돌리면 28개 중 1개 파일이 실패한다.
`sqlite-knowledge.test.mjs`가 `node:sqlite` 로드 오류(ERR_UNKNOWN_BUILTIN_MODULE)로 **테스트 45개가 하나도
실행되지 않는다.** 엔진 핵심 로직 전부가 이 파일에만 있다. 원인은 `sqlite-knowledge.mjs:19`의 동적 import가
실패를 삼켰다가 사용 시점에 던지는 구조라 "건너뜀"이 아니라 "파일 실패"로 나온다(skip 처리 없음). 더 근본적으로
저장소 CI(`.github/workflows/validate-plugins.yml`)에는 `node --test`가 없다. 테스트는 작성자 로컬에서만 돈다.
릴리스 게이트가 없으므로 16번의 1.x 패치가 무엇으로 검증됐는지 유지보수자는 확인할 방법이 없다.
선례: CI에 안 걸린 테스트는 곧 썩는다 — 보편적 실패 양상(테스트가 존재해도 실행되지 않아 조용히 깨짐).

## 반론 2: 상수는 측정마다 하나씩 쌓이고, 상수를 고정하는 테스트도 상수 사이의 관계를 설명하는 곳도 없다 · structural · severity: high
`sqlite-knowledge.mjs`의 최상위 상수만 27개, 그중 순위 결정에 직접 쓰이는 것: `RRF_K=60`(:39),
`RELATION_RRF_WEIGHT=0.35`(:1043), `RELATION_PARTICIPANT_WINDOW_SHARE=0.5`(:1056),
`RELATION_SOURCE_RANK_LIMIT=8`(:1063), `RELATION_PARTICIPANT_FLOOR=2`(:43), `COLUMN_RRF_WEIGHTS`
0.5/0.35/0.15(:977), 융합 가중치 0.7/0.3(:1251), `DEFAULT_HOLDOUT_RATIO=0.35`(:44),
`DECISIVE_P=0.05`(:1754), 한국어 조사 19개 목록(:909)과 어간 2자 하한(:915). 그리고 상호작용이 있다.
승격 점수는 `weights.lexical * RELATION_RRF_WEIGHT * relationRrf`(:1325~1330)로 lexical 가중치에 **결합**되어
있는데, 이는 "고정 보너스가 0.7/0.3에서 상위 lexical 히트를 넘었다"(:1325 주석)는 버그 하나를 막으려고 들어온
곱셈이다. 즉 상수 하나를 바꾸면 다른 상수의 의미가 바뀐다. 테스트는 이 값들을 참조하지 않는다
(`RELATION_*`, `fusionWeights`, `koreanForms` grep 결과 테스트 파일에서 0건). 동작 단위 테스트뿐이라 값을 0.35→0.5로
바꿔도 통과할 수 있고, 통과해도 WMS 볼트의 순위가 조용히 변한다. 주석은 "측정했다"고 말하지만(`Measured on a real
vault ... four comparison answers for three non-relational ones`, :1051 이하) 그 측정은 코드 옆이 아니라
커밋 메시지·ROADMAP에 있고, 재현 스크립트는 저장소에 없다. 유지보수자는 상수를 건드릴 근거도, 건드리지 않을
근거도 코드에서 못 얻는다.
선례: 튜닝 상수가 서로 얽힌 랭킹 코드가 아무도 못 건드리는 "마법 숫자 덩어리"가 되는 흔한 패턴(레거시 검색 랭커의 boost 누적).

## 반론 3: 2100줄 단일 파일에 6개 관심사가 있고, 버전 1.5→1.19가 사실상 한 달에 몰려 있다 · timing · severity: medium
`sqlite-knowledge.mjs` 하나에 인덱서, FTS/트라이그램 질의 파서, 융합·승격, 리랭커, eval·스윕·부호검정, MCP 서버
(`serveMcp` :2072, 도구 정의 :1931)가 들어 있고 함수는 74개다. `servers/knowledge-mcp.mjs`는 19줄짜리 래퍼일 뿐이라
"MCP 서버가 별도 파일"이라는 인상과 달리 MCP를 고치려면 이 거대 파일을 열어야 한다. 이 파일의 최근 변경 이력은
8월 31일과 9월 23~24일 두 번의 돌진에 집중돼 있고(`git log --format='%ad %s'`), 9월 23일 하루에만 fix 커밋 7건과
"correct overclaims"(1.18.0)가 들어갔다. 검증 없이 낸 주장을 다음 날 고치는 속도로 바뀌는 코드는 리뷰어가 따라가지
못한다. 스킬 8개(SKILL.md 1,253줄) + README 439 + KOR 421 + theory 473 + ROADMAP 164줄은 코드 규칙마다 서술이 중복되어
있어, 규칙 하나를 바꾸면 최소 코드·SKILL.md·README·KOR·theory 5곳을 손봐야 한다. `CLAUDE.md`의 "README와 KOR.md가
함께 움직인다"는 규칙은 사람의 기억에만 의존하고 검사기가 없다(validate-knowledge는 볼트용이지 문서 동기화용이 아니다).
선례: 단일 파일 "god module"에 기능이 몰리면 소유자 이탈 후 아무도 수정하지 못한다 — 흔한 유지보수 실패 양상.

## 핵심 취약점
**버스 팩터 1을 지탱하는 유일한 안전망(테스트)이 CI 밖에 있고, 그 테스트조차 튜닝 상수를 고정하지 않는다.**
근거는 작성자의 머릿속과 커밋 메시지에만 있어서, 작성자가 빠지는 순간 어떤 상수도 안전하게 바꿀 수 없다.
(기준 의견의 N=1 문제가 "믿을 수 있나"라면 이쪽은 "물려받아 고칠 수 있나"다.)

## 가역성
partially reversible — 코드는 되돌릴 수 있지만 `SCHEMA_VERSION='5'`(:38)로 인덱스 재구축이 필요하고, 사용자 볼트의
`.knowledge/`와 저장된 eval baseline은 `BASELINE_MUST_MATCH`(:1584)로 조건이 달라지면 비교를 거부한다. 상수를 바꾸면
과거 측정이 전부 incomparable이 된다.

## 개선 경로
1. (반론 1) CI에 `node --test`를 추가하되 `node:sqlite` 부재 시 파일 전체 실패가 아니라 skip(`test.skip`/사전 검사)으로
   처리하고, Node 24 잡을 하나 둔다. 릴리스가 CI 통과에 묶이면 해소된다.
2. (반론 2) 상수를 한 모듈(`tuning.mjs`)로 모으고, 각 상수 옆에 "이 값을 바꾸면 깨져야 하는 테스트 1개"와 근거 측정
   링크를 둔다. 상수를 ±로 흔들어 eval 지표가 어떻게 변하는지 스윕 표가 있으면 "값이 선택된 것"임이 증명된다.
3. (반론 3) 파일을 `index / query / eval / mcp`로 나누고, 문서는 규칙 원문 1곳 + 나머지는 링크로 줄인다.
   README/KOR 섹션 헤더·핵심 문장 동기화 검사기를 CI에 넣는다. 작성자 외 1인이 한 번이라도 릴리스를 내 보면 버스 팩터가
   실측된다.
