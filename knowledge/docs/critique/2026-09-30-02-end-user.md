# Devil's Advocate — knowledge 플러그인 (페르소나: 실사용자 팀 리드)

작성 2026-09-30, 대상 v1.19.1. 근거: README, KOR, ROADMAP, skills/*/SKILL.md, hooks/, .mcp.json, compose.yaml, Dockerfile. 기준 의견(`2026-09-30-00-baseline.md`)의 N=1 코퍼스, 자작 질문, 94문항 재실행 대기, 소스 드리프트는 반복하지 않는다.

```
Position:   "우리 백엔드 저장소에 knowledge 플러그인을 깔아 온보딩 문서와 영향 분석용 볼트를 만든다"
Steel-man:  한 번 잘 만들어 두면 신입도 화면 이름이든 매퍼 id든 같은 노트에 닿고, 답마다 근거와
            coverage 등급이 붙어서 "그럴듯한 오답"을 걸러내는 팀 지식 자산이 된다.
```

## 숨은 가정
1. 볼트를 만드는 데 드는 시간·토큰이 팀 리드가 한 번 치를 만한 크기다.
2. 팀원이 자기 Claude Code 세션에서 이 볼트를 grep보다 먼저 찾아 쓴다.
3. 볼트를 "만드는 일"과 "유지하는 일"의 비용을 같은 사람이 같은 도구로 감당할 수 있다.

## 반론 1: 첫 산출물까지 가는 길이 "설치"가 아니라 "프로젝트"다 · execution · severity: high
`knowledge-workflow` 프런트매터가 스스로 `estimated_time: "2-6 hours (first build), 20-40 minutes per
repair round"`를 적는다. 토큰 비용 추정은 어디에도 없다(README, SKILL 전체에 cost/token 견적 없음).
빌드는 catalog → graph → RAG → index 4단계이고(knowledge-workflow Phase A), 그 앞에 사용자가 질문을 직접
공급해야 한다: "Competency questions ... are a **precondition for Phase B**"이고 표의 "What You Do"에도
"Supplies the competency questions"가 있다. 처음 설치한 리드는 노트 한 장 보기 전에 질문 세트 설계라는
숙제부터 받는다. 게다가 README는 진입점을 `knowledge-workflow` 항목 두 개로 중복 서술하고(Skills 절,
"The entry point"와 "Entry point for a full build"), 총 8개 스킬, 9개 핵심 개념(각각 논문 인용)을 깐다.
온보딩 문서가 필요한 사람에게 "onboarding doc 3장"이라는 가장 짧은 경로가 없다.
`sqlite-index-builder`는 Node 24+(또는 22.5-23에 `--experimental-sqlite`과 FTS5 빌드)를 요구하고
(sqlite-index-builder SKILL, 인덱서 요건), 의미 검색은 Ollama와 모델을 "이미 있어야" 하며 스킬이 설치해
주지도 않는다("Do not silently install Ollama"). 리랭커도 "Never install or start one"(knowledge-query 6항).
즉 품질을 올리는 레버는 전부 사용자가 직접 띄울 인프라다.
선례: 사내 위키·RAG 도입 프로젝트가 "구축 비용은 큰데 첫 결과물이 늦어" 후원자를 잃는 흔한 패턴 — 정형 사례 인용은 하지 않고 no clear precedent — speculative concern.

## 반론 2: 2주차에 코드가 바뀌면 볼트를 갱신하는 도구가 없다 · structural · severity: critical
훅은 `PostToolUse`에서 `Write|Edit|MultiEdit|NotebookEdit`만 보고, 그중 **`.md` 파일이 지식 워크스페이스
안에 있을 때만** 동작한다(hooks.json, knowledge-delta-check.mjs의 `.endsWith('.md')`, `findKnowledgeRoot`).
즉 팀원이 `OrderService.java`를 고쳐도 아무 일도 일어나지 않는다. 훅이 하는 일은 노트를 고친 뒤
`catalog-delta-queue.jsonl` 등에 **큐 줄을 append**하는 것뿐이고, 그 큐를 비우는 소비자는 훅에도 스킬에도
없다(큐 파일 이름만 있고 처리 스킬은 README·SKILL에서 확인되지 않음). `knowledge-base-builder`에는 소스
변경분만 재추출하는 증분 절차가 없다. 남는 건 "meaningful build or update work" 뒤에 `improvement-notes.md`를
쓰라는 문장뿐이다. 리드 입장에서 2주차는 이렇다: 스프린트에서 PR 20개가 머지되고, 볼트는 그대로이며,
누가 언제 어느 노트가 낡았는지 알 방법이 없고, 재빌드는 2–6시간짜리 프로젝트를 반복하는 것이다.
(기준 의견 반론 4가 "eval이 드리프트를 못 본다"였다면, 이건 그보다 앞선 문제다: 갱신을 **일으킬 트리거와
실행 경로 자체가 없다**.) 팀 스프린트 속도로 바뀌는 저장소에서 스냅샷 볼트는 첫 달에 신뢰 손실이 시작된다.
선례: 손으로 유지하는 위키/ADR이 코드와 어긋나며 방치되는 documentation rot.

## 반론 3: grep과 CLAUDE.md만 쓰는 기준선보다 낫다는 증거가 사용자에게 제시된 적이 없다 · assumption · severity: high
README의 실측은 전부 "볼트 내부" 비교다: 답변 모델 두 개끼리(94문항), 검색 설정끼리. 리드가 묻는 비교 —
"같은 저장소에 그냥 Claude Code에게 grep으로 물어본 것" 대비 정확도, 시간, 토큰 — 는 어디에도 없다.
플러그인이 자기 수치로 인정하는 것도 불리하다: 로컬 모델은 94문항 중 29개를 노트를 하나도 열지 않고
답했고, `complete`라 선언한 69–80건 중 실제 완전 답은 22–38건이었다(README 핵심 개념 8, knowledge-query 절).
다시 말해 볼트를 만든 뒤에도 답변 품질은 "열어본 노트 수를 강제하는 스킬 지침"에 기대고, 그 지침을 안
따르는 세션(팀원이 스킬 없이 그냥 질문)은 플러그인이 측정한 대로 오답을 자신 있게 내놓는다. 팀원이
`knowledge-query`를 부르지 않고 평소처럼 물으면 MCP `knowledge_search`가 있어도 coverage 등급 규율이
적용되지 않는다. 그리고 `.mcp.json`은 `--root ${CLAUDE_PROJECT_DIR}`로 프로젝트 루트를 잡으므로, 볼트가
`knowledge-system/`에 있을 때 팀원 각자가 인덱스를 자기 머신에서 만들어야 하는지, `.knowledge/knowledge.sqlite`가
"disposable local state — Markdown and JSONL stay in Git"(README sqlite 절)이라 매 클론마다 재색인인지가
팀 관점의 미해결 문제다. "다른 팀원이 쓰게 만드는 절차"는 문서에 없다.
선례: 사내 검색/지식 도구가 "기본 도구(grep, IDE 검색)보다 나은지" 입증 없이 배포돼 채택률이 낮은 패턴 — no clear precedent — speculative concern.

## 핵심 취약점
**볼트는 "한 번 만드는 프로젝트"로 설계됐고, 팀이 매주 쓰는 "유지되는 자산"으로는 설계되지 않았다.**
소스 코드 변경을 감지·반영하는 경로가 없고(훅은 `.md`만), 반영 비용의 단위가 시간 단위(2–6시간)이며,
품질 레버는 사용자 직접 인프라(Ollama, 리랭커, Node 24)다. 8개 스킬과 9개 개념의 정교함은 빌더의 입장에서
합리적이지만, 팀 리드에게 그 정교함은 학습 비용이자 유지 비용이다.

## 가역성
reversible — 설치·제거 명령이 한 줄이고 볼트는 Git의 Markdown이라 지워도 저장소를 해치지 않는다.
다만 실질 비용은 되돌릴 수 없다: 처음 빌드에 쓴 시간과 팀 신뢰. "볼트가 낡아 틀린 답을 낸다"는 경험이
한 번 팀에 퍼지면 도구가 아니라 방식 전체가 기각된다.

## 개선 경로
- **반론 2 (critical)** 가 풀리려면: 소스 파일 변경(또는 `git diff` 기준)을 받아 영향받는 노트 id를 `source_ref`로
  찾아 재추출 대상으로 표시하고, 큐를 실제로 소비하는 "refresh" 경로(스킬 한 개 또는 CI 잡)가 있으며, 한
  스프린트분 변경을 반영하는 데 분 단위가 걸려야 한다. 그리고 `status`가 "낡은 노트 N개"를 보고해야 한다.
- **반론 1 (high)** 이 풀리려면: "질문 세트 없이" 30분 안에 결과가 나오는 최소 경로(온보딩 개요 + 진입점
  MOC 정도)가 있고, 시간·토큰 견적이 README 첫 화면에 실측으로 적혀 있으며, Ollama/리랭커 없이도 기본값에서
  충분하다는 수치가 있어야 한다.
- **반론 3 (high)** 이 풀리려면: 같은 저장소·같은 질문을 "볼트+스킬" 대 "grep만"으로 돌린 정확도·토큰·시간
  비교 한 표가 README에 있고, 스킬을 안 부르는 팀원 세션에도 coverage 규율이 걸리도록(MCP 응답이나 CLAUDE.md
  스니펫으로) 기본 배선이 있어야 한다.
