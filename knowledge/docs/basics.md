# 검색 기초 — 이 엔진이 노트를 찾는 방법

`knowledge`의 검색(`sqlite-knowledge.mjs`, `knowledge_search`)을 처음 보는 사람을 위한 설명입니다. 용어마다
**무엇인지 → 숫자로 보면 → 이 엔진에서는** 순서로 씁니다. 논문 출처와 이론에서 벗어난 지점은
[theory.md](theory.md) §4–5에 있습니다. 기준 버전은 1.23.0입니다.

---

## 0. 한 장 요약

```
질문 ─┬─ 어휘 검색 (FTS5 + BM25) ── 제목 / 별칭 / 본문 순위 ──┐
      │    + trigram · 한글 접두어                              ├─ RRF 융합 ─ (리랭커) ─ 결과 창 (노트당 1개)
      └─ 의미 검색 (임베딩, 코사인 유사도) ── 의미 순위 ────────┘        └ relation 참여자는 창 끝에 추가
```

- 어휘 검색은 **같은 단어**를 찾고, 의미 검색은 **같은 뜻**을 찾습니다.
- 두 순위를 점수가 아니라 **순위로** 합칩니다(RRF).
- 측정은 recall@k와 MRR로 합니다.

---

## 1. 어휘 검색 — 단어가 겹치는가

### 1.1 역색인 (inverted index)

- **무엇:** 책 뒤의 찾아보기와 같습니다. "단어 → 그 단어가 나오는 노트 목록"을 미리 만들어 두면, 질문의
  단어마다 목록을 꺼내기만 하면 됩니다. 노트를 하나씩 다 읽지 않습니다.
- **이 엔진:** SQLite의 전문 검색 확장 **FTS5**가 역색인을 만들고 관리합니다.

### 1.2 BM25 — 겹친 단어에 점수 매기기

단어가 겹치는 노트가 여러 개면 순서를 정해야 합니다. BM25는 세 가지를 봅니다.

| 요소 | 뜻 | 직관 |
|---|---|---|
| **IDF** (드문 정도) | 그 단어가 나오는 노트가 적을수록 큼 | "재고"는 어디에나 있고 "수불부"는 드물다 → "수불부"가 맞은 쪽이 더 관련 있다 |
| **TF** (반복 횟수) | 노트 안에 그 단어가 많을수록 큼, 단 **포화**함 | 10번 나온다고 1번보다 10배 관련 있지는 않다 |
| **길이 보정** | 평균보다 긴 노트는 깎음 | 긴 노트는 아무 단어나 우연히 들어 있을 확률이 높다 |

한 단어의 점수는 다음과 같습니다. 질문의 단어마다 구해서 더합니다.

```
점수 = IDF × tf·(k1+1) / ( tf + k1·(1 − b + b·노트길이/평균길이) )
IDF  = ln( (N − n + 0.5)/(n + 0.5) + 1 )      N: 전체 노트 수, n: 그 단어가 나오는 노트 수
k1 = 1.2, b = 0.75 (FTS5 기본값)
```

**숫자로 보면** (노트 100개 볼트)

| 단어 | 나오는 노트 수 n | IDF |
|---|---|---|
| 재고 | 40 | 0.91 |
| 수불부 | 2 | 3.70 |

드문 "수불부" 한 번이 흔한 "재고" 한 번보다 약 4배 무겁습니다.

| 같은 노트 안 반복 (평균 길이 노트) | TF 부분 |
|---|---|
| 1번 | 1.00 |
| 2번 | 1.38 |
| 10번 | 1.96 |

10번 나와도 2배를 넘지 못합니다(포화). 같은 1번이라도 노트가 평균의 2배 길이면 0.71로 줄어듭니다.

**이 엔진:** BM25를 노트 전체에 한 번 돌리지 않고 **컬럼마다** 따로 돌립니다 — `title`, `terms`(별칭·사용자 용어·
소스 기호), `body`. 세 순위를 RRF(§3)로 합치므로, 제목이나 별칭에서 맞은 노트가 본문에서 한 번 스친 노트를
노트 길이와 상관없이 이깁니다.

### 1.3 토크나이저와 한국어

- **무엇:** 역색인에 넣기 전에 글을 "단어"로 자르는 규칙입니다. 영어는 띄어쓰기로 충분하지만, 한국어는
  "재시도한", "재고를"처럼 조사·어미가 붙어 띄어쓰기 단위가 곧 단어가 아닙니다.
- **이 엔진:** 세 가지를 겹쳐 씁니다.

| 방법 | 하는 일 | 예 |
|---|---|---|
| `unicode61` (정확 토큰) | 띄어쓰기 단위로 정확히 일치 | "재시도" ↔ "재시도" |
| `trigram` (3글자 조각) | 3글자씩 잘라 부분 문자열 일치 | "재시도" → "재시도한"에서도 찾음 |
| 한글 접두어 + 조사 떼기 | 2음절 명사는 trigram이 못 잡으므로 앞부분 일치, 끝 조사를 뗀 형태도 함께 | "재고" → "재고가", "재고를" → "재고" |

정확 토큰과 trigram 순위는 `0.7 / 0.3` 가중 RRF로 하나의 어휘 순위가 됩니다. 조사 목록은 한 곳에서만
관리합니다(capture와 색인이 같은 목록을 씀).

## 2. 의미 검색 — 뜻이 가까운가

### 2.1 임베딩

- **무엇:** 글을 수백 개 숫자의 목록(벡터)으로 바꾸는 모델입니다. 뜻이 비슷한 글은 비슷한 벡터가 되도록
  학습되어 있어서, "출고가 늦다"와 "배송 지연"처럼 단어가 하나도 안 겹쳐도 가깝게 나옵니다.
- **어휘 검색이 못 하는 것:** 사용자가 노트와 다른 말로 물을 때(바꿔 말하기). 실제 볼트에서 기본 `hash`를
  의미 모델(`embeddinggemma`)로 바꾸자 recall@10이 0.631 → 0.803으로 올랐습니다. 엔진을 6번 고친 것보다 큰
  차이였습니다.

### 2.2 코사인 유사도

- **무엇:** 두 벡터가 같은 방향을 보는 정도입니다. 1이면 같은 방향, 0이면 무관.
- **숫자로 보면:** 2차원으로 줄인 장난감 예시 — 질문 (1, 1), 노트 A (2, 2), 노트 B (1, −1).
  A는 길이만 다르고 방향이 같아서 1.0, B는 직각이라 0입니다. 길이(글 분량)가 아니라 방향(뜻)만 봅니다.

### 2.3 질문과 문서를 다르게 넣는 모델 (비대칭)

- **무엇:** 검색용으로 학습된 모델은 짧은 질문과 긴 문서를 다르게 다루도록 앞에 표시를 붙여 학습되어 있습니다.
  같은 표시를 붙여야 학습된 대로 동작합니다.
- **이 엔진:**

| 모델 | 질문 앞 | 문서 앞 | 한 번에 넣는 길이 |
|---|---|---|---|
| E5 (`intfloat/multilingual-e5-base`, TEI·OpenAI 호환 서버) | `query: ` | `passage: ` | 460자 |
| `embeddinggemma` (Ollama) | `task: search result \| query: ` | `title: … \| text: ` | 1800자 |
| 모르는 모델 | 없음 | 없음 | 제한 없음 |

  어떤 표시를 썼는지 색인에 기록하고, 질문도 그 색인과 같은 방식으로만 붙입니다.

### 2.4 긴 노트 — 겹치는 윈도

- **무엇:** 모델은 한 번에 읽는 길이가 정해져 있습니다(E5는 512토큰). 넘치면 앞부분만 보고 나머지는
  의미 검색에서 안 보입니다.
- **이 엔진:** 긴 노트를 서로 조금씩 겹치게 잘라 각각 임베딩한 뒤 평균을 내어 벡터 하나로 만듭니다.
  겹치게 자르는 건 경계에 걸친 문장이 어느 한 조각에는 온전히 들어가게 하려는 것입니다. 노트는 여전히
  결과 하나로 나옵니다.

### 2.5 기본값 `hash`는 의미 검색이 아니다

- 설치만 하고 아무 모델도 연결하지 않으면 `hash` 임베딩이 쓰입니다. 단어를 해시해 숫자로 바꾼 것이라
  사실상 어휘 검색입니다. 결과에 `embedding_quality: lexical-baseline`이 찍힙니다.
- 임베딩 서버가 꺼져 있으면 질문을 임베딩하지 못하므로 어휘만으로 답하고, `query_embedding.applied: false`와
  가중 `0 / 1`로 그 사실을 알립니다.

### 2.6 임베딩에서 꼭 알아야 할 것

| # | 알아야 할 것 | 왜 | 이 엔진에서 |
|---|---|---|---|
| 1 | **색인과 질문은 같은 모델로** | 모델마다 숫자 공간이 달라서, A 모델로 만든 노트 벡터와 B 모델의 질문 벡터는 비교해도 의미가 없음 | 모델·접두어를 색인 메타데이터에 기록. 모델을 바꾸면 **전체 재색인** |
| 2 | **차원 수** | 벡터 길이(E5-base 768, 큰 모델 1024 이상). 길수록 표현력은 크지만 저장·계산이 늘고, 같은 차원끼리만 비교 가능 | 색인에 차원이 고정됨 → 1번과 같은 이유로 재색인 |
| 3 | **정규화** | 길이를 1로 맞추면 코사인 유사도 = 내적이 되어 계산이 빠름. 서버마다 정규화 여부가 다름 | 비교는 코사인으로 해서 정규화 여부에 흔들리지 않음 |
| 4 | **토큰 한도** | 모델이 한 번에 읽는 길이(E5 512토큰). 넘친 부분은 조용히 잘려 사라짐 — 에러가 안 남 | 겹치는 윈도로 나눠 평균(§2.4). 노트 자체를 짧게 쪼개는 게 우선(`rag-corpus-builder` 청크 규칙) |
| 5 | **접두어(프롬프트)** | `query:` / `passage:` 같은 표시를 빼면 성능이 눈에 띄게 떨어지는 모델이 있음 | 아는 모델만 자동으로 붙이고, 모르는 모델엔 추측해서 붙이지 않음(§2.3) |
| 6 | **다국어** | 영어 전용 모델은 한국어를 잘게 쪼개 뜻을 놓침 | 한국어 볼트는 다국어 모델(`multilingual-e5-base`) |
| 7 | **임베딩은 정확한 단어에 약함** | 뜻이 비슷한 글을 모으는 대신, 코드명·화면 라벨·숫자 같은 정확한 일치는 흐려짐 | 그래서 어휘 검색(BM25)과 **함께** 쓰고 RRF로 합침(§3) |
| 8 | **많아지면 근사 검색(ANN)** | 노트 수만 개를 넘으면 모든 벡터와 비교(전수)가 느려짐. HNSW 같은 색인은 아주 조금 놓치는 대신 빠름 | 기본 SQLite는 전수 비교. 커지면 `status`가 크기를 알려 주고, pgvector 백엔드로 옮김(`migrate`) |
| 9 | **좋아졌는지는 재 봐야 안다** | 모델·청크·가중을 바꾸면 어떤 질문은 좋아지고 어떤 질문은 나빠짐 | `eval`로 recall@k·MRR과 질문별 증감을 확인(§6) |

## 3. 두 순위 합치기 — RRF

- **무엇:** BM25 점수와 코사인 유사도는 단위가 달라서 그냥 더할 수 없습니다. Reciprocal Rank Fusion은 점수를
  버리고 **순위만** 씁니다.

```
RRF 점수(노트) = Σ 가중치 / (60 + 순위)          순위는 1부터
```

- **숫자로 보면** (의미 0.7 / 어휘 0.3, 이 엔진의 기본 출발점)

| 노트 | 어휘 순위 | 의미 순위 | RRF 점수 |
|---|---|---|---|
| A | 1 | 5 | 0.3/61 + 0.7/65 = 0.01569 |
| B | 10 | 1 | 0.3/70 + 0.7/61 = 0.01576 |
| C | 2 | 없음 | 0.3/62 = 0.00484 |

  B가 A를 근소하게 이깁니다. 한쪽에서만 나온 C는 크게 밀립니다. 60이라는 상수 때문에 1위와 5위의 차이가
  극단적이지 않아서, 한쪽 목록이 다른 쪽을 혼자 뒤집지 못합니다.
- **이 엔진:** RRF를 세 번 씁니다 — 컬럼(제목·별칭·본문), 정확 토큰과 trigram, 어휘와 의미.
  `0.7 / 0.3`은 측정해서 정한 값이 아니라 **출발점**입니다. 화면 라벨을 그대로 묻는 질문은 어휘 쪽이,
  바꿔 말한 질문은 의미 쪽이 이깁니다. `eval --sweep 0.3,0.4,0.5`로 볼트마다 확인합니다.

## 4. 리랭커 — 후보를 다시 읽기

- **무엇:** 임베딩은 질문과 노트를 **따로** 숫자로 바꿔 비교합니다(바이인코더). 리랭커(크로스인코더)는
  질문과 노트를 **함께** 읽고 관련도를 매깁니다. 더 정확하지만 느려서, 상위 50개 정도만 다시 정렬합니다.
- **한계:** 이미 후보에 든 것만 순서를 바꿀 수 있습니다. 그래서 얻을 수 있는 최대치는 미리 잴 수 있습니다:
  **recall@50 − recall@10**. 이 값이 작으면 리랭커를 붙여도 얻을 게 없습니다.
- **이 엔진:** `--reranker-url` / `--reranker-model`로 붙이는 선택 사항입니다. 실패하면 융합 순서로 돌아가고
  `rerank_error`를 남깁니다.

## 5. 이 엔진만의 규칙 두 가지

- **노트당 결과 하나:** 한 노트가 청크 여러 개로 나뉘어도 기본으로 노트 하나로 묶습니다. 청크가 많은 노트가
  상위 k를 독차지하지 못하게 합니다.
- **relation 참여자 추가:** "A와 B의 차이"를 물으면 대조 노트(relation)가 1위로 오지만, 답에는 A와 B 각각의
  근거도 필요합니다. 그래서 relation 노트가 상위에 오면 선언된 참여자를 결과 창의 **끝**에 붙입니다.
  위로 올리지 않는 이유: 올렸더니 비교 질문은 좋아졌지만 다른 질문 5개의 정답이 밀려났습니다.

## 6. 잘 찾는지 재는 법

질문마다 "이 노트가 나와야 한다"는 정답을 정해 두고(`questions.jsonl`의 `required_note_ids`), 검색 결과와 비교합니다.

| 지표 | 뜻 | 예 (정답 노트 1개) |
|---|---|---|
| **recall@k** | 정답이 상위 k개 안에 들었는가 (질문들의 평균) | 3위에 나옴 → recall@10 = 1, recall@1 = 0 |
| **MRR** | 정답이 처음 나온 순위의 역수 평균 | 1위 → 1.0, 2위 → 0.5, 3위 → 0.33, 안 나옴 → 0 |

- recall은 "찾았나", MRR은 "얼마나 위에서 찾았나"입니다.
- **holdout:** 고칠 때 쓴 질문으로만 재면 그 질문들에 맞춰질 뿐입니다. 고칠 때 보지 않은 질문 묶음으로 다시
  확인합니다.
- **누수 주의:** 질문을 노트 문장에서 베껴 쓰면 어휘 검색이 실제보다 좋아 보입니다. 사용자가 실제로 할 말로 씁니다.
- 한 번에 하나만 바꾸고, 나빠지면 되돌립니다(`eval`이 질문별로 좋아진 것·나빠진 것을 보여 줌).

|---|---|---|
| **질의, 쿼리** (query) | 검색창에 넣는 질문이나 단어 | "재고 수불부와 현황표 차이" |
| **문서, 노트** (document) | 검색해서 돌려받는 단위. 이 엔진에서는 볼트의 노트 하나 | `notes/wms/inventory-ledger.md` |
| **코퍼스** (corpus) | 검색 대상 문서 전체 | 볼트의 노트 전부 |
| **색인, 인덱스** (index) | 빨리 찾으려고 미리 만들어 둔 자료 구조. 책 뒤의 찾아보기 | `_knowledge/` 아래 SQLite 파일 |
| **역색인** (inverted index) | "단어 → 그 단어가 나오는 문서 목록" 형태의 색인 | FTS5가 만듦 |
| **청크** (chunk) | 긴 문서를 검색 단위로 자른 조각 | 섹션 단위로 자름. 결과는 노트당 하나로 묶음 |
| **순위** (rank) | 결과 목록에서 몇 번째인가. 1위가 가장 관련 있음 | |
| **상위 k** (top-k) | 결과 앞쪽 k개. 사람이나 LLM이 실제로 읽는 범위 | 보통 k = 10 |
| **결과 창** (result window) | 돌려주는 상위 k개 자리 | relation 참여자는 이 창의 끝자리에 붙음 |
| **하이브리드 검색** (hybrid search) | 어휘 검색과 의미 검색을 함께 쓰고 합치는 방식 | 이 엔진의 기본 방식 |

### 7.2 어휘 검색

| 용어 | 뜻 | 예 / 이 엔진에서 |
|---|---|---|
| **어휘 검색** (lexical search) | 같은 **글자·단어**가 있는지로 찾음 | "재고" → "재고"가 들어간 노트 |
| **전문 검색** (full-text search) | 본문 전체를 대상으로 하는 어휘 검색 | |
| **FTS5** | SQLite에 내장된 전문 검색 기능. 역색인과 BM25를 제공 | 별도 서버 없이 파일 하나로 동작 |
| **토큰** (token) | 색인이나 모델이 다루는 글의 최소 단위. 어휘 검색에서는 "단어", 모델에서는 단어 조각 | "재시도한" → 토크나이저에 따라 한 토큰 또는 여러 조각 |
| **토크나이저** (tokenizer) | 글을 토큰으로 자르는 규칙 | `unicode61`, `trigram` |
| **trigram** | 글을 3글자씩 겹쳐 자른 조각. 형태소 분석 없이 부분 일치를 찾음 | "재시도한" → 재시도·시도한 |
| **접두어 일치** (prefix match) | 단어의 앞부분이 같으면 일치로 봄 | "재고*" → 재고가·재고를 |
| **조사 떼기** | "재고를"에서 "를"을 떼어 "재고"로도 찾음. 원형 옆에 **추가**하지, 바꾸지 않음 | "재시도"의 "도"처럼 조사처럼 보이는 글자가 있어서 |
| **형태소 분석** | 단어를 의미 단위(어간·조사·어미)로 나누는 것 | 이 엔진은 쓰지 않음 (설치 없이 동작하도록) |
| **TF** (term frequency) | 한 문서 안에 그 단어가 나온 횟수 | |
| **DF / IDF** (document frequency / inverse DF) | 그 단어가 나오는 문서 수 / 그 역수 쪽 값. 드문 단어일수록 IDF가 큼 | "수불부" IDF 3.70, "재고" 0.91 (§1.2) |
| **TF-IDF** | TF × IDF. BM25의 단순한 조상 | |
| **BM25** | TF·IDF에 **포화**와 **길이 보정**을 더한 어휘 점수 | 컬럼별(제목·별칭·본문)로 계산 |
| **포화** (saturation) | 반복이 늘어도 점수가 일정 이상 오르지 않는 성질 | 10번 나와도 1번의 2배 미만 |
| **길이 보정** (length normalization) | 긴 문서의 점수를 깎는 것 | 평균의 2배 길이면 1.00 → 0.71 |
| **k1, b** | BM25의 조절값. k1은 포화 속도, b는 길이 보정 세기 | FTS5 기본 1.2, 0.75 |
| **BM25F** | 필드(제목·본문)별 가중을 점수 안에 섞는 BM25 확장 | 이 엔진은 대신 필드별 순위를 RRF로 합침 |

### 7.3 의미 검색과 임베딩

| 용어 | 뜻 | 예 / 이 엔진에서 |
|---|---|---|
| **의미 검색** (semantic search) | 단어가 달라도 **뜻**이 가까우면 찾음 | "출고 늦음" → "배송 지연" 노트 |
| **밀집 검색** (dense retrieval) | 임베딩 벡터로 하는 의미 검색. 대부분의 칸이 0이 아닌 벡터라서 "밀집" | |
| **희소 검색** (sparse retrieval) | BM25 같은 어휘 검색. 단어 수만큼 칸이 있고 대부분 0이라서 "희소" | |
| **벡터** (vector) | 숫자의 목록. 공간 위의 한 점이나 화살표로 생각하면 됨 | `[0.12, -0.03, …]` 768개 |
| **임베딩** (embedding) | 글을 벡터로 바꾼 것, 또는 그렇게 바꾸는 일 | |
| **임베딩 모델** | 글 → 벡터 변환을 학습한 모델 | E5, embeddinggemma |
| **차원** (dimension) | 벡터의 숫자 개수 | E5-base 768 |
| **정규화** (normalization) | 벡터 길이를 1로 맞추는 것 | 맞추면 코사인 = 내적 |
| **내적** (dot product) | 두 벡터의 칸끼리 곱해서 더한 값 | |
| **코사인 유사도** (cosine similarity) | 두 벡터의 방향이 같은 정도. 1 같음, 0 무관, −1 반대 | 이 엔진의 의미 점수 |
| **바이인코더** (bi-encoder) | 질문과 문서를 **따로** 벡터로 바꿔 비교. 문서 벡터를 미리 만들어 둘 수 있어 빠름 | 임베딩 검색이 이것 |
| **크로스인코더** (cross-encoder) | 질문과 문서를 **함께** 넣어 관련도를 바로 매김. 정확하지만 느림 | 리랭커가 이것 |
| **비대칭 검색** (asymmetric retrieval) | 짧은 질문으로 긴 문서를 찾는 상황. 모델이 둘을 다르게 다루도록 학습됨 | |
| **접두어, 프롬프트** (prefix, prompt) | 비대칭 모델에 "이건 질문/문서"라고 알리는 앞 표시 | E5 `query:` / `passage:` |
| **컨텍스트 길이, 토큰 한도** (context window) | 모델이 한 번에 읽는 최대 길이. 넘으면 잘림 | E5 512토큰 → 이 엔진 460자 |
| **윈도 + 평균 풀링** (window, mean pooling) | 긴 글을 겹치게 나눠 각각 임베딩하고 평균 내기 | §2.4 |
| **다국어 모델** (multilingual) | 여러 언어를 한 공간에 담도록 학습된 모델 | `multilingual-e5-base` |
| **특징 해싱** (feature hashing) | 단어를 해시해 정해진 칸에 넣어 벡터를 만드는 방법. 뜻은 모름 | 기본 `hash` provider |
| **provider** | 이 엔진에서 임베딩을 누가 만드는가 | `hash`, `ollama`, `openai` |

### 7.4 서버와 저장소

| 용어 | 뜻 | 예 / 이 엔진에서 |
|---|---|---|
| **Ollama** | 내 컴퓨터에서 모델을 띄우는 프로그램 | `--provider ollama --model embeddinggemma` |
| **TEI** (text-embeddings-inference) | 임베딩 모델 전용 서버 (Hugging Face) | `--provider openai`로 연결 |
| **OpenAI 호환** | OpenAI와 같은 주소·형식(`/v1/embeddings`)으로 답하는 서버 | TEI, vLLM, OpenAI 자체 |
| **SQLite** | 파일 하나짜리 데이터베이스 | 기본 저장소 |
| **PostgreSQL + pgvector** | 큰 데이터베이스와 그 벡터 확장 | 커지면 `migrate`로 이전 |
| **전수 비교** (brute force) | 질문 벡터를 모든 문서 벡터와 하나씩 비교. 정확하지만 많으면 느림 | SQLite 기본 |
| **ANN** (approximate nearest neighbor) | 아주 조금 놓치는 대신 훨씬 빨리 가까운 벡터를 찾는 방법 | |
| **HNSW** | 가장 널리 쓰는 ANN 색인 (그래프 모양) | pgvector가 만듦. 2000차원 초과면 못 만듦 |
| **재색인** (reindex, rebuild) | 색인을 처음부터 다시 만드는 것 | 모델·접두어를 바꾸면 필수 |

### 7.5 합치기와 재정렬

| 용어 | 뜻 | 예 / 이 엔진에서 |
|---|---|---|
| **융합** (fusion) | 여러 검색 결과 목록을 하나로 합치는 것 | |
| **RRF** (reciprocal rank fusion) | 순위만으로 합치는 방법. 점수 = Σ 가중치 / (60 + 순위) | §3 |
| **가중치** (weight) | 각 목록을 얼마나 믿을지 | 의미 0.7 / 어휘 0.3 |
| **리랭커** (reranker) | 후보 몇십 개를 크로스인코더로 다시 정렬하는 단계 | 선택 사항 (`--reranker-url`) |
| **천장** (ceiling) | 리랭커가 낼 수 있는 최대 이득 | recall@50 − recall@10 |
| **relation 노트** | 두 개념의 대조·동등·순서를 담은 노트. 참여자(participants)를 선언함 | "수불부 vs 현황표" |
| **승격** (promotion) | relation 노트가 상위에 오면 그 참여자를 결과 창 끝에 붙이는 규칙 | §5 |

### 7.6 평가

| 용어 | 뜻 | 예 / 이 엔진에서 |
|---|---|---|
| **정답 노트** (gold, required notes) | 그 질문에 꼭 나와야 하는 노트 | `questions.jsonl`의 `required_note_ids` |
| **recall@k** (재현율) | 정답이 상위 k개 안에 들었는가 | 3위 → recall@10 = 1, recall@1 = 0 |
| **precision** (정밀도) | 돌려준 것 중 정답 비율 | 10개 중 정답 2개 → 0.2 |
| **MRR** (mean reciprocal rank) | 정답 첫 등장 순위의 역수 평균. 높을수록 위에서 찾음 | 1위 1.0, 2위 0.5 |
| **hit** | 질문 하나에서 정답을 찾았는가 (찾음/못 찾음) | hits 43 → 62 |
| **베이스라인** (baseline) | 바꾸기 전 점수. 바뀐 걸 비교하는 기준 | `eval --baseline` |
| **holdout** | 고칠 때 보지 않은 확인용 질문 묶음 | 고친 효과가 진짜인지 확인 |
| **과적합** (overfitting) | 재는 질문에만 맞춰져 실제로는 안 좋아진 상태 | holdout으로 잡음 |
| **누수** (leakage) | 질문에 정답 노트의 문장을 베껴 써서 점수가 부풀려진 상태 | 사용자가 실제로 할 말로 질문을 씀 |
| **회귀** (regression) | 고친 뒤 원래 맞던 질문이 틀리게 된 것 | `eval`이 질문별로 보여 줌 |
| **스윕** (sweep) | 값 하나를 여러 개로 바꿔 가며 한꺼번에 재는 것 | `eval --sweep 0.3,0.4,0.5` |
| **부호 검정** (sign test) | 좋아진 질문 수와 나빠진 질문 수가 우연인지 보는 통계 검정 | `decisive`, `p_value` < 0.05 |
